# --log-requests-level

## Кратко

Аргумент читается ровно в одном месте — `RequestLogger._compute_metadata` (`sglang/python/sglang/srt/utils/request_logger.py`), которое возвращает тройку `(max_length, skip_names, out_skip_names)`: предел обрезки строк и списков, набор вырезаемых полей запроса и набор вырезаемых полей ответа. Всё остальное поведение логирования выводится из этой тройки.

Значение по умолчанию — `2`, и на нем содержимое запросов и ответов **уже пишется в лог**. Уровни 0 и 1 — единственные, которые дают гарантию отсутствия текста.

## Оригинальная справка

```text
0: Log metadata (no sampling parameters). 1: Log metadata and sampling parameters. 2: Log metadata, sampling parameters and partial input/output. 3: Log every input/output.
```

## Паспорт аргумента

- Флаги: `--log-requests-level`
- Группа: `observability`
- Тип значения: int
- Допустимые значения: `0`, `1`, `2`, `3` (жесткий `choices` в argparse)
- Значение по умолчанию: `2`
- Эффективное значение: совпадает с заданным; действует только при включенном `--log-requests`. Меняется на живом сервере через `POST /configure_logging`, и там `choices` уже не проверяется
- Где объявлен: `ServerArgs.log_requests_level`, файл — `sglang/python/sglang/srt/server_args.py`
- Статус: обычный
- Этап применения: инициализация `TokenizerManager` → каждый прием и каждое завершение запроса

## Что меняет в движке

Точная таблица из `_compute_metadata`:

| Уровень | `max_length` | Вырезается из запроса (`skip_names`) | Вырезается из ответа (`out_skip_names`) |
| --- | --- | --- | --- |
| 0 | 2³⁰ | `text`, `input_ids`, `input_embeds`, `image_data`, `audio_data`, `video_data`, `mm_data_mooncake`, `lora_path`, `sampling_params` | `text`, `output_ids`, `embedding` |
| 1 | 2³⁰ | то же без `sampling_params` | `text`, `output_ids`, `embedding` |
| 2 | 2048 | ничего | ничего |
| 3 | 2³⁰ | ничего | ничего |

Из таблицы следуют три факта, которые обычно понимают неправильно.

**Первый.** Разница между 2 и 3 — не в том, «пишется содержимое или нет», а только в длине обрезки. На уровне 2 строка длиннее 2048 символов сокращается до `первые 1024 + " ... " + последние 1024` (`_dataclass_to_string_truncated`, `half_length = max_length // 2`). Списки токенов обрезаются по тому же правилу, но по числу элементов. Иначе говоря, «partial input/output» из справки — это два килобайта текста на каждое строковое поле, а не «немного метаданных».

**Второй.** Обрезка применяется к **каждой строке в отдельности**, включая вложенные. Диалог из пятидесяти сообщений на уровне 2 даст до пятидесяти фрагментов по 2048 символов, а не 2048 символов на весь запрос.

**Третий.** Уровень ≥ 2 включает дополнительную точку логирования, которой на 0 и 1 нет вообще: `OpenAIServingBase.handle_request` вызывает `log_openai_received_request` и печатает **сырое тело OpenAI-запроса** до адаптации — то есть `messages` как их прислал клиент (`sglang/python/sglang/srt/entrypoints/openai/serving_base.py`). Строка начинается с `Receive OpenAI: obj=`.

Есть и побочный эффект в самом движке: при уровне ≥ 2, если запрос пришел токенами (`obj.text is None`, `obj.input_ids` заданы), `log_received_request` детокенизирует промпт и записывает результат обратно в `obj.text`. Это блок, помеченный в исходниках как `FIXME`; он добавляет полное декодирование промпта в путь приема запроса.

Наконец, `skip_names` фильтрует **только поля верхнего уровня** объекта запроса: и `_dataclass_to_string_truncated`, и `_transform_data_for_logging` передают вложенным значениям пустой набор. Для `GenerateReqInput` этого достаточно (`text` и `input_ids` — поля верхнего уровня), но полагаться на список как на универсальный редактор содержимого нельзя.

## Значения и формат

- `0` — метаданные без `sampling_params`: идентификатор запроса, флаги потока, служебные поля. Самый тихий полезный режим.
- `1` — то же плюс `sampling_params` (температура, `max_new_tokens`, штрафы, грамматики). Текста по-прежнему нет. Это правильный выбор для «хочу видеть, кто и с какими параметрами ходит».
- `2` (по умолчанию) — всё, включая текст промпта и ответа, каждое строковое поле обрезано до 2048 символов, плюс отдельная строка с сырым OpenAI-телом.
- `3` — то же без практической обрезки (`2³⁰`).
- Значение вне `0..3` argparse отвергает. Через `POST /configure_logging` его можно протолкнуть, и тогда `_compute_metadata` бросит `ValueError: Invalid --log-requests-level: self.log_requests_level=…` прямо в обработчике — запрос вернет 500, а `RequestLogger` останется в несогласованном состоянии.
- Без `--log-requests` аргумент не делает ничего: `log_received_request` и `log_finished_request` выходят по первой же проверке.

## Когда использовать

- Нужны параметры сэмплирования при разборе «модель отвечает не так» — `1`.
- Нужен ровно текст, который увидел движок после применения шаблона чата, — `2` достаточно; `3` имеет смысл только когда важны хвосты длиннее двух килобайт (длинные структурированные ответы, полные трассировки вызовов инструментов).
- Нужен учет обращений без содержимого — `0`.
- Не оставляйте значение по умолчанию на сервере, который обслуживает реальные данные: `--log-requests` без явного `--log-requests-level` — это уровень 2 со всем содержимым.

## Влияние на производительность и память

- На VRAM и forward не влияет.
- Стоимость растет ступенчато: 0 и 1 — короткая строка на запрос; 2 — до нескольких килобайт на запрос плюс отдельная строка сырого OpenAI-тела; 3 — объем, равный суммарному объему промптов и ответов.
- На уровнях ≥ 2 добавляется детокенизирование промпта для token-in-запросов.
- Дисковое место при 3 и длинных контекстах — самая частая причина неожиданного заполнения раздела с логами.

## Взаимодействие с другими аргументами

- `--log-requests`: без него уровень не действует.
- `--log-requests-format`: `json` использует ту же тройку `(max_length, skip_names, out_skip_names)`, отличается только сериализация.
- `--log-requests-target`: определяет, куда именно уйдет этот объем.
- `--crash-dump-folder`: независимый механизм, свой список исключаемых ключей `meta_info`.
- Переменная окружения `SGLANG_LOG_REQUEST_EXCEEDED_MS` (не CLI): при значении > 0 строка завершения печатается только для запросов дольше указанного порога — способ оставить уровень 3 и не утонуть в объеме.

## Типовые проблемы и диагностика

- **Симптом:** ожидали «метаданные», получили диалоги. **Причина:** уровень по умолчанию 2. **Лечение:** явный `--log-requests-level 1`.
- **Симптом:** в логе есть `Receive: obj=` и `Finish: obj=`, но нет `Receive OpenAI: obj=`. **Причина:** уровень ниже 2 либо запрос пришел на `/generate`, а не на OpenAI-совместимый маршрут.
- **Симптом:** текст в логе оборван посередине и склеен через ` ... `. **Причина:** уровень 2, обрезка 1024 + 1024 символа. **Лечение:** `3`, если хвост действительно нужен.
- **Симптом:** после `POST /configure_logging` сервер отвечает 500 на этот запрос. **Причина:** передан уровень вне `0..3`. **Лечение:** повторить с корректным значением.
- **Проверка принятого значения:** дамп `server_args=` при старте содержит `log_requests_level=`.

## В arriero

Граница «0/1 против 2/3» здесь важнее, чем где-либо еще, потому что разбор лога (`apps/api/src/process/log-parsers/sglang.ts`) классифицирует строки по тексту: любая строка со словами `error`, `fatal`, `failed`, `exception`, `traceback`, `out of memory`, `oom` считается ошибкой инстанса, а `warn`/`warning` — предупреждением. На уровнях 2 и 3 эти слова приходят из пользовательских промптов и ответов модели, и здоровый инстанс уходит в `degraded` (`apps/api/src/process/health-summary.ts`) из-за содержимого чужого сообщения.

На уровнях 0 и 1 текста в логе нет, и этот класс ложных срабатываний исчезает полностью. Это и есть рекомендуемая настройка для управляемого инстанса; содержимое, если оно нужно, захватывается узлом `capture-request` в конвейере прокси — с отдельными файлами и 30-дневным сроком хранения (`docs/API_PROXY_FOUNDATION.md`, arriero).

## Примеры

```bash
python -m sglang.launch_server --model-path /models/Qwen3-30B-A3B --host 127.0.0.1 --port 30000 --log-requests --log-requests-level 1
```

```bash
python -m sglang.launch_server --model-path /models/Qwen3-30B-A3B --host 127.0.0.1 --port 30000 --log-requests --log-requests-level 3 --log-requests-target /var/log/sglang-requests
```
