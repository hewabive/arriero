# --skip-server-warmup

## Кратко

После старта scheduler'ов SGLang поднимает фоновый поток `_wait_and_warmup`, который стучится в собственный HTTP-порт: сначала опрашивает `/model_info` (до 120 попыток с интервалом в секунду), затем шлет один настоящий запрос генерации. Только после успеха `server_status` переводится в `Up`, и `/health` начинает отвечать 200 вместо 503.

`--skip-server-warmup` убирает и опрос, и запрос: статус `Up` выставляется сразу. Это ускоряет момент, когда сервер считается готовым, но убирает и защиту — при неудачном прогреве штатная ветка вызывает `kill_process_tree(os.getpid())`, то есть неработающий сервер убивает себя, а не отдает ошибки клиентам.

## Оригинальная справка

```text
If set, skip warmup.
```

## Паспорт аргумента

- Флаги: `--skip-server-warmup`
- Группа: `serving`
- Тип значения: bool; поле объявлено как `bool`, argparse получает `action="store_true"`, парного `--no-*` нет
- Допустимые значения: флаг без значения
- Значение по умолчанию: `False`
- Эффективное значение: **принудительно `True`** в двух случаях, оба в `__post_init__`: при заданном `--debug-tensor-dump-output-folder` (лог: `Cuda graph and server warmup are disabled because of using tensor dump mode`) и при заданном `--msprobe-dump-config` (лог: `... warmup is disabled(skip_server_warmup=True) because there is no need to dump data for this stage`). Оба случая заодно выключают CUDA graph. Отдельно прогрев пропускается для elastic-EP joiner'а (`is_ep_scale_joiner`) — там это не связано с флагом
- Где объявлен: `ServerArgs.skip_server_warmup`, файл — `sglang/python/sglang/srt/server_args.py`
- Статус: обычный
- Этап применения: `__post_init__` (принудительные включения) → HTTP-слой, поток `_wait_and_warmup` внутри lifespan приложения

## Что меняет в движке

### Что делает штатный прогрев

`_execute_server_warmup` (`entrypoints/http_server.py`):

1. строит URL из `ServerArgs.url()` (петля вместо `0.0.0.0`, схема `https` при заданном `--ssl-certfile`), добавляет `Authorization: Bearer <api_key>`, если ключ задан, и берет `verify=` из `ssl_verify()`;
2. до 120 секунд опрашивает `/model_info`; при неуспехе логирует `Initialization failed. warmup error: …` и **убивает дерево процессов**;
3. формирует запрос: `/generate` для генеративной модели, `/encode` для эмбеддингов, `/v1/chat/completions` с картинкой для VLM (когда не задан `--skip-tokenizer-init`), `input_ids` вместо текста при `--skip-tokenizer-init`. Количество элементов текста равно `--dp-size`;
4. шлет запрос с таймаутом `SGLANG_WARMUP_TIMEOUT` (по умолчанию `-1`, что означает 600 секунд для обычного режима и 1800 для PD-disaggregation) и при успехе ставит `server_status = ServerStatus.Up`. При исключении — снова `kill_process_tree`.

Затем печатается строка `The server is fired up and ready to roll!` — она появляется в обоих случаях, с прогревом и без, поэтому сама по себе не доказывает, что прогрев состоялся.

### Что происходит с флагом

`_wait_and_warmup` пропускает вызов `execute_warmup_func` и напрямую выполняет `_global_state.tokenizer_manager.server_status = ServerStatus.Up`. Ни `/model_info`, ни `/generate` не запрашиваются.

### Почему это влияет на `/health`

Обработчик `/health` (он же `/health_generate`) возвращает 503, пока `server_status == ServerStatus.Starting`. Дальше поведение зависит от `SGLANG_ENABLE_HEALTH_ENDPOINT_GENERATION` (по умолчанию `True`): в этом режиме `/health` ставит в очередь генерацию одного токена и ждет ответа детокенизатора, опрашивая состояние раз в секунду до `SGLANG_HEALTH_CHECK_TIMEOUT` (по умолчанию 20 секунд). То есть даже успешный `/health` занимает не меньше секунды.

Важно, что модель к этому моменту уже загружена в любом случае: HTTP-сервер стартует после `wait_for_ready()`. `--skip-server-warmup` не ускоряет загрузку весов и не пропускает захват CUDA graph — он убирает только прогревочный запрос.

## Значения и формат

- Флаг без значения.
- Отключить принудительное включение нельзя: при `--debug-tensor-dump-output-folder` или `--msprobe-dump-config` прогрев выключается независимо от вашего выбора.
- На пользовательские прогревы из `--warmups` флаг не влияет — это разные механизмы (см. `warmups.md`).

## Когда использовать

- Отладочные и профилировочные запуски, где лишний запрос портит картину: дампы тензоров, замеры первого запроса, воспроизведение конкретной последовательности обращений.
- Ситуация, когда прогрев не проходит по внешней причине, а не из-за модели: например, `--api-key` задан, а вы измеряете время старта и не хотите ждать таймаута.
- Модели с очень дорогой JIT-компиляцией ядер, где вы сознательно переносите эту стоимость на первый реальный запрос ради более раннего старта, — но тогда учитывайте, что первый клиент получит эту задержку целиком.
- **Не** используйте в продакшне по умолчанию: вы теряете единственную автоматическую проверку того, что связка «токенизатор — планировщик — модель — детокенизатор» вообще работоспособна. Известный класс отказов SGLang-KT — HTTP 200 при семантически испорченном выводе (`docs/KTRANSFORMERS_OPERATIONS.md`); прогрев его не поймает, но поймает более грубые поломки конвейера.

## Влияние на производительность и память

- VRAM: косвенно. Прогревочный forward выделяет рабочие буферы и запускает JIT-компиляцию ядер (Triton, DeepGEMM), поэтому без него пик потребления сдвигается на первый клиентский запрос. Для конфигураций, живущих на грани `--mem-fraction-static`, это означает, что OOM проявится не на старте, а под нагрузкой.
- Время старта: экономия от нескольких секунд до минут — ровно столько, сколько занимал бы прогревочный forward и опрос `/model_info`.
- Latency первого запроса: растет на ту же величину.
- На throughput в установившемся режиме не влияет.

## Взаимодействие с другими аргументами

- `--warmups`: независим. Пользовательские прогревы выполняются в lifespan **до** старта прослушивания и не отменяются этим флагом.
- `--skip-tokenizer-init`: меняет форму прогревочного запроса (`input_ids` вместо текста), но не отменяет его.
- `--dp-size`: определяет количество элементов в прогревочном запросе, чтобы задеть все реплики.
- `--disaggregation-mode`: включает отдельную ветку `_send_disaggregation_warmup_requests` по всем DP-рангам с таймаутом 1800 секунд.
- `--debug-tensor-dump-output-folder`, `--msprobe-dump-config`: принудительно включают флаг и выключают CUDA graph.
- `--api-key`: прогревочный клиент сам подставляет ключ, поэтому включение ключа прогрев не ломает.
- `--ssl-ca-certs`: определяет `verify=` для прогревочного HTTPS-клиента; при включенном TLS без CA-бандла верификация отключается с предупреждением.

## Типовые проблемы и диагностика

- **Симптом:** сервер загрузил модель и через некоторое время сам себя убил, в логе `Initialization failed. warmup error: …`. **Причина:** прогревочный запрос не прошел. **Диагностика:** трассировка в той же строке; частые причины — несовместимая конфигурация backend'а внимания, нехватка памяти на первом forward, недоступность собственного адреса (`--host` указывает на интерфейс, которого нет). **Обход на время диагностики:** `--skip-server-warmup`, чтобы сервер поднялся и можно было отправить запрос вручную и увидеть настоящую ошибку.
- **Симптом:** `/health` возвращает 503 несколько минут после появления строк о готовности в логе. **Причина:** прогрев еще идет, `server_status` все еще `Starting`. **Лечение:** ждать; это ожидаемое поведение, и arriero трактует его так же (`docs/KTRANSFORMERS_OPERATIONS.md`: «HTTP 503 means loading even if the log parser has seen a ready-looking line»).
- **Симптом:** первый клиентский запрос выполняется в разы дольше последующих. **Причина:** прогрев пропущен, JIT-компиляция ядер пришлась на него. **Лечение:** снять флаг либо прогреть вручную.
- **Симптом:** флаг не задан, а прогрев не выполнялся. **Причина:** включен `--debug-tensor-dump-output-folder` или `--msprobe-dump-config`. **Подтверждение:** предупреждение в логе про отключение прогрева и CUDA graph.
- **Подтверждение того, что прогрев прошел:** в логе видны последовательно опрос `/model_info`, затем строка `The server is fired up and ready to roll!` и переход `/health` в 200.

## В arriero

Менеджер выводит готовность инстанса из HTTP-пробы `/health` (`apps/api/src/process/health-summary.ts`), а не из логов, — лог-парсер SGLang дает только прогресс загрузки. Поэтому `--skip-server-warmup` напрямую влияет на то, как быстро инстанс перейдет в `ready`: без прогрева это произойдет сразу после старта HTTP-сервера.

Это не выигрыш, а риск. Прокси arriero начнет направлять запросы в цель, как только она станет `ready`, и первый же запрос примет на себя всю стоимость прогрева. При эвикции по политике `idle-only` (дефолт для kind `ktransformers`) это особенно неприятно: каждый цикл «остановили — подняли» будет отдавать первому запросу полную задержку JIT.

Кроме того, проба `/health` у ktransformers-инстанса выполняется с таймаутом 15 секунд (`apps/api/src/process/engine-probe.ts`), а сам `/health` по умолчанию генерирует токен и может ждать до 20 секунд. На занятом или подвисшем движке проба отвалится по таймауту менеджера раньше, чем сервер ответит 503, — это выглядит как ошибка соединения, а не как «не готов».

Рекомендация для профиля из `docs/KTRANSFORMERS_OPERATIONS.md`: флаг не задавать, пусть прогрев остается ранним фильтром неработоспособной сборки.

## Примеры

```bash
python -m sglang.launch_server --model-path /models/Qwen3-30B-A3B --host 127.0.0.1 --port 30000 --skip-server-warmup
```

```bash
python -m sglang.launch_server --model-path /models/Qwen3-30B-A3B --host 127.0.0.1 --port 30000 --skip-server-warmup --warmups prefill_shapes
```
