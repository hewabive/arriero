# --scheduler-recv-interval

## Кратко

Каждая итерация цикла планировщика начинается с опроса каналов, по которым приходят токенизированные запросы и управляющие команды. На чистом decode этот опрос — заметная доля времени CPU-цикла. `--scheduler-recv-interval` позволяет опрашивать не каждую итерацию. Реализовано это не простым «каждый N-й раз», а счетчиком с весами по типу предыдущего батча, поэтому prefill никогда не пропускает опрос.

## Оригинальная справка

```text
The interval to poll requests in scheduler. Can be set to >1 to reduce the overhead of this.
```

## Паспорт аргумента

- Флаги: `--scheduler-recv-interval`
- Группа: `schedule`
- Тип значения: целое
- Допустимые значения: не ограничены; проверок при старте нет
- Значение по умолчанию: `1` — опрос на каждой итерации
- Эффективное значение: не переопределяется. При значении `<= 1` объект-пропускатель вообще не создается (`SchedulerRecvSkipper.maybe_create` возвращает `None`), и код опроса работает по старому пути
- Где объявлен: `ServerArgs.scheduler_recv_interval`, файл — `sglang/python/sglang/srt/server_args.py`
- Статус: обычный
- Этап применения: создание `SchedulerRecvSkipper` при инициализации планировщика → начало каждой итерации цикла (`recv_requests`)

## Что меняет в движке

`SchedulerRecvSkipper` (`sglang/python/sglang/srt/managers/scheduler_components/recv_skipper.py`) на каждой итерации прибавляет к счетчику вес, зависящий от режима **предыдущего** батча, и опрашивает каналы только когда счетчик достиг порога (после чего счетчик обнуляется):

| режим предыдущего батча | вес (переменная окружения) | значение по умолчанию |
| --- | --- | --- |
| `DECODE` | `SGLANG_SCHEDULER_RECV_SKIPPER_WEIGHT_DECODE` | 1 |
| `TARGET_VERIFY` (спекуляция) | `SGLANG_SCHEDULER_RECV_SKIPPER_WEIGHT_TARGET_VERIFY` | 1 |
| батча не было (idle) | `SGLANG_SCHEDULER_RECV_SKIPPER_WEIGHT_NONE` | 1 |
| все остальные (prefill/extend и прочие) | `SGLANG_SCHEDULER_RECV_SKIPPER_WEIGHT_DEFAULT` | 1000 |

Отсюда практический смысл: после prefill-прохода счетчик перескакивает порог сразу (1000 против типичного порога в единицы), и опрос происходит немедленно. Пропускаются только итерации внутри непрерывной серии decode-шагов, то есть `--scheduler-recv-interval 4` означает «во время генерации опрашивать вход раз в 4 decode-шага».

При DP attention режим предыдущего батча берется не локальный, а согласованный между рангами (`recv_skipper_forward_mode`, вычисляется `derive_forward_mode` из собранных all-gather'ом режимов): решение об опросе обязано быть одинаковым на всех рангах, иначе широковещательная рассылка запросов рассинхронизируется. Правило свертки: любой extend-подобный ранг ⇒ `EXTEND` (то есть опрос), только `TARGET_VERIFY` ⇒ `TARGET_VERIFY`, иначе `DECODE`; полностью idle-набор считается «батча не было».

Пропуск опроса откладывает не только новые запросы, но и все управляющие сообщения, идущие тем же каналом (в том числе abort'ы).

## Значения и формат

- Целое число — порог взвешенного счетчика, а не «каждый N-й раз» в чистом виде.
- `1` (по умолчанию) и любое значение `<= 1` — пропусков нет.
- Практический диапазон — единицы: при весе decode-шага 1 значение `4` дает опрос раз в 4 decode-шага.
- Большие значения (десятки и выше) заметно увеличивают задержку постановки новых запросов в очередь и задержку обработки abort'ов.
- Веса настраиваются только переменными окружения, CLI-аргументов для них нет.

## Когда использовать

- Профиль показывает заметную долю времени scheduler-процесса в опросе каналов, а нагрузка — длинные генерации при небольшом потоке новых запросов.
- Много DP-рангов и высокая частота decode-шагов: экономия умножается на число процессов.
- Не увеличивайте на интерактивной нагрузке с коротким TTFT-бюджетом: каждый пропуск добавляет запросу до `N-1` decode-шагов ожидания перед постановкой в очередь.
- Не используйте `--num-continuous-decode-steps` для той же цели — в текущей версии кода он не читается вовсе.

## Влияние на производительность и память

- На память не влияет.
- Снижает нагрузку на CPU scheduler-процесса; на GPU-загрузку влияет только косвенно, через уменьшение простоя между шагами.
- TTFT растет в среднем на половину интервала, в худшем случае — на полный интервал в decode-шагах.
- Реакция на abort и на управляющие команды замедляется на ту же величину.
- На время старта влияния нет.

## Взаимодействие с другими аргументами

- `--enable-dp-attention`: включает согласованный между рангами выбор режима; без него берется локальный режим последнего батча.
- `--max-running-requests`: чем больше decode-батч, тем длиннее серии decode-шагов и тем больше выигрыш от пропусков.
- `--disable-overlap-schedule`: меняет структуру цикла и долю времени, приходящуюся на опрос; выигрыш от аргумента при этом обычно меньше.
- `--max-queued-requests`: отказ по переполнению очереди проверяется в момент постановки в очередь, то есть тоже откладывается пропуском опроса.
- `--num-continuous-decode-steps`: исторический аналог, сегодня не работает.

## Типовые проблемы и диагностика

- Выросло время до появления запроса в `#queue-req` — прямое следствие интервала; уменьшите значение.
- Abort'ы обрабатываются с задержкой — та же причина: команды идут тем же каналом.
- Значение задано, но эффекта нет: проверьте, что оно больше 1 — при `<= 1` пропускатель не создается вообще.
- Принятое значение видно в дампе `server_args=` при старте. Отдельной метрики или лог-строки у механизма нет.

## Примеры

```bash
python -m sglang.launch_server --model-path /models/Qwen3-30B-A3B --scheduler-recv-interval 4 --max-running-requests 128
```

```bash
python -m sglang.launch_server --model-path /models/Qwen3-30B-A3B --enable-dp-attention --dp-size 2 --tp-size 2 --scheduler-recv-interval 2
```
