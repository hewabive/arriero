# --weight-cache-timeout

## Кратко

Единственная точка применения аргумента — цикл ожидания в `Engine._launch_weight_cache_daemons`: движок породил процессы демонов и ждет появления их `.ready`-файлов. Значение по умолчанию 1800 секунд рассчитано на большие модели и медленные диски. В режиме `client` таймаут не используется вовсе: там подключение к сокету идет с зашитым в код лимитом 30 секунд.

## Оригинальная справка

```text
Timeout in seconds for weight cache daemon readiness (default: 1800).
```

## Паспорт аргумента

- Флаги: `--weight-cache-timeout`
- Группа: `model`
- Тип значения: целое, секунды
- Допустимые значения: `choices` нет; проверок диапазона нет
- Значение по умолчанию: `1800`
- Эффективное значение: не переопределяется
- Где объявлен: `ServerArgs.weight_cache_timeout`, файл — `sglang/python/sglang/srt/server_args.py`
- Статус: обычный
- Этап применения: запуск демонов в `Engine._launch_weight_cache_daemons`, до запуска scheduler-процессов

## Что меняет в движке

`_launch_weight_cache_daemons` (`sglang/python/sglang/srt/entrypoints/engine.py`) после `subprocess.Popen` каждого демона входит в цикл ожидания: для каждой пары `(pp_rank, tp_rank)` вычисляет `global_rank`, берет путь `.ready`-файла и опрашивает его существование с интервалом 2 секунды. Таймаут отсчитывается **суммарно от начала ожидания всех демонов**, а не для каждого по отдельности: `start_time` фиксируется один раз до цикла.

В том же цикле на каждой итерации проверяется, живы ли порожденные процессы: если любой из них уже завершился, поднимается `RuntimeError` не дожидаясь таймаута.

Любое исключение из этого блока (таймаут, преждевременная смерть демона, прерывание) приводит к `_terminate_weight_cache_daemons`: сначала SIGTERM, чтобы демоны сами удалили свои `.sock`/`.ready`, затем SIGKILL отставшим. Это сделано специально — иначе следующая попытка старта в режиме `client` наткнется на устаревший сокет и получит невнятное «socket exists but connection refused» вместо чистого «демона нет».

Отдельно стоит помнить: у standalone-демона есть **свой** `--timeout` с тем же значением по умолчанию 1800 — он используется многоранговым режимом самого демона (`launch_weight_cache_daemons`) и никак не связан с этим аргументом сервера.

## Значения и формат

- Целое число секунд. Отрицательные значения и ноль argparse примет; ноль означает, что первая же проверка после `time.sleep(2)` превысит лимит и даст `TimeoutError`.
- Единица опроса — 2 секунды, поэтому реальная гранулярность отказа около этого шага.
- Значение не читается, если `--weight-cache-mode` равен `off` или `client`.

## Когда использовать

- Модель большая и лежит на медленном или сетевом хранилище, а демоны не успевают загрузиться за штатные 30 минут — увеличивайте.
- Автоматизированный запуск, где долгое зависание хуже быстрого отказа: уменьшайте до величины, заведомо превышающей нормальное время загрузки демона (проверьте по логу его `.ready`).
- Не трогайте, если используете `client`: аргумент там не читается, и ожидание готовности демона в этом режиме вообще не предусмотрено — сокета либо нет, либо есть.
- Не пытайтесь этим таймаутом лечить `Refusing to connect` или несовпадение `CacheConfig`: это мгновенные отказы, не связанные со временем.

## Влияние на производительность и память

На производительность и память не влияет: значение задает только верхнюю границу ожидания при старте в режиме `daemon`. Косвенное влияние на время старта одно — слишком маленькое значение превращает нормальную долгую загрузку в отказ и заставляет начинать заново.

## Взаимодействие с другими аргументами

- `--weight-cache-mode`: аргумент имеет смысл только при значении `daemon`.
- `--weight-cache-socket`: путь клиента; если он расходится с путем, который биндит демон, ожидание `.ready` пройдет успешно, а подключение все равно упадет — таймаут тут не поможет.
- `--tp-size`, `--pp-size`: определяют число демонов, которых надо дождаться, при неизменном общем бюджете времени.
- Все аргументы, влияющие на скорость загрузки весов демоном (`--load-format`, `--weight-loader-*`, расположение чекпойнта), задают, сколько времени реально нужно.

## Типовые проблемы и диагностика

- `TimeoutError: Weight cache daemon for pp_rank=<i> tp_rank=<j> did not become ready within <t>s` — не хватило времени. Посмотрите лог самого демона: если он еще читал веса, увеличивайте значение.
- `RuntimeError: Weight cache daemon (pid=<p>) exited prematurely with code <c>` — демон упал; таймаут ни при чем, разбирайтесь по его выводу.
- После любого из этих отказов движок гасит уже запущенные демоны — повторный запуск не должен натыкаться на устаревшие файлы; если наткнулся, у standalone-демона есть `--force`.
- Успешное ожидание подтверждают строки `Weight cache daemon for pp_rank=<i> tp_rank=<j> is ready` и `All <n> weight cache daemons on node <r> are ready`.
- Принятое значение видно в дампе `server_args=` при старте (`sglang/python/sglang/srt/entrypoints/engine.py`).

## Примеры

```bash
python -m sglang.launch_server --model-path /mnt/nfs/models/Qwen3-30B-A3B --weight-cache-mode daemon --weight-cache-timeout 3600 --host 127.0.0.1 --port 30000
```

```bash
python -m sglang.launch_server --model-path /models/Qwen3-30B-A3B --weight-cache-mode daemon --weight-cache-timeout 300 --mem-fraction-static 0.6
```
