# --cpu-offload-gb

## Кратко

`--cpu-offload-gb` включает первую (простую) схему оффлоада: движок обходит слои модели по порядку и переносит их параметры в закрепленную (pinned) память хоста, пока суммарный объем перенесенного не достигнет заданного числа гигабайт. У каждого затронутого модуля подменяется `forward`: перед вычислением весь его `state_dict` копируется обратно на GPU, вычисление выполняется через `functional_call`, после чего копия отбрасывается.

Именно из этого следует главное свойство: перенесенные веса едут по PCIe **на каждый forward**, то есть на каждый токен декодирования. На хосте из квалифицированного профиля arriero (одна RTX A5000, PCIe 4.0 x16, практическая полоса порядка 20–25 ГБ/с) 8 ГиБ вынесенных весов — это около 0.35 с чистого копирования на один decode-шаг. Аргумент имеет смысл ровно тогда, когда альтернатива — не запустить модель вовсе.

## Оригинальная справка

```text
How many GBs of RAM to reserve for CPU offloading.
```

## Паспорт аргумента

- Флаги: `--cpu-offload-gb`
- Группа: `exec.offload`
- Тип значения: int (гигабайты, домножаются на `1024**3`)
- Допустимые значения: неотрицательное целое; `0` отключает
- Значение по умолчанию: `0`
- Эффективное значение: совпадает с заданным; автоподбора нет
- Где объявлен: `ServerArgs.cpu_offload_gb`, файл — `sglang/python/sglang/srt/server_args.py`
- Статус: обычный
- Этап применения: создание `ModelRunner` (`create_offloader_from_server_args`) → построение слоев модели (`make_layers`) → каждый forward затронутых модулей

## Что меняет в движке

`create_offloader_from_server_args` (`sglang/python/sglang/srt/utils/offloader.py`) выбирает реализацию по одному правилу: значение больше нуля → `OffloaderV1`; иначе, если задан `--offload-group-size` больше нуля → `OffloaderV2`; иначе — заглушка. Две схемы взаимно исключены жестким ассертом `V2 offload does not support cpu_offload_gb yet`.

`OffloaderV1.maybe_offload_to_cpu` работает **по параметрам**, а не по модулям: обход идет по слоям в порядке построения, и как только накопленный объем достигает лимита, перенос прекращается — последний затронутый модуль может оказаться перенесенным частично. Копия на хосте создается через `torch.empty_strided(..., pin_memory=is_pin_memory_available())`, то есть занимает закрепленную, не вытесняемую в своп память.

Подмена `forward`:

```python
device_state = {k: v.to(device, non_blocking=True) for k, v in module.state_dict().items()}
output = functional_call(module, device_state, args=args, kwargs=kwargs)
```

Копирование идет в текущем потоке CUDA, без отдельного stream'а и без предвыборки. Ни асинхронности, ни перекрытия с вычислениями здесь нет — этим занимается только вторая схема (`--offload-group-size`).

Важно, что эта схема работает на **любой** модели, построенной через `make_layers`/`make_layers_non_pp`, — в отличие от V2, которой нужна поддержка со стороны модели.

## Значения и формат

- Целое число гигабайт (двоичных: множитель `1024**3`). Дробные значения argparse не примет — тип `int`.
- `0` — оффлоад выключен, это значение по умолчанию.
- Значение — верхняя граница объема перенесенного, а не точный объем: перенос прекращается на первом параметре, после которого лимит исчерпан.
- Проверки «влезет ли в RAM хоста» нет. Если закрепленной памяти не хватит, вы получите ошибку аллокации от PyTorch на этапе загрузки весов.
- Значение действует на каждый TP/PP-ранг отдельно: при `--tp-size 2` суммарный расход RAM хоста удваивается.

## Когда использовать

- Когда веса не помещаются в VRAM даже при агрессивной квантизации, и цель — работоспособность, а не скорость: одиночные запросы, batch-обработка без требований к latency.
- Как временную меру, чтобы измерить реальные потребности модели перед подбором квантизации или второй карты.
- Не использовать для MoE-моделей на пути KTransformers: там за вынос экспертов на CPU отвечает своя, гораздо более эффективная схема (`--kt-num-gpu-experts`, `--kt-cpuinfer`) с CPU-вычислением вместо копирования весов туда-обратно.
- Не использовать ради увеличения KV-пула: освобожденная VRAM действительно достанется пулу, но decode станет на порядок медленнее.

## Влияние на производительность и память

- VRAM: освобождает примерно заданный объем под весами. Поскольку KV-пул считается от **свободной памяти после загрузки весов**, освобожденное автоматически уходит в пул — отдельно менять `--mem-fraction-static` не требуется, но резерв под активации при этом не растет.
- RAM хоста: занимает заданный объем **закрепленной** памяти на каждый ранг. Такая память не участвует в подкачке, и она же конкурирует за хостовый пул arriero (`docs/RESOURCE_MANAGEMENT.md`) — заявку `host` в memory-draw инстанса нужно увеличивать вручную.
- Время старта: перенос выполняется при загрузке весов, добавляется одно полное копирование в закрепленную память.
- Latency decode: линейно растет с объемом оффлоада. Оценка — `объем / полоса PCIe` на каждый forward.
- Throughput: копирование не зависит от размера батча, поэтому большой батч частично амортизирует расход. На батче 1 накладные расходы максимальны.
- CUDA graph: `--cpu-offload-gb` больше нуля попадает в список причин отключения piecewise-графа (наравне с `--enable-hierarchical-cache`).

## Взаимодействие с другими аргументами

- `--offload-group-size`: включает вторую схему и требует `--cpu-offload-gb 0`; комбинация падает ассертом.
- `--offload-mode`, `--offload-num-in-group`, `--offload-prefetch-step`: относятся только ко второй схеме и при `--cpu-offload-gb` не читаются.
- `--mem-fraction-static`: KV-пул сам заберет освобожденную VRAM; при явно заданной статике проверьте, что резерв под активации остался достаточным.
- `--disable-piecewise-cuda-graph`: piecewise-граф в этом режиме отключается автоматически, задавать флаг вручную не нужно.
- `--quantization`: почти всегда более выгодная альтернатива — уменьшает и VRAM, и трафик, а не переносит трафик на PCIe.
- `--kt-num-gpu-experts` / `--kt-cpuinfer`: правильный механизм разделения GPU/CPU для MoE в профиле KTransformers.

## Типовые проблемы и диагностика

- `AssertionError: V2 offload does not support cpu_offload_gb yet` — заданы оба механизма сразу; оставьте один.
- Резкое падение скорости декодирования (в разы или на порядок) сразу после включения — это ожидаемое поведение, а не сбой.
- Ошибка аллокации закрепленной памяти на этапе загрузки весов — на хосте нет столько свободной RAM либо уперлись в лимит `RLIMIT_MEMLOCK`.
- Ожидали освобождения VRAM, но ее не прибавилось — лимит исчерпался на первых же слоях (перенос идет по порядку построения слоев) либо параметры модуля уже были на CPU.
- Что смотреть: `cpu_offload_gb=` в дампе `server_args=` при старте, `nvidia-smi` для фактического потребления VRAM и строку с `max_total_num_tokens=…, available_gpu_mem=… GB` — освободившаяся память видна там как выросший пул.

## Примеры

```bash
python -m sglang.launch_server --model-path /models/Qwen3-30B-A3B --cpu-offload-gb 8
```

```bash
python -m sglang.launch_server --model-path /models/Qwen3-30B-A3B --cpu-offload-gb 12 --mem-fraction-static 0.85 --max-running-requests 2
```
