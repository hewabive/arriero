# --gc-warning-threshold-secs

## Кратко

Флаг вешает callback на сборщик мусора Python и печатает предупреждение, если один цикл GC занял дольше заданного времени. Нужен ровно для одной задачи — доказать или опровергнуть гипотезу «периодические провалы latency вызваны сборкой мусора». Ставится только в **tokenizer**-процессе, то есть в том, который принимает HTTP-запросы и стримит ответы; на scheduler-процесс, где живет forward, он не влияет. Значение по умолчанию `0.0` означает «выключено», и это не подстановка, а буквально условие `> 0.0` в коде.

## Оригинальная справка

```text
The threshold for long GC warning. If a GC takes longer than this, a warning will be logged. Set to 0 to disable.
```

## Паспорт аргумента

- Флаги: `--gc-warning-threshold-secs`
- Группа: `observability`
- Тип значения: float (секунды)
- Допустимые значения: `choices` нет, границы не проверяются. Любое значение `<= 0` эквивалентно «выключено»
- Значение по умолчанию: `0.0` — механизм выключен
- Эффективное значение: совпадает с заданным; ни один `_handle_*` его не переписывает
- Где объявлен: `ServerArgs.gc_warning_threshold_secs`, файл — `sglang/python/sglang/srt/server_args.py`
- Статус: обычный
- Этап применения: конструктор `TokenizerManager` (регистрация callback), далее — каждый цикл GC в этом процессе

## Что меняет в движке

Единственная точка чтения — `TokenizerManager.__init__`:

```python
if self.server_args.gc_warning_threshold_secs > 0.0:
    configure_gc_warning(self.server_args.gc_warning_threshold_secs)
```

`configure_gc_warning` (`sglang/python/sglang/srt/utils/common.py`) добавляет функцию в `gc.callbacks`. На фазе `start` она запоминает время по поколению, на фазе `stop` считает длительность и при превышении порога печатает:

```text
LONG GARBAGE COLLECTION DETECTED | Generation 2 | Duration: 0.4213s | # Objects: gen0=12345, gen1=6789, gen2=987654 | This may cause latency jitter. Consider calling the freeze_gc API after sending a few warmup requests.
```

Уровень записи — предупреждение (`logger.warn`).

Совет из текста сообщения указывает на реальный эндпоинт: `POST /freeze_gc` вызывает `gc.freeze()` и в tokenizer-процессе, и в scheduler-процессах (запрос сначала рассылается планировщикам, потом выполняется локально). Это переносит уже созданные долгоживущие объекты в «замороженное» поколение, которое GC перестает обходить, — правильное лекарство после прогрева.

Существенное ограничение: `configure_gc_warning` не вызывается больше нигде. Ни scheduler, ни detokenizer callback не ставят. Если джиттер вызван сборкой мусора в scheduler-процессе, этот флаг его не покажет.

## Значения и формат

- Секунды, дробные: `--gc-warning-threshold-secs 0.1`.
- `0` (и любое отрицательное) — выключено, callback не регистрируется вовсе.
- Верхней границы нет; слишком большой порог просто никогда не сработает.
- Изменить у работающего сервера нельзя: callback ставится один раз.
- Порог сравнивается с длительностью **одного** цикла GC отдельного поколения, а не с суммой за интервал.

## Когда использовать

- Когда межтокенная задержка имеет регулярные выбросы, не объяснимые нагрузкой: разумный старт — порог около 0.05–0.1 с, чтобы поймать любую заметную паузу и не утонуть в шуме.
- При работе с очень длинными контекстами и большим числом одновременных запросов: в tokenizer-процессе живут структуры на каждый активный запрос, gen2 растет, и полный проход становится дорогим.
- После подтверждения гипотезы — не оставлять флаг, а лечить: прогреть сервер несколькими запросами и вызвать `POST /freeze_gc`.
- Не включать «для профилактики» с порогом вроде `0.001`: предупреждения посыпятся на каждый цикл gen0, а каждое предупреждение само по себе стоит трех полных обходов кучи (см. ниже).
- Не ожидать от флага диагностики пауз в forward — он их не видит.

## Влияние на производительность и память

- VRAM: не затрагивает.
- RAM хоста: не затрагивает.
- Пока порог не превышен, стоимость близка к нулю: два обращения к словарю на каждый цикл GC.
- Когда порог превышен, вызывается `gc_object_counts()` — а это `len(gc.get_objects(0))`, `len(gc.get_objects(1))`, `len(gc.get_objects(2))`, то есть три полных материализации списков объектов соответствующих поколений. На большой куче это **дороже самой сборки мусора**. Именно поэтому слишком низкий порог вреден: диагностика начнет усугублять проблему, которую измеряет.
- Latency: описанный эффект проявляется в tokenizer-процессе, то есть прямо на пути стриминга ответов.

## Взаимодействие с другими аргументами

- `--enable-request-time-stats-logging`: соседний способ увидеть джиттер, но с другой стороны — по времени конкретных запросов в scheduler'е. Совпадение по времени между `LONG GARBAGE COLLECTION DETECTED` и всплеском `forward_duration` — это уже не совпадение.
- `--enable-metrics` и `--bucket-inter-token-latency`: гистограмма межтокенной задержки покажет наличие выбросов, а этот флаг — их причину. Порядок работы обычно такой: сначала увидели хвост в гистограмме, потом включили этот флаг.
- `--soft-watchdog-timeout`: другой класс «зависаний» — там речь о секундах и десятках секунд в scheduler'е, здесь о десятках-сотнях миллисекунд в tokenizer'е.
- `--log-level`: сообщение печатается как предупреждение, поэтому переживает `--log-level warning`, но не `error`.
- `--enable-cudagraph-gc`: относится к сборке мусора во время захвата CUDA graph в другом процессе и с этим флагом не связан.

## Типовые проблемы и диагностика

- Флаг задан, предупреждений нет — либо сборка действительно быстрая, либо джиттер живет в scheduler-процессе, где callback не ставится. Проверьте `gc_warning_threshold_secs=…` в дампе `server_args=` при старте, затем сравните тайминги с `--enable-request-time-stats-logging`.
- Поток предупреждений с длительностями чуть выше порога и растущим `gen0` — порог слишком низкий; поднимите его до 0.1 с.
- Предупреждения про `Generation 2` с длительностью в сотни миллисекунд и `gen2` в миллионах объектов — классический случай: сервер накопил долгоживущие структуры. Прогрейте и вызовите `POST /freeze_gc`.
- Сообщения появились и сразу прекратились после прогрева — нормальное поведение: первые полные сборки после загрузки модели самые дорогие.
- **В arriero:** строка `LONG GARBAGE COLLECTION DETECTED` содержит слово `WARNING`/`warn` и будет подхвачена парсером лога SGLang (`apps/api/src/process/log-parsers/sglang.ts` собирает последние восемь строк, подходящих под `\b(warn|warning)\b`) — то есть предупреждение окажется в блоке warnings инстанса в UI. Если предупреждения идут потоком, они вытеснят из этого блока все остальные, включая содержательные предупреждения старта. Это еще один довод не ставить порог слишком низким.

## Примеры

```bash
python -m sglang.launch_server --model-path /models/DeepSeek-V3 --gc-warning-threshold-secs 0.1
```

```bash
python -m sglang.launch_server --model-path /models/DeepSeek-V3 --gc-warning-threshold-secs 0.05 --enable-request-time-stats-logging
```
