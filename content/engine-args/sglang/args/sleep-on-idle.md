# --sleep-on-idle

## Кратко

По умолчанию цикл scheduler'а крутится непрерывно, и каждый scheduler-процесс держит одно ядро CPU занятым на 100% даже без единого запроса. `--sleep-on-idle` добавляет в конец «пустого» прохода блокирующий `zmq.Poller.poll(1000)`: процесс засыпает до появления сообщения или до истечения секунды. Это чисто хостовая экономия — на GPU и на пропускную способность аргумент не влияет, но на машине с несколькими картами возвращает несколько ядер и снимает лишний нагрев.

## Оригинальная справка

```text
Reduce CPU usage when sglang is idle.
```

## Паспорт аргумента

- Флаги: `--sleep-on-idle`
- Группа: `device`
- Тип значения: bool (`store_true`)
- Допустимые значения: флаг без значения; парного `--no-sleep-on-idle` нет
- Значение по умолчанию: `False`
- Эффективное значение: совпадает с заданным. Дополнительное условие включения — ранг: `IdleSleeper` создается только при `pp_rank == 0 and attn_tp_rank == 0 and attn_cp_rank == 0`, то есть на «ведущих» scheduler'ах, читающих сокеты от tokenizer'а и RPC. Прочие ранги продолжают крутиться
- Где объявлен: `ServerArgs.sleep_on_idle`, файл — `sglang/python/sglang/srt/server_args.py`
- Статус: обычный
- Этап применения: конструктор `Scheduler` (`init_idle_sleeper`), действует на каждом проходе цикла событий

## Что меняет в движке

`init_idle_sleeper` (`sglang/python/sglang/srt/managers/scheduler.py`) регистрирует в `zmq.Poller` два сокета — `recv_from_tokenizer` и `recv_from_rpc` — и складывает объект в `self.idle_sleeper`; при выключенном аргументе туда кладется `None`.

Вызов происходит ровно в одном месте — в конце `on_idle()`, метода, который выполняется, когда `is_fully_idle()` истинно: пуст `running_batch`, нет chunked-запроса и пуста очередь ожидания. `on_idle()` перед сном успевает сделать регулярную работу простоя — проверку инвариантов пулов, публикацию KV-событий, сброс token-ratio и принудительную публикацию load snapshot, чтобы `/get_loads` и DP-балансировка не видели устаревшую нагрузку, — и уже затем вызывает `maybe_sleep_on_idle()`.

`IdleSleeper.maybe_sleep` (`sglang/python/sglang/srt/managers/scheduler_components/idle_sleeper.py`) делает `poller.poll(1000)`: возврат происходит либо немедленно при появлении данных в любом из двух сокетов, либо через секунду. Дополнительно, если переменная `SGLANG_EMPTY_CACHE_INTERVAL` больше нуля, раз в этот интервал на простое вызывается `current_platform.empty_cache()` — освобождение кешированных аллокаций torch.

Есть и вариант для встроенного Rust-сервера (`RustServerIdleSleeper`), который вместо zmq паркуется на кольце запросов; там пробуждение приходит от producer'а мгновенно.

## Значения и формат

- Булев флаг, значения не принимает.
- «Выключено» = не указывать; отдельного отключающего флага нет.
- Длительность сна — константа 1000 мс в коде, аргументом не настраивается.
- На рангах, не удовлетворяющих условию `pp_rank == 0 and attn_tp_rank == 0 and attn_cp_rank == 0`, флаг не даст ничего: они не читают внешние сокеты и просыпаются по внутренним коллективам.

## Когда использовать

- Локальная или полулокальная установка, где сервер большую часть суток простаивает: несколько ядер, занятых на 100%, — это шум вентиляторов, лишние ватты и меньше теплового запаса для того момента, когда запрос все-таки придет. Комментарий в исходнике называет именно этот сценарий.
- Многокарточный хост: без флага занятых ядер ровно столько, сколько scheduler-процессов.
- Хост, где рядом живет что-то еще (сборка, второй движок, десктоп) и постоянные 100% CPU мешают.
- Не включать там, где важна каждая миллисекунда TTFT на первом запросе после паузы и CPU не дефицитен: пробуждение по сокету происходит сразу, но лишний проход через `poll` все же добавляется.
- Не рассматривать как «энергосбережение GPU»: карта при простое и так в низком P-state, флаг про CPU.

## Влияние на производительность и память

- CPU хоста: главный и единственный заметный эффект — одно ядро на ведущий scheduler-процесс перестает крутиться вхолостую.
- Latency: на пробуждение по данным в сокете задержки практически нет (zmq-опрос возвращается по событию). Замедление возможно только для внутренних периодических действий, которые теперь выполняются не чаще раза в секунду.
- Throughput: под нагрузкой ноль — `on_idle()` не вызывается, пока есть что считать.
- VRAM и RAM: не меняются. Косвенно, при заданном `SGLANG_EMPTY_CACHE_INTERVAL`, простой становится моментом освобождения кеша аллокатора torch — то есть флаг делает это освобождение регулярным.

## Взаимодействие с другими аргументами

- `--tp-size` / `--pp-size`: определяют, сколько процессов вообще есть и сколько из них подпадают под условие рангов (спит только `pp_rank == 0`, `attn_tp_rank == 0`, `attn_cp_rank == 0`).
- `--dp-size` / `--enable-dp-attention`: у каждой DP-группы свой ведущий ранг, значит и свой sleeper.
- `--watchdog-timeout`: конфликта нет. Сторожевой пес считает активным только состояние с текущим батчем, поэтому спящий на простое scheduler под таймаут не попадает.
- `--enable-metrics`: публикация метрик простоя (`_maybe_log_idle_metrics`) выполняется в `on_idle()` **до** сна, поэтому не теряется — только реже.

## Типовые проблемы и диагностика

- Флаг задан, а ядро по-прежнему занято на 100% — смотрите, какой именно процесс: `ps -o pid,pcpu,comm -p $(pgrep -d, -f 'sglang::scheduler')`. Ненулевые TP-ранги спать не будут по определению; это ожидаемо.
- Флаг задан, но сервер не простаивает — `is_fully_idle()` требует пустых `running_batch`, `chunked_req` и очереди ожидания. Регулярный health-check со стороны балансировщика не мешает (он идет по HTTP и не создает батч), а вот фоновый поток запросов — мешает.
- Подозрение на задержку первого токена после паузы: измеряйте TTFT на первом запросе после простоя с флагом и без. Сон прерывается событием сокета, поэтому разница должна быть в пределах шума; устойчивая разница означает, что задержка в другом месте.
- Что смотреть в логе: `sleep_on_idle=` в итоговом дампе `server_args=`. Отдельной строки о создании `IdleSleeper` движок не печатает.
- **В arriero:** флаг не заменяет политику простоя менеджера. Остановка и вытеснение простаивающих инстансов — решение прокси-планировщика (`docs/RESOURCE_MANAGEMENT.md`), а `--sleep-on-idle` только снижает потребление CPU процессом, который продолжает жить и держать VRAM.

## Примеры

```bash
python -m sglang.launch_server --model-path /models/Qwen3-30B-A3B --sleep-on-idle
```

```bash
python -m sglang.launch_server --model-path /models/Qwen3-32B --tensor-parallel-size 2 --sleep-on-idle --mem-fraction-static 0.85
```
