# --enable-layerwise-nvtx-marker

## Кратко

Без разметки профиль Nsight Systems выглядит как сплошной поток ядер, в котором тяжело понять, какому слою принадлежит конкретный GEMM. Флаг решает ровно эту задачу: после загрузки весов на модель регистрируются pre/post forward-хуки (`PytHooks.register_hooks`), которые открывают и закрывают NVTX-диапазон вокруг каждого модуля и подкладывают в имя параметры слоя и размерности тензоров. Это диагностическая ручка, а не режим работы: держать ее включенной на боевом инстансе не надо.

## Оригинальная справка

```text
Enable layerwise NVTX profiling annotations for the model.
```

## Паспорт аргумента

- Флаги: `--enable-layerwise-nvtx-marker`
- Группа: `exec.comm` (аргумент попал в группу коммуникаций по месту объявления в датаклассе; к all-reduce и коллективам он отношения не имеет)
- Тип значения: bool (флаг без значения, `store_true`)
- Допустимые значения: `choices` нет
- Значение по умолчанию: `false`
- Эффективное значение: совпадает с заданным — ни один `_handle_*` и ни одно правило `arg_groups/overrides.py` его не переписывают
- Где объявлен: `ServerArgs.enable_layerwise_nvtx_marker`, файл — `sglang/python/sglang/srt/server_args.py`
- Статус: обычный
- Этап применения: разбор CLI → `ModelRunner.load_model` после загрузки весов и предкомпиляции ядер → каждый eager-forward

## Что меняет в движке

Единственная точка чтения в inference-движке — `model_executor/model_runner.py`:

```python
if get_exec().comm.enable_layerwise_nvtx_marker:
    pyt_hooks = PytHooks()
    pyt_hooks.register_hooks(self.model, module_prefix="model")
```

`PytHooks` (`utils/nvtx_pytorch_hooks.py`) обходит дерево модулей, запоминает их имена и вешает форвард-хуки, которые вызывают `torch.cuda.nvtx`. Для типовых слоев (свертки, линейные, нормализации, внимание) в имя диапазона добавляются статические параметры модуля и размерности входных тензоров — их собирает `process_layer_params` / `print_tensor`.

Важное ограничение, вытекающее из места регистрации: хуки Python не выполняются при воспроизведении захваченного CUDA graph. Диапазоны NVTX появятся только там, где forward идет в eager-режиме — то есть на prefill без графа, на батчах вне захваченных размеров, либо если графы отключены целиком. Захват графов происходит **после** регистрации хуков, и `cuda_graph_setup.py` явно оговаривает обратный случай для `--forward-hooks`: хуки регистрируются после захвата, чтобы их операции не попали в граф.

На потребление памяти и на выбор алгоритмов флаг не влияет: он не меняет ни один тензор и ни один коллектив.

## Значения и формат

- Флаг без значения; парной `--no-…` формы нет.
- Гранулярность не настраивается: размечаются все модули дерева, отфильтровать «только внимание» нельзя.
- Флаг ничего не пишет на диск. Сами диапазоны видит только внешний профилировщик, запущенный поверх процесса (`nsys profile …`).

## Когда использовать

- Разбор профиля в Nsight Systems: понять, какие слои дают хвост latency, где стоят синхронизации, сколько занимает конкретный блок.
- Сравнение двух конфигураций по форме профиля, а не по агрегированным числам.
- Не оставляйте флаг включенным на постоянно работающем инстансе: сотни Python-хуков на каждый forward — это ощутимый оверхед на CPU-стороне, ровно в том месте, где SGLang и так борется за то, чтобы не отставать от GPU.
- Не ждите разметки внутри захваченного CUDA graph: чтобы увидеть decode послойно, придется отключить графы, а это само по себе меняет профиль.
- Не путайте с `--enable-trace`: там OpenTelemetry-трассировка запросов, совсем другой уровень.

## Влияние на производительность и память

- **VRAM.** Не влияет: буферов не выделяется, тензоры не меняются.
- **CPU и latency.** Основная цена. Каждый forward каждого модуля проходит через Python-хук, собирающий размерности тензоров и формирующий строку имени диапазона. На decode с сотнями модулей это может сделать CPU узким местом и исказить ровно тот профиль, который вы снимаете, — помните об этом при интерпретации.
- **Throughput.** Падает на eager-пути; на graph-replay не меняется, потому что хуки там не вызываются.
- **Время старта.** Плюс обход дерева модулей и регистрация хуков — доли секунды.

## Взаимодействие с другими аргументами

- `--disable-cuda-graph`: единственный способ увидеть послойную разметку decode — иначе decode идет replay'ем и хуки не срабатывают.
- `--enable-profile-cuda-graph`: профилирует сам процесс захвата графа; ортогонален этому флагу.
- `--enable-trace`: OpenTelemetry-трассировка на уровне запросов, а не слоев.
- `--debug-tensor-dump-layers`: другой инструмент послойной диагностики — дамп тензоров на диск вместо аннотаций в профиле.
- `--enable-torch-compile`: скомпилированные графы схлопывают модульную структуру, и часть диапазонов пропадет.

## Типовые проблемы и диагностика

- **Симптом:** в профиле нет ни одного NVTX-диапазона от модели. **Причина №1:** decode идет через CUDA graph replay. **Причина №2:** профилировщик запущен без сбора NVTX. **Решение:** `--disable-cuda-graph` для эксперимента и проверка ключей `nsys`.
- **Симптом:** после включения флага TPOT вырос в разы. **Причина:** оверхед хуков на CPU. **Решение:** это ожидаемо; снимать профиль на короткой сессии и выключать флаг после.
- **Симптом:** разметка есть на prefill, но не на decode. **Причина:** та же — replay графа.
- **Что смотреть:** итоговый дамп `server_args=` при старте — единственное подтверждение, что флаг принят; отдельного сообщения о регистрации хуков движок не печатает.
- **В arriero:** флаг меняется правкой инстанса и рестартом; на живом процессе он отобразится как `config drift` в health summary до перезапуска.

## Примеры

```bash
python -m sglang.launch_server --model-path /models/Qwen3-32B --enable-layerwise-nvtx-marker
```

```bash
python -m sglang.launch_server --model-path /models/Qwen3-32B --enable-layerwise-nvtx-marker --disable-cuda-graph
```
