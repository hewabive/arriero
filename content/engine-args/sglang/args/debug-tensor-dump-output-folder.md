# --debug-tensor-dump-output-folder

## Кратко

Режим отладки численных расхождений: движок регистрирует `register_forward_hook` на каждом листовом модуле модели, копирует все выходы на CPU и после каждого полного прохода пишет их одним `torch.save` в файл `Pass<NNNNN>.pt`. Включение аргумента **меняет конфигурацию сервера**: `__post_init__` принудительно выключает CUDA graph для prefill и decode и ставит `skip_server_warmup=True`. Это не наблюдаемость в эксплуатационном смысле — это инструмент для сравнения тензоров между двумя сборками, и на нагруженном сервере он неприменим ни по скорости, ни по объему.

## Оригинальная справка

```text
The output folder for dumping tensors. In Eagle mode, tensor outputs from draft and target models are stored in separate subdirectories ('draft' and 'target').
```

## Паспорт аргумента

- Флаги: `--debug-tensor-dump-output-folder`
- Группа: `observability`
- Тип значения: str — путь к каталогу
- Допустимые значения: `choices` нет; существование пути не проверяется, подкаталоги создаются рекурсивно при инициализации дампера
- Значение по умолчанию: `null` — дамп выключен
- Эффективное значение: совпадает с заданным, но **само его наличие переписывает три других поля**: `cuda_graph_config.decode.backend = DISABLED`, `cuda_graph_config.prefill.backend = DISABLED`, `skip_server_warmup = True` (в `__post_init__`, с предупреждением в логе)
- Где объявлен: `ServerArgs.debug_tensor_dump_output_folder`, файл — `sglang/python/sglang/srt/server_args.py`
- Статус: обычный, но отладочный; в исходниках рядом с объявлением соседнего поля оставлен комментарий-напоминание о будущем удалении старого кода дампера, а на смену этому пути идет не-интрузивный дампер `sglang/python/sglang/srt/debug_utils/dumper.py`, включаемый не через CLI
- Этап применения: `__post_init__` (переопределение графов и warmup) → загрузка весов в model runner (`maybe_register_debug_tensor_dump_hook`) → каждый forward

## Что меняет в движке

### Регистрация хуков

Сразу после `Load weight end.` вызывается `maybe_register_debug_tensor_dump_hook`. При Eagle-спекуляции к пути добавляется подкаталог `draft` или `target` в зависимости от роли runner'а. Дальше `register_forward_hook_for_model` (`sglang/python/sglang/srt/debug_utils/tensor_dump_forward_hook.py`) рекурсивно обходит `model._modules` и вешает хук на каждый модуль, у которого нет дочерних (плюс на сам верхнеуровневый модуль). Промежуточные контейнеры пропускаются намеренно: выход `self_attn` совпадает с выходом `self_attn.o_proj`, дублировать незачем.

Обход требует, чтобы у модели был модуль с именем `model` (переопределяется переменной окружения `TENSOR_DUMP_TOP_LEVEL_MODULE_NAME`), иначе срабатывает `assert` и процесс падает. Имя контейнера слоев по умолчанию `layers` (`TENSOR_DUMP_LAYERS_MODULE_NAME`).

### Структура файлов

Каталог на процесс: `<folder>/TP{tp_rank}_PP{pp_rank}_Rank{rank}_pid{pid}/`, где `rank = tp_size * pp_rank + tp_rank`. Внутри — `Pass00000.pt`, `Pass00001.pt` и так далее, по файлу на каждый полный проход модели. Формат — обычный `torch.save` словаря, ключи которого повторяют имена модулей (как в `model.safetensors.index.json`), значения — тензоры, уже перенесенные на CPU. Каждый файл сопровождается строкой лога `Dump 00042th pass to …`.

Помимо выходов модулей в словарь попадает вход верхнего уровня: `…forward_batch_info.input_ids`, `…forward_batch_info.seq_lens`, `…forward_batch_info.positions`. Для `PPProxyTensors` раскладываются все передаваемые между стадиями тензоры.

Тонкость, о которой стоит знать при чтении дампов: сброс файла выполняется в хуке верхнеуровневого модуля **до** того, как в накопитель кладется собственный выход этого модуля. Поэтому выход верхнего уровня для прохода N окажется в файле `Pass<N+1>.pt`, а не в `Pass<N>.pt`.

### Почему выключаются графы и warmup

Захваченный CUDA graph при replay не исполняет Python-хуки — дамп в decode просто не сработал бы. Поэтому оба backend'а переводятся в `disabled`, и об этом печатается предупреждение `Cuda graph and server warmup are disabled because of using tensor dump mode`. Warmup отключается, чтобы прогревочный запрос не попал в дамп первым проходом.

## Значения и формат

- Путь к каталогу; пишите абсолютный. Подкаталоги на процесс создаются автоматически.
- Каталог не очищается: при перезапуске появится новый подкаталог (в имени есть `pid`), старые останутся.
- Пустая строка не эквивалентна выключению: проверка идет как `is not None`, так что `--debug-tensor-dump-output-folder ""` включит режим и попытается писать в текущий каталог.
- Специальных значений (`auto`, `-`) нет.
- Отключить у работающего сервера нельзя.

## Когда использовать

- Когда после смены сборки, ядра внимания или квантизации изменился выход модели и нужно найти **первый** слой, где числа разошлись. Для сравнения дампов в checkout'е есть готовые инструменты (`sglang/python/sglang/srt/debug_utils/dump_comparator.py`).
- Только на стенде, с одним коротким запросом и, как правило, с `--debug-tensor-dump-layers`, ограничивающим набор слоев.
- Не использовать для «посмотреть, что происходит» на работающем сервере: с выключенными CUDA graph и покомпонентной синхронизацией пропускная способность падает на порядки, а диск заполняется за минуты.
- Не оставлять включенным в конфигурации инстанса «до следующего раза»: аргумент молча выключает CUDA graph, и падение производительности легко списать на что-то другое.
- Не использовать как замену `--forward-hooks`, если нужна выборочная инструментация: там вы контролируете и модули, и объем.

## Влияние на производительность и память

- **Скорость.** На каждый листовой модуль приходится `tensor.cpu()` — синхронная передача с устройства, то есть барьер после каждого модуля. Плюс полностью выключенные CUDA graph. Замедление на два порядка — нормальный результат.
- **RAM хоста.** Все тензоры одного прохода накапливаются в словаре и только потом сериализуются: пиковое потребление равно размеру одного файла.
- **Диск.** Порядок величины считается так: `число слоев × число листовых модулей в слое × число токенов в проходе × hidden_size × размер элемента`. Для 32-слойной модели с `hidden_size = 4096` в bf16, примерно десятью листовыми модулями на слой и prefill'ом на 512 токенов это около 1.3 ГиБ **на один файл**. В decode проход обрабатывает по одному токену на последовательность, файл выходит порядка мегабайтов — но файл создается **на каждый сгенерированный токен**. Ответ в сто токенов даст сто файлов. У MoE-моделей число листовых модулей в слое кратно числу экспертов, и оценку надо умножать соответственно.
- VRAM: сам дамп не занимает, но отключение CUDA graph освобождает память, которая раньше уходила на графы, — эффективное значение `--mem-fraction-static`, если оно подбиралось автоматически, будет другим.
- Время старта: обход модулей мгновенен; warmup пропускается, так что старт даже быстрее обычного.

## Взаимодействие с другими аргументами

- `--debug-tensor-dump-layers`: единственный способ уменьшить объем — ограничить набор слоев. Настоятельно рекомендуется задавать вместе.
- `--debug-tensor-dump-input-file`: в этом checkout'е сочетание нерабочее. Файл входа читается только в прогревочном запросе, а warmup этот аргумент как раз и отключает; сразу после старта процесс убивает сам себя. Подробности — в документе того аргумента.
- `--cuda-graph-config` и `--cuda-graph-*`: любые ваши настройки графов переопределяются на `disabled`.
- `--skip-server-warmup`: выставляется принудительно в `True`.
- `--speculative-algorithm` (Eagle): дампы draft- и target-моделей раскладываются по подкаталогам `draft` и `target`.
- `--tp-size` / `--pp-size`: каждый ранг пишет в свой подкаталог, объем умножается на число рангов.
- `--msprobe-dump-config`: альтернативный инструментальный путь, который так же принудительно выключает CUDA graph и warmup.
- `--forward-hooks`: тот же механизм PyTorch, но с вашей логикой и без переопределения настроек графов.

## Типовые проблемы и диагностика

- `AssertionError: model should have a module named model` при загрузке весов — у архитектуры другой верхнеуровневый модуль. Задайте `TENSOR_DUMP_TOP_LEVEL_MODULE_NAME` в переменных окружения.
- Каталог создан, файлов нет — не было ни одного forward. Проверьте, что запросы вообще доходят: warmup отключен, поэтому первый проход случится только на реальном запросе.
- Диск заполнился за считаные минуты — ожидаемое поведение; ограничивайте `--debug-tensor-dump-layers` и шлите один короткий запрос.
- `Cuda graph and server warmup are disabled because of using tensor dump mode` в логе при старте — подтверждение, что режим включился, и одновременно объяснение просевшей производительности.
- В файле `Pass00000.pt` нет ключа верхнеуровневого модуля — см. выше про сдвиг на один проход.
- Тензоры одного слоя отсутствуют, хотя слой в списке — модуль не листовой; хуки вешаются только на модули без дочерних.
- **В arriero:** запуск инстанса с этим аргументом гарантированно испортит любые измерения. Оценка памяти и авто-ассессмент (`docs/MEMORY_ESTIMATION.md`) снимут фактическое потребление без CUDA graph и запишут его как эталон для конфигурации, у которой графы включены; фингерпринт при этом от аргументов не зависит. Каталог дампа держите вне `data/` и вне `data/config/` (`docs/CONFIG_GIT.md`) — это неограниченный по объему машинный мусор.

## Примеры

```bash
python -m sglang.launch_server --model-path /models/Qwen3-30B-A3B --debug-tensor-dump-output-folder /var/tmp/sglang-tensors --debug-tensor-dump-layers 0 1
```

```bash
python -m sglang.launch_server --model-path /models/Qwen3-30B-A3B --tp-size 2 --debug-tensor-dump-output-folder /var/tmp/sglang-tensors --debug-tensor-dump-layers 0 --max-running-requests 1
```
