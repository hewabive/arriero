# --trust-mm-content-hashes

## Кратко

Кеш препроцессинга (`--mm-preprocess-cache-size-mb`) адресуется SHA-256-хешем содержимого медиа — но чтобы посчитать хеш, медиа надо сначала скачать и прочитать, а это и есть самая дорогая часть. Клиент может прислать хеш сам (поле `content_hash` у `image_url` в OpenAI-совместимом API, список `mm_content_hashes` в нативном `/generate`). По умолчанию такой хеш — только **утверждение для проверки**: сервер все равно читает байты и падает с ошибкой при несовпадении. `--trust-mm-content-hashes` переводит хеш в ранг **идентификатора**: если артефакт с таким ключом уже в кеше, медиа не скачивается и не читается вовсе. Включать можно только тогда, когда вызывающая сторона гарантирует, что хеш действительно однозначно именует неизменяемые байты — сервер принимает эту гарантию на веру.

## Оригинальная справка

```text
Trust caller-provided multimodal SHA-256 content hashes. This can skip reading media on a hot metadata-cache hit; only enable it when the caller guarantees that hashes identify immutable media bytes.
```

## Паспорт аргумента

- Флаги: `--trust-mm-content-hashes`
- Группа: `mm`
- Тип значения: bool, `action="store_true"`
- Значение по умолчанию: `false` — хеши проверяются, но не заменяют чтение
- Эффективное значение: не переписывается; читается в конструкторе `BaseMultimodalProcessor`
- Где объявлен: `ServerArgs.trust_mm_content_hashes`, файл — `sglang/python/sglang/srt/server_args.py`
- Статус: обычный
- Этап применения: конструирование мультимодального процессора в tokenizer-процессе → путь разрешения артефактов каждого запроса с медиа

## Что меняет в движке

Разрешение артефактов (`sglang/python/sglang/srt/multimodal/media_artifacts/base.py`) идет в два прохода:

1. **Быстрый путь — только при включенном флаге.** Для каждого медиа с присланным хешем строится ключ артефакта прямо из этого хеша (плюс отпечаток процессора) и выполняется поиск в кеше. Попадание — артефакт взят, источник медиа (URL, base64, файл) не открывался. Это и есть «hot metadata-cache hit» из справки: сервер узнал размер, токенную сетку и фичу медиа, не видя самих байтов.
2. **Обычный путь — для всех остальных.** Медиа читается, считается его реальный дайджест, и если клиент прислал хеш, он сверяется: несовпадение — `ValueError: content hash mismatch for media_data[i]: expected …, got …`, запрос отклонен. Эта сверка выполняется **и при включенном флаге** — доверие распространяется только на попадание в кеш, промах всегда честный.

Формат хеша жесткий: строка `sha256:<64 hex>`; все прочее отвергает валидатор `parse_content_hash` еще на разборе запроса. Число хешей обязано совпадать с числом медиа-элементов.

В логе включение видно в строке кеша препроцессинга: `…; caller content hashes are trusted.` (против `verified` по умолчанию).

## Значения и формат

- Флаг без значения; парной `--no-*` формы нет.
- Без кеша препроцессинга (бюджет 0 или дефолтный 0 у процессора модели) быстрый путь не срабатывает никогда — кеш пуст; флаг осмыслен только в паре с `--mm-preprocess-cache-size-mb`.
- Хеш считается от **байтов** источника: перекодированный или ужатый клиентом файл — другой хеш, попадания не будет.

## Когда использовать

- Свой доверенный клиент поверх стабильного хранилища (CAS, S3 с версионированием), который считает SHA-256 честно: повторные обращения к тем же медиа перестают трогать сеть и диск, TTFT падает на всю стоимость скачивания и препроцессинга.
- Не включать на сервере, куда ходят посторонние клиенты: злоумышленник, угадавший или подсмотревший хеш чужого медиа, получит его артефакт (размер, сетку токенов, фичу) без владения самим файлом, а мусорный хеш с последующим успешным попаданием другого запроса склеит чужие артефакты. Доверие здесь — свойство всего периметра, а не одного клиента.
- Не включать «на всякий случай»: без кеша и без клиентских хешей флаг ничего не ускоряет.

## Влияние на производительность и память

- Latency: горячее попадание убирает из запроса скачивание, декодирование и препроцессинг медиа — для URL-картинок это обычно сотни миллисекунд на элемент.
- Сеть и IO-потоки: при попадании исходящих запросов нет вовсе.
- RAM/VRAM: сам флаг ничего не выделяет; память расходует кеш, размер которого задан `--mm-preprocess-cache-size-mb`.
- При промахе поведение и стоимость идентичны выключенному флагу.

## Взаимодействие с другими аргументами

- `--mm-preprocess-cache-size-mb`: обязательный партнер — без включенного кеша быстрый путь мертв.
- `--allowed-media-domains` / `--media-url-max-file-size-mb`: при горячем попадании проверка домена и лимит размера не выполняются — скачивания нет; при промахе действуют как обычно.
- `--tokenizer-worker-num`: кеши воркеров независимы — попадание по хешу случается только в воркере, уже видевшем это медиа.
- `--enable-mm-global-cache`: кеш эмбеддингов энкодера — отдельный слой; «безфичевый» артефакт из быстрого пути полезен, только когда эмбеддинг уже есть там.

## Типовые проблемы и диагностика

- `content_hash must use the form 'sha256:<64 hex digits>'` — хеш в другом формате (голый hex, md5, верхний регистр допустим, но префикс обязателен).
- `ValueError: mm_content_hashes has N entries for M image items` — список хешей не совпал по длине со списком медиа.
- `ValueError: content hash mismatch for media_data[0]: expected sha256:…, got sha256:…` — клиент прислал хеш не тех байтов; типовая причина — хеш от исходника, а отправка перекодированной версии.
- Флаг включен, а ускорения нет — проверьте строку `…; caller content hashes are trusted.` в логе (иначе кеш не включился), что клиент реально шлет `content_hash`, и что медиа уже попадало в этот же tokenizer-воркер.
- Состояние поля видно в дампе `server_args=` (`trust_mm_content_hashes=True`).

## Примеры

```bash
python -m sglang.launch_server --model-path /models/Qwen3-VL-8B-Instruct --mm-preprocess-cache-size-mb 512 --trust-mm-content-hashes
```

Запрос клиента с хешем (фрагмент тела chat completions):

```json
{"type": "image_url", "image_url": {"url": "https://cdn.example.com/doc.png", "content_hash": "sha256:9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08"}}
```
