# --eplb-rebalance-layers-per-chunk

## Кратко

Аргумент режет одну перебалансировку на несколько forward-проходов. Список MoE-слоев модели разбивается на куски по N штук; после каждого куска (если кусков больше одного) генератор `EPLBManager` делает `yield`, и сервер успевает обслужить следующий батч, прежде чем перенести следующую порцию весов. Это единственная ручка, которая превращает одну длинную паузу в цепочку коротких.

## Оригинальная справка

```text
Number of layers to rebalance per forward pass.
```

## Паспорт аргумента

- Флаги: `--eplb-rebalance-layers-per-chunk`
- Группа: `exec.moe`
- Тип значения: int (число MoE-слоев на порцию)
- Допустимые значения: `choices` нет, проверок в коде нет
- Значение по умолчанию: `null` — дробления нет
- Эффективное значение: не переопределяется; внутри менеджера `null` (и любое ложное значение, включая `0`) превращается в `1000000`, то есть «все слои одним куском»
- Где объявлен: `ServerArgs.eplb_rebalance_layers_per_chunk`, файл — `sglang/python/sglang/srt/server_args.py`
- Статус: обычный
- Этап применения: конструктор `EPLBManager` → каждая перебалансировка

## Что меняет в движке

В `EPLBManager._compute_update_layer_ids_chunks` берется отсортированный список ключей `model.routed_experts_weights_of_layer` (то есть только слои с маршрутизируемыми экспертами) и режется на куски по `chunk_size = eplb_rebalance_layers_per_chunk or 1000000`. Дальше `rebalance()` идет по кускам:

- если кусков больше одного, перед каждым делается `yield` — управление возвращается в `on_forward_pass_end`, и следующий кусок начнется только на следующем проходе;
- на каждом куске вызывается `update_expert_location_with_recovery`, который переставляет веса через `ExpertLocationUpdater` и при необходимости дочитывает недостающих экспертов с диска или из DRAM-бэкапа;
- при `--ep-dispatch-algorithm lp` после всех кусков пересобираются LP-решатели.

Второй, менее очевидный эффект: `enable_timing = self._rebalance_layers_per_chunk is None`. Пока аргумент не задан, вокруг перебалансировки стоят `synchronize()` и замер времени, и в лог уходит `[EPLBManager] rebalance end time=<N>s`. Как только вы включаете дробление, замер выключается и строка становится просто `[EPLBManager] rebalance end`. То есть измерять стоимость перебалансировки надо до включения дробления, а не после.

Важно, что новая карта экспертов вычисляется целиком до первого куска: пока переносятся не все слои, часть модели уже работает по новой раскладке, а часть — по старой. Это штатное состояние, ради него в `ExpertLocationUpdater` и передается явный список `update_layer_ids`.

## Значения и формат

- Не задан — все слои за один проход. Максимальная пауза, зато с измеренной длительностью в логе.
- `1` — предельное дробление: один MoE-слой за проход. Полная перебалансировка растягивается на столько проходов, сколько у модели MoE-слоев (для DeepSeek-V3 это ~58).
- `4`–`8` — разумный компромисс для крупных моделей: пауза в разы короче, а весь цикл заканчивается за десяток проходов.
- `0` — из-за `or` ведет себя как «не задан», но при этом отключает замер времени; смысла нет.
- Отрицательное значение — `range(0, len, -N)` пуст, кусков не будет вовсе, и перебалансировка молча не обновит ни одного слоя. Не используйте.
- Значение больше числа MoE-слоев эквивалентно «не задан», но также глушит замер времени.

## Когда использовать

- Инстанс обслуживает интерактивную нагрузку, и разовая пауза в перебалансировке видна в p99: включайте дробление и подбирайте N по остаточному всплеску.
- Модель крупная и весов экспертов много: без дробления первая же перебалансировка даст заметный провал throughput.
- Не включайте, пока измеряете стоимость перебалансировки: без дробления в логе есть готовая цифра `time=<N>s`.
- Не ставьте `1` бездумно: между кусками модель работает со смешанной раскладкой, и общее время цикла растет пропорционально числу кусков.

## Влияние на производительность и память

- **Latency.** Прямая цель аргумента: пауза делится примерно на `ceil(num_moe_layers / N)` частей.
- **Общее время перебалансировки.** Растет: между кусками выполняется полноценный forward-проход, плюс на elastic EP после каждого куска ставится `dist.barrier()`.
- **VRAM.** Пиковый расход временных буферов переноса ниже, потому что одновременно переставляются веса меньшего числа слоев.
- **Диагностика.** Замер `time=` пропадает — это осознанный размен, а не баг.

## Взаимодействие с другими аргументами

- `--enable-eplb`: без него аргумент не читается.
- `--eplb-rebalance-num-iterations`: период между перебалансировками; дробление растягивает саму перебалансировку внутри периода.
- `--eplb-min-rebalancing-utilization-threshold`: если срабатывание пропущено по порогу, дробление вообще не начинается.
- `--ep-num-redundant-experts`: чем больше реплик, тем больше весов переезжает и тем сильнее нужен размен на дробление.
- `--ep-dispatch-algorithm` со значением `lp`: LP-решатели пересобираются после последнего куска, а не после каждого.

## Типовые проблемы и диагностика

- Периодические провалы latency с интервалом `--eplb-rebalance-num-iterations` — это перебалансировка; включите дробление.
- После включения дробления пропала строка `time=` — ожидаемо, замер отключается вместе с `null`.
- Раскладка не меняется, хотя `[EPLBManager] rebalance start` есть, — проверьте, не задано ли отрицательное значение: тогда список кусков пуст.
- Понять, какие слои обновились в данном срабатывании, помогает `SGLANG_LOG_EXPERT_LOCATION_METADATA=1` — печатаются layout до, целевой layout и дифф именно по обновляемым слоям.

## Примеры

```bash
python -m sglang.launch_server --model-path deepseek-ai/DeepSeek-V3 --tp-size 8 --ep-size 8 --moe-a2a-backend deepep --deepep-mode normal --enable-eplb --eplb-rebalance-layers-per-chunk 8
```

```bash
python -m sglang.launch_server --model-path deepseek-ai/DeepSeek-V3 --tp-size 8 --ep-size 8 --moe-a2a-backend deepep --deepep-mode normal --enable-eplb --ep-num-redundant-experts 32 --eplb-rebalance-num-iterations 2000 --eplb-rebalance-layers-per-chunk 1
```
