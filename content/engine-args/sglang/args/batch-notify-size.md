# --batch-notify-size

## Кратко

Планировщик присылает в `TokenizerManager` один объект на весь батч — с выводом сразу для десятков запросов. Разбирая его, менеджер должен разбудить корутину каждого HTTP-обработчика. `--batch-notify-size` определяет, через сколько таких пробуждений делается `await asyncio.sleep(0)` — то есть насколько крупными пачками event loop получает работу.

Это чисто внутренняя оптимизация Python-процесса токенизатора: ни один байт ответа от нее не меняется.

## Оригинальная справка

```text
Number of streaming notifications to batch before yielding to the event loop. Reduces asyncio wakeup overhead under high concurrency.
```

## Паспорт аргумента

- Флаги: `--batch-notify-size`
- Группа: `serving`
- Тип значения: целое, единица измерения — запросы
- Допустимые значения: `choices` нет; осмысленный диапазон — целые ≥ 1
- Значение по умолчанию: `16`
- Эффективное значение: `__post_init__` не переопределяет и не валидирует
- Где объявлен: `ServerArgs.batch_notify_size`, файл — `sglang/python/sglang/srt/server_args.py`
- Статус: обычный
- Этап применения: `TokenizerManager._handle_batch_output`, то есть на каждом выходном батче планировщика

## Что меняет в движке

`sglang/python/sglang/srt/managers/tokenizer_manager.py`:

```python
pending_notify: dict[str, ReqState] = {}
batch_notify_size = self.server_args.batch_notify_size
for i, rid in enumerate(recv_obj.rids):
    ...
    if out_dict is not None:
        state.out_list.append(out_dict)
        pending_notify[rid] = state
        if len(pending_notify) >= batch_notify_size:
            for s in pending_notify.values():
                s.event.set()
            pending_notify = {}
            await asyncio.sleep(0)
...
for s in pending_notify.values():
    s.event.set()
```

Ключевая деталь — `await asyncio.sleep(0)`. Это единственная точка, где цикл разбора батча отдает управление, позволяя разбуженным корутинам `_wait_one_response` реально отправить свои SSE-кадры. Значит:

- **маленькое значение** — частые уступки event loop: разбуженный клиент получает свой кадр раньше, но разбор батча прерывается чаще и общий CPU-оверхед выше;
- **большое значение** (≥ числа одновременных запросов) — промежуточных уступок нет вовсе, все `event.set()` выполняются в конце цикла, разбор батча идет одним куском.

Обратите внимание: `event.set()` внутри пачки выполняется **до** `sleep(0)`, поэтому «отложенных» пробуждений не остается — финальный цикл после `for` добивает только незаполненный остаток.

## Значения и формат

- Целое число запросов; `16` по умолчанию.
- `1` — уступка event loop после каждого разбуженного запроса. Минимальная задержка доставки, максимальный оверхед.
- `0` и отрицательные argparse примет; условие `len(pending_notify) >= batch_notify_size` станет истинным сразу после первой вставки, то есть поведение выродится в `1`. Отдельного смысла у этих значений нет, ошибок они не вызывают.
- Значение больше фактического числа одновременных запросов эквивалентно «никогда не уступать в середине батча».
- Значения «отключить» нет.

## Когда использовать

- Сотни одновременных стримов, процесс токенизатора упирается в CPU (видно по `top`: один Python-процесс держит ядро), а GPU при этом недогружен — поднимайте до `32`–`64`.
- Нагрузка «много коротких запросов» с высоким QPS: там доля времени на пробуждения максимальна.
- **Не трогайте** при единицах одновременных запросов: пачка всё равно никогда не заполняется, и значение не играет роли.
- **Не используйте** для снижения TTFT — эффект обратный: увеличение размера пачки может только отложить доставку первого кадра.

## Влияние на производительность и память

- VRAM, KV-пул, скорость генерации — не затрагиваются.
- CPU процесса токенизатора: уменьшает число переключений корутин примерно в `batch_notify_size` раз на батч.
- Latency доставки: в худшем случае кадр запроса ждет, пока разберутся остальные запросы пачки. При батче в 200 запросов и `batch_notify_size 64` это до трех «квантов» разбора — доли миллисекунды, но под нагрузкой они складываются.
- Память: `pending_notify` — словарь не больше `batch_notify_size` элементов, вклад пренебрежимо мал.

## Взаимодействие с другими аргументами

- `--stream-interval`: уменьшает **количество** выходных сообщений; `--batch-notify-size` уменьшает число переключений event loop при разборе того же сообщения. Под высокой конкурентностью их обычно поднимают вместе.
- `--incremental-streaming-output`: в инкрементальном режиме несколько накопившихся порций склеиваются в `_coalesce_streaming_chunks`, поэтому редкие пробуждения там безопаснее для целостности текста.
- `--max-running-requests`: задает потолок числа запросов в одном выходном батче, то есть и потолок полезного значения этого аргумента.
- `--tokenizer-worker-num`: при нескольких токенизатор-воркерах нагрузка на один event loop падает, и потребность поднимать значение уменьшается.

## Типовые проблемы и диагностика

- **Ожидали ускорения генерации — не получили.** Аргумент не влияет ни на GPU, ни на планировщик; он снимает только оверхед доставки.
- **Первый кадр стал приходить позже** — слишком большое значение при большом батче; вернитесь к `16`.
- Что подтверждает эффект: снижение CPU-времени процесса токенизатора при неизменном throughput. Отдельной строки в логе у этого аргумента нет — только значение в дампе `server_args=` при старте.

## Примеры

```bash
python -m sglang.launch_server --model-path /models/Qwen3-30B-A3B --batch-notify-size 32 --port 30000
```

```bash

```
