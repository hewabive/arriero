# --forward-pass-metrics-worker-id

## Кратко

Скрытый аргумент (объявлен с `argparse.SUPPRESS`, в `--help` не показывается). Единственное назначение — проставить строку в поле `worker_id` структуры `ForwardPassMetrics`, чтобы внешний планировщик мог различить, от какого воркера пришло сообщение. Никакой семантики внутри SGLang у значения нет: оно нигде не проверяется, ни с чем не сравнивается и ни на что не влияет, кроме содержимого публикуемых сообщений. Работает только вместе с `--enable-forward-pass-metrics`; механизм целиком описан там.

## Паспорт аргумента

- Флаги: `--forward-pass-metrics-worker-id`
- Группа: `observability`
- Тип значения: str
- Допустимые значения: `choices` нет, ограничений нет — любая строка
- Значение по умолчанию: `""` (пустая строка, не `null`)
- Эффективное значение: совпадает с заданным; никакой `_handle_*` его не переписывает и подстановки по умолчанию нет — при незаданном аргументе в сообщениях будет пустое `worker_id`
- Где объявлен: `ServerArgs.forward_pass_metrics_worker_id`, файл — `sglang/python/sglang/srt/server_args.py`
- Статус: скрытый (`argparse.SUPPRESS`); контракт может измениться без предупреждения
- Этап применения: конструктор `SchedulerMetricsReporter` (`_init_fpm`), только в процессе с `attn_tp_rank == 0` на последней PP-стадии

## Что меняет в движке

Значение копируется в `scheduler._fpm_worker_id`, передается в конструктор `_FpmPublisherThread` и оттуда попадает в каждое публикуемое сообщение:

```python
fpm = ForwardPassMetrics(
    worker_id=self.scheduler._fpm_worker_id,
    dp_rank=self.scheduler._fpm_dp_rank,
    wall_time=wall_time,
    scheduled_requests=…,
    queued_requests=…,
)
```

То же значение подставляется в heartbeat-сообщения, которые публикатор шлет раз в секунду при простое. `dp_rank` рядом заполняется автоматически и отдельного аргумента не требует.

Внутри SGLang значение больше нигде не используется: ни в логах (кроме общей строки дампа `server_args=`), ни в маршрутизации, ни в Prometheus-метках. Это чистый пассивный ярлык для потребителя.

## Значения и формат

- Произвольная строка. В shell значение с пробелами надо взять в кавычки.
- Пустая строка — значение по умолчанию и валидный вариант; ее и увидит потребитель, если аргумент не задать.
- Специальных значений (`auto`, `none`, `0`) нет.
- Длина не ограничена, но строка уходит в **каждом** сообщении — то есть на каждой итерации scheduler'а; держите ее короткой.
- Изменить у работающего сервера нельзя.
- Значение полностью игнорируется без `--enable-forward-pass-metrics`.

## Когда использовать

- Когда один планировщик подписан на несколько инстансов SGLang: без `worker_id` сообщения от разных серверов различаются только адресом сокета, что неудобно и теряется при агрегации.
- Когда идентификатор должен совпадать с внешним реестром воркеров — например, с именем инстанса arriero, чтобы решения планировщика можно было сопоставить с трейсами прокси.
- Не использовать для различения DP-рангов внутри одного сервера: для этого уже есть поле `dp_rank`, оно заполняется само.
- Не задавать, если FPM не включены: аргумент скрытый и в `--help` установленной сборки может отсутствовать.

## Влияние на производительность и память

- На производительность влияет только через размер сообщения: строка сериализуется msgpack'ом в каждое сообщение, то есть на каждой итерации. Разница между пустой строкой и коротким именем — единицы байт.
- На память не влияет.
- На время старта не влияет.

## Взаимодействие с другими аргументами

- `--enable-forward-pass-metrics`: без него значение не читается.
- `--forward-pass-metrics-ipc-name`: вторая половина адресации. Адрес сокета отвечает на вопрос «куда», `worker_id` — «от кого».
- `--dp-size`: `dp_rank` заполняется отдельным полем и в `worker_id` не входит; при `dp_size > 1` все ранги одного сервера публикуют одинаковый `worker_id`.
- `--served-model-name`: разумный источник значения, если у вас один инстанс на модель; но в сообщение имя модели не попадает автоматически.

## Типовые проблемы и диагностика

- У потребителя `worker_id` пустой — аргумент не задан (значение по умолчанию именно пустая строка, а не `null`).
- Значение задано, но сообщений нет вообще — проблема не в этом аргументе; ищите строку `FPM: ZMQ PUB bound on …` в логе scheduler'а и проверяйте `--enable-forward-pass-metrics`.
- `unrecognized arguments: --forward-pass-metrics-worker-id` — установленная сборка старше checkout'а. Аргумент скрытый, поэтому в `--help` его нет и проверить наличие можно только пробным запуском.
- Подтвердить, что значение принято, можно по итоговому дампу `server_args=` в логе при старте: там оно печатается наравне с остальными полями.
- **В arriero:** удобный источник значения — имя инстанса (оно же рантайм-ключ везде: `process_runs.instanceId`, `instance:<name>` в прокси). Сам менеджер это поле не читает — FPM-канал он не использует.

## Примеры

```bash
python -m sglang.launch_server --model-path /models/DeepSeek-V3 --enable-forward-pass-metrics --forward-pass-metrics-worker-id kt-dsv3-a
```

```bash
python -m sglang.launch_server --model-path /models/DeepSeek-V3 --enable-forward-pass-metrics --forward-pass-metrics-ipc-name ipc:///run/user/1000/sglang-fpm --forward-pass-metrics-worker-id kt-dsv3-a
```
