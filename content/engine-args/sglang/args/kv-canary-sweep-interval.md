# --kv-canary-sweep-interval

## Кратко

Обычная проверка KV-канарейки смотрит только на слоты, затронутые текущим forward (голова и хвост записанного диапазона). Полный обход (sweep) проверяет **все** слоты, которые сейчас удерживает дерево префиксов, — то есть ловит порчу давно закешированных блоков, к которым в этом шаге никто не обращался.

Аргумент задает период такого обхода в шагах forward. Значение `0` (по умолчанию) отключает его полностью. Любое положительное значение требует включенной канарейки: `--kv-canary-sweep-interval N` при `--kv-canary none` дает `ValueError: --kv-canary-sweep-interval requires --kv-canary in {log, raise}` еще на разборе аргументов.

## Оригинальная справка

```text
Every N forward steps, run a full-pool sweep.
```

## Паспорт аргумента

- Флаги: `--kv-canary-sweep-interval`
- Группа: `observability`
- Тип значения: int (шаги forward)
- Допустимые значения: `choices` нет. Осмысленный диапазон — `0` (выключено) и положительные значения; отрицательные argparse принимает, и они приводят к обходу на каждом шаге (см. «Значения и формат»)
- Значение по умолчанию: `0`
- Эффективное значение: попадает в `CanaryConfig.sweep_interval` без преобразований; при `--kv-canary none` канарейка не устанавливается вовсе и значение не читается
- Где объявлен: `ServerArgs.kv_canary_sweep_interval`, файл — `sglang/python/sglang/srt/server_args.py`
- Статус: обычный аргумент узкоспециального диагностического механизма
- Этап применения: `__post_init__` (проверка связки с `--kv-canary`) → `SweepOrchestrator` внутри менеджера канарейки, на каждом forward

## Что меняет в движке

`SweepOrchestrator.maybe_run_sweep` (`sglang/python/sglang/srt/kv_canary/runner/sweep.py`) на каждом шаге:

1. выходит немедленно, если `sweep_interval == 0`;
2. выходит, если с прошлого обхода прошло меньше `sweep_interval` шагов (первый вызов обходит всегда: начальное значение счетчика — `-1`);
3. выходит, если дерево префиксов еще не привязано к оркестратору;
4. для каждой группы буферов канарейки строит план проверки по всем слотам, удерживаемым радиксным деревом (`build_verify_plan_radix_sweep`), с учетом окна SWA для SWA-групп, и запускает ядра проверки;
5. печатает через `logger.info` строку `[canary] sweep succeeded <N> times (last_step=<M>)`.

Пересечение с обычной пофорвардной проверкой авторы считают безвредной избыточностью — это прямо сказано в комментарии к полю `sweep_interval` в `CanaryConfig`.

Есть и вторая роль значения: «health checker» канарейки следит, что ожидаемые ядра действительно запускались. При `sweep_interval <= 0` он исключает теги обхода из набора ожидаемых, иначе — требует, чтобы счетчики этих ядер росли, и бросает `RuntimeError: kv-canary: kernel_run_counter did not increase …`, если обход почему-то не исполняется.

## Значения и формат

- `0` — обход выключен, остается только пофорвардная проверка.
- Положительное `N` — обход раз в `N` шагов forward. Ориентир: при decode-нагрузке шаг forward это один токен на батч, то есть `N = 200` дает обход примерно раз в две сотни токенов.
- Отрицательное значение: `ValueError` не срабатывает (проверка в `__post_init__` смотрит только `> 0`), а сравнение `outer_step - last_sweep_step < sweep_interval` при отрицательном пороге всегда ложно — обход выполняется **на каждом шаге**. Это самый дорогой из возможных режимов и почти наверняка не то, чего вы хотели.
- Единица измерения — шаги forward, а не запросы, не токены на запрос и не секунды.

## Когда использовать

- Подозрение на порчу давно лежащих в кеше блоков: симптом — ответ портится не в первом запросе, а после того, как префикс был переиспользован через какое-то время. Пофорвардная проверка такие случаи не видит, обход — видит.
- Прогон на стенде под `--kv-canary raise --kv-canary-sweep-interval N`: это заявленный «CI lane».
- Не включайте на рабочем сервере ради подстраховки — стоимость линейна по объему закешированных токенов и платится регулярно.
- Бессмысленно при `--disable-radix-cache`: обход строится именно по слотам, удерживаемым деревом префиксов; без дерева проверять нечего.

## Влияние на производительность и память

- Дополнительной VRAM не требует: буферы уже выделены самим `--kv-canary`.
- Стоимость одного обхода пропорциональна числу слотов, удерживаемых деревом, то есть фактическому объему кеша, а не размеру батча. На большом заполненном пуле это заметная пауза внутри шага forward.
- Средние накладные расходы = стоимость обхода / `N`. Уменьшая `N`, вы линейно увеличиваете постоянный налог на throughput.
- `--kv-canary-real-data all` умножает стоимость обхода на объем читаемого содержимого слота.
- Каждый обход добавляет строку INFO в лог; при малом `N` это заметный поток строк.

## Взаимодействие с другими аргументами

- `--kv-canary`: обязательное условие; `log` или `raise`.
- `--kv-canary-real-data`: определяет, сверяется ли при обходе реальное содержимое KV или только метаданные канарейки.
- `--disable-radix-cache`: обход теряет смысл — дерева, по которому строится план, нет.
- `--enable-hierarchical-cache`: проверяются слоты, удерживаемые деревом на устройстве; выгруженные на хост уровни обходом не покрываются.
- `--page-size`, `--attention-backend`: через класс KV-пула определяют, какие группы буферов существуют и сколько планов строится за обход.

## Типовые проблемы и диагностика

- **Симптом:** `ValueError: --kv-canary-sweep-interval requires --kv-canary in {log, raise}` при старте. **Причина:** задан период без включенной канарейки. **Лечение:** добавить `--kv-canary log`.
- **Симптом:** заметная просадка throughput после включения. **Причина:** слишком маленький `N` относительно объема кеша. **Лечение:** увеличить `N` на порядок и посмотреть, сохраняется ли обнаружение.
- **Симптом:** строк `[canary] sweep succeeded …` в логе нет. **Причина:** обход не выполняется — либо `sweep_interval == 0`, либо дерево префиксов не привязано (например, `--disable-radix-cache`), либо уровень логирования выше `info`.
- **Симптом:** `RuntimeError: kv-canary: kernel_run_counter did not increase …` с тегами обхода. **Причина:** обход объявлен ожидаемым, но ядра не запускались. **Лечение:** это дефект конфигурации, сообщайте вместе с полной строкой запуска.
- **Проверка принятого значения:** строка `install_canary: … config=CanaryConfig(mode=…, sweep_interval=…)` при старте.

## В arriero

Отдельного смысла для менеджера у аргумента нет: он не меняет ни здоровье инстанса, ни учет памяти, ни поведение прокси. Учитывайте только два практических следствия.

Первое: строки `[canary] sweep succeeded …` идут на уровне INFO в лог инстанса и при малом `N` вытесняют из последних 1000 строк, которые читает разбор лога (`apps/api/src/process/log-summary.ts`), действительно полезные сообщения движка.

Второе: обход выполняется внутри шага forward, то есть удлиняет его. Планировщик прокси arriero арбитрирует конкуренцию по времени удержания аренды домена (`docs/RESOURCE_MANAGEMENT.md`, arriero), и систематически более долгий forward выражается в росте задержек всех конкурирующих запросов, а не только тех, что попали на шаг с обходом.

## Примеры

```bash
python -m sglang.launch_server --model-path /models/Qwen3-30B-A3B --host 127.0.0.1 --port 30000 --kv-canary log --kv-canary-sweep-interval 500
```

```bash
python -m sglang.launch_server --model-path /models/Qwen3-30B-A3B --host 127.0.0.1 --port 30000 --kv-canary raise --kv-canary-sweep-interval 100 --kv-canary-real-data partial
```
