# --disable-tokenizer-batch-decode

## Кратко

На каждом шаге вывода детокенизатор превращает token ids всех активных запросов в текст. По умолчанию он делает это группами: запросы с одинаковой парой `(skip_special_tokens, spaces_between_special_tokens)` собираются вместе и декодируются одним вызовом `batch_decode`. `--disable-tokenizer-batch-decode` отключает группировку и переводит декодирование на построчный `tokenizer.decode`.

Аргумент — обходной путь, а не настройка производительности. В комментарии кода прямо написано: «Do not use batch decode to prevent some detokenization edge cases (e.g., gpt-oss)».

## Оригинальная справка

```text
Disable batch decoding when decoding multiple completions.
```

## Паспорт аргумента

- Флаги: `--disable-tokenizer-batch-decode`
- Группа: `serving`
- Тип значения: bool; поле объявлено как `bool`, argparse получает `action="store_true"`, парного `--no-*` нет
- Допустимые значения: флаг без значения
- Значение по умолчанию: `False` — групповое декодирование включено
- Эффективное значение: совпадает с заданным. Ни один `_handle_*` его не переписывает — в отличие от соседних аргументов токенизаторного батчинга, которые сбрасываются при `--skip-tokenizer-init`
- Где объявлен: `ServerArgs.disable_tokenizer_batch_decode`, файл — `sglang/python/sglang/srt/server_args.py`
- Статус: обычный
- Этап применения: инициализация процесса детокенизатора (`DetokenizerManager.init_running_status` копирует значение в `self.disable_tokenizer_batch_decode`) → каждый шаг обработки `BatchTokenIDOutput`

## Что меняет в движке

В `DetokenizerManager.handle_batch_token_id_out` (`managers/detokenizer_manager.py`) на каждом шаге собираются два набора последовательностей: `surr_ids` (контекст-суррогат до `read_offset`) и `read_ids` (то, что нужно отдать клиенту). Дальше — развилка:

```python
if not self.disable_tokenizer_batch_decode:
    surr_texts = self._grouped_batch_decode(surr_ids, skip, spaces)
    read_texts = self._grouped_batch_decode(read_ids, skip, spaces)
else:
    surr_texts = [self.tokenizer.decode(surr, skip_special_tokens=skip,
                                        spaces_between_special_tokens=space)
                  for surr, skip, space in zip(...)]
    read_texts = [...]
```

`_grouped_batch_decode` дополнительно отфильтровывает пустые последовательности перед вызовом (комментарий в коде объясняет: пустые спаны декодируются в `""`, но каждый ряд все равно стоит накладных расходов, и «под высококонкурентным стримингом это накапливается»), декодирует остальные и раскладывает результат обратно.

Итоговый текст получается инкрементально как разность `read_texts[i]` и `surr_texts[i]`, поэтому оба набора обязаны декодироваться одинаковым способом — что и обеспечивается общим флагом.

Рядом живет второй известный краевой случай, обрабатываемый отдельно: `trim_matched_stop` не срезает последний токен, если это `200012` и включен `--tool-call-parser gpt-oss`. Это независимая заплатка, но она же указывает на семейство моделей, где детокенизация ведет себя нестандартно.

## Значения и формат

- Флаг без значения. Указан — построчное декодирование, не указан — групповое.
- Область действия — процесс детокенизатора целиком; выбрать режим на уровне запроса нельзя.
- При `--detokenizer-worker-num > 1` значение одинаково во всех воркерах.

## Когда использовать

- Наблюдаются краевые артефакты детокенизации: пропавшие или задвоенные символы на границах спецтокенов, некорректная обработка `skip_special_tokens`, расхождение потокового текста с итоговым. Модель `gpt-oss` названа в коде как известный случай.
- При отладке несоответствия между потоковым и непотоковым ответом — чтобы исключить групповое декодирование из подозреваемых.
- **Не** включайте профилактически: вы платите временем CPU детокенизатора на каждом шаге каждого стрима, а выигрываете корректность только там, где она реально ломается.
- Не путайте с `--enable-tokenizer-batch-encode`: тот про вход и про один запрос со списком текстов, этот — про выход и про все активные запросы сразу.

## Влияние на производительность и память

- **CPU процесса детокенизатора — единственная значимая величина.** Групповой `batch_decode` вызывает нативный код токенизатора один раз на группу; построчный вариант делает по вызову на запрос, и это в горячем цикле на каждом шаге декодирования. Чем больше одновременных стримов и чем меньше `--stream-interval`, тем дороже.
- Эффект становится ощутимым ровно там, где полезен: при десятках одновременных запросов. При одном-двух стримах разница неизмерима.
- **VRAM** и **RAM** не затрагиваются: обе ветки работают с теми же списками token ids.
- **Throughput модели** не меняется напрямую, но перегруженный детокенизатор становится узким местом стрима — токены будут генерироваться и ждать выдачи.

## Взаимодействие с другими аргументами

- `--detokenizer-worker-num`: если построчное декодирование насытило один процесс, N процессов распределят нагрузку — но только в multi-tokenizer-режиме (см. `detokenizer-worker-num.md`).
- `--stream-interval`: определяет частоту шагов детокенизации; при малом значении цена построчного декодирования умножается.
- `--enable-tokenizer-batch-encode`: зеркальный аргумент на входе, независимый.
- `--skip-tokenizer-init`: декодировать нечего, флаг бездействует.
- `--tool-call-parser`: значение `gpt-oss` включает отдельную заплатку в `trim_matched_stop` для того же семейства моделей.
- `--tokenizer-path`: артефакты детокенизации могут быть следствием не режима декодирования, а неправильного токенизатора — проверяйте это первым.

## Типовые проблемы и диагностика

- **Симптом:** в потоковом ответе теряются или дублируются символы на границах спецтокенов, итоговый текст отличается от склейки чанков. **Причина:** краевой случай группового декодирования. **Проверка:** повторить тот же запрос с флагом; если артефакт исчез — диагноз подтвержден. **Лечение:** оставить флаг и сообщить о случае апстриму.
- **Симптом:** после включения флага вырос лаг выдачи токенов при высокой конкурентности. **Причина:** ожидаемая цена. **Проверка:** загрузка процесса `sglang::detokenizer` (при `--enable-metrics` там работает поток мониторинга CPU). **Лечение:** снять флаг либо распределить детокенизацию по нескольким процессам.
- **Симптом:** артефакты остались и с флагом. **Причина:** проблема не в режиме декодирования — смотрите на токенизатор (`--tokenizer-path`), на парсер вызова инструментов и на парсер рассуждений.
- **Подтверждение значения:** `disable_tokenizer_batch_decode=True` в дампе `server_args=` при старте.

## В arriero

Флаг влияет на текст, который менеджер получает от движка, — то есть на все, что видит клиент через прокси. Если в трассировках запросов (`#/proxy/traces`) заметны артефакты именно на границах чанков SSE, а не в самом содержании ответа, это как раз тот класс проблем, который аргумент лечит.

Для инстанса kind `ktransformers` включение безопасно: конкурентность в квалифицированном профиле низкая (`docs/KTRANSFORMERS_OPERATIONS.md` — 2 одновременных запроса), поэтому цена построчного декодирования там неощутима. Учтите только, что известный отказ этого профиля — семантически испорченный вывод при HTTP 200 из-за неверной пары пакетов, и он **не** лечится этим флагом; сначала убедитесь, что версии `sglang-kt`/`kt-kernel` соответствуют квалифицированным.

Ключ не зарезервирован за конфигурацией движка и задается обычным аргументом инстанса.

## Примеры

```bash
python -m sglang.launch_server --model-path /models/gpt-oss-20b --host 127.0.0.1 --port 30000 --disable-tokenizer-batch-decode
```

```bash
python -m sglang.launch_server --model-path /models/gpt-oss-20b --host 127.0.0.1 --port 30000 --disable-tokenizer-batch-decode --tool-call-parser gpt-oss
```
