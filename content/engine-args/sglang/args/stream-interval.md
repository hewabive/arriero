# --stream-interval

## Кратко

Это буфер на стороне **планировщика**, а не HTTP-слоя. На каждом шаге декодирования `OutputStreamer` решает, включать ли запрос в исходящий батч, по остатку от деления числа уже сгенерированных токенов на `--stream-interval`. Всё, что не отдано, копится в запросе и уходит одной порцией на следующем совпадении.

Аргумент действует на все стриминговые пути сразу: `/v1/chat/completions`, `/v1/completions`, `/v1/responses`, нативный `/generate`. Нестриминговые запросы им не затрагиваются — у них своя ветка.

## Оригинальная справка

```text
The interval (or buffer size) for streaming in terms of the token length. A smaller value makes streaming smoother, while a larger value makes the throughput higher
```

## Паспорт аргумента

- Флаги: `--stream-interval`
- Группа: `serving`
- Тип значения: целое, единица измерения — токены
- Допустимые значения: `choices` нет; осмысленный диапазон — целые ≥ 1 (см. «Значения и формат» про `0` и отрицательные)
- Значение по умолчанию: `1`
- Эффективное значение: `__post_init__` не переопределяет. На каждом запросе значение может быть перекрыто полем `sampling_params.stream_interval` — но только на нативном `/generate` или через `--preferred-sampling-params`, поскольку OpenAI-схемы этого поля не содержат
- Где объявлен: `ServerArgs.stream_interval`, файл — `sglang/python/sglang/srt/server_args.py`
- Статус: обычный
- Этап применения: инициализация планировщика → каждый шаг декодирования (`_GenerationStreamAccumulator.accept`)

## Что меняет в движке

`sglang/python/sglang/srt/managers/scheduler_components/output_streamer.py`:

```python
stream_interval = req.sampling_params.stream_interval or self.default_stream_interval
should_output = (
    len(req.output_ids) % stream_interval == 1
    if stream_interval > 1
    else len(req.output_ids) % stream_interval == 0
)
if should_output:
    should_output &= not req.check_match_stop_str_prefix()
```

Три следствия:

1. **При `stream_interval > 1` сравнение идет с `1`, а не с `0`.** То есть первый токен уходит клиенту немедленно (`len == 1`), а дальше порции на `1 + k·interval`. TTFT от этого аргумента практически не страдает — страдает плавность после первого токена.
2. **Условие `check_match_stop_str_prefix`** дополнительно придерживает вывод, если хвост совпадает с началом какой-то stop-строки: это чтобы не отдать клиенту кусок стоп-последовательности. Работает независимо от интервала.
3. **Завершение запроса всегда пробивает буфер**: ветка `if req.finished()` выставляет `should_output = True` безусловно, поэтому «хвост» не теряется даже при большом интервале.

У нестриминговых запросов действует отдельный принудительный интервал `DEFAULT_FORCE_STREAM_INTERVAL` из переменной окружения `SGLANG_FORCE_STREAM_INTERVAL` (по умолчанию 50) — он нужен для обновления метрик и обнаружения отвалившегося клиента, `--stream-interval` на него не влияет.

Что именно экономится при большом интервале: сообщение из процесса планировщика в детокенизатор и дальше в токенизатор-менеджер, инкрементальная детокенизация и пробуждение asyncio-задачи HTTP-обработчика. При сотнях одновременных стримов это заметная доля CPU процессов Python.

## Значения и формат

- `1` (по умолчанию) — каждый шаг декодирования отдается наружу. Самый плавный стрим, самая высокая нагрузка на IPC/детокенизацию.
- `2`…`16` — обычный диапазон тюнинга под высокую конкурентность. При `8` клиент получает текст порциями примерно по 8 токенов.
- Значение больше нескольких десятков делает стрим визуально «ступенчатым» и полезно только при очень большом числе одновременных запросов.
- `0` argparse примет, но это фатально: при первом же стриминговом запросе ветка `len(req.output_ids) % 0` даёт `ZeroDivisionError` в процессе планировщика. Значения «отключить стриминг» у аргумента нет.
- Отрицательные значения argparse тоже примет; из-за семантики `%` в Python результат `len % -1 == 0` истинен всегда, то есть поведение вырождается в `1` (для `-1`), а для меньших — в нерегулярную выдачу. Полагаться на это не стоит.
- Единица — токены модели, не символы и не байты.

## Когда использовать

- Много одновременных стримов (десятки-сотни), процесс токенизатора/детокенизатора упирается в CPU, а не GPU — поднимайте до `4`–`16`. Признак: время шага декодирования на GPU мало, а TPOT, который видит клиент, заметно больше.
- Клиент — не человек, а программа (агент, пайплайн), которой плавность не нужна — интервал можно поднимать смело.
- **Не трогайте**, если стрим читает человек в UI: на `8`+ текст начинает «прыгать» блоками.
- **Не используйте** для борьбы с низким throughput генерации: аргумент не ускоряет модель, он только снижает накладные расходы доставки.

## Влияние на производительность и память

- VRAM и KV-пул не затрагиваются вообще.
- RAM/CPU: линейно снижает число межпроцессных сообщений и вызовов инкрементальной детокенизации — примерно в `interval` раз.
- Latency: TTFT не меняется (первый токен уходит сразу), а вот межтокенная задержка, которую видит клиент, становится пилообразной: `interval` токенов приходят одним куском.
- Throughput под конкурентной нагрузкой растет только в том случае, если узкое место было в Python-процессах, а не в GPU.

## Взаимодействие с другими аргументами

- `--batch-notify-size`: соседний по смыслу буфер, но на другом уровне — он группирует пробуждения asyncio уже в `TokenizerManager`. Оба уменьшают накладные расходы стриминга; `--stream-interval` уменьшает **количество** сообщений, `--batch-notify-size` — количество переключений event loop на то же количество сообщений.
- `--incremental-streaming-output`: определяет, что лежит в порции (дельта или накопленный текст). При большом интервале дельты просто становятся длиннее.
- `--preferred-sampling-params`: единственный способ задать `stream_interval` для OpenAI-запросов иначе, чем глобально, — ключ `stream_interval` в этом JSON.
- `--max-running-requests`: чем больше одновременных стримов, тем сильнее эффект от увеличения интервала.
- `--enable-metrics`: метрики TPOT считаются по фактическим выдачам, поэтому при большом интервале распределение межтокенных задержек станет бимодальным — это артефакт измерения, а не деградация модели.

## Типовые проблемы и диагностика

- `ZeroDivisionError` в логе процесса планировщика при первом стриминговом запросе — задан `--stream-interval 0`.
- **Клиент жалуется на «рывки»** — интервал слишком велик; вернитесь к `1`–`4`.
- **Стрим «залипает» на конце фразы** — это `check_match_stop_str_prefix`, а не интервал: хвост совпал с началом одной из stop-строк и придерживается до разрешения неоднозначности.
- **Последняя порция приходит всегда** — по построению; если хвост теряется, причина не в этом аргументе.
- Принятое значение — в дампе `server_args=` при старте.
