# --speculative-ngram-capacity

## Кратко

`--speculative-ngram-capacity` — размер пула узлов префиксного дерева, в котором `--speculative-algorithm NGRAM` хранит n-граммы из обработанных запросов. Пул выделяется целиком при создании воркера (`std::vector<TrieNode>` фиксированной длины), поэтому значение по умолчанию `10 000 000` — это не «до 10 миллионов», а сразу примерно 1.7 ГиБ RAM хоста. Когда свободных узлов не хватает, дерево вытесняет наименее недавно использованные листья. Для локального однопользовательского сервера значение по умолчанию избыточно на порядок.

## Оригинальная справка

```text
The cache capacity for ngram speculative decoding.
```

## Паспорт аргумента

- Флаги: `--speculative-ngram-capacity`
- Группа: `spec`
- Тип значения: int
- Допустимые значения: `choices` нет. Практический минимум — десятки тысяч; ноль или отрицательное значение приведут к попытке взять узел из пустого пула уже при создании корня
- Значение по умолчанию: `10 * 1000 * 1000`, то есть `10000000` (в extract это выражение, а не число)
- Эффективное значение: не переопределяется
- Где объявлен: `ServerArgs.speculative_ngram_capacity`, файл — `sglang/python/sglang/srt/server_args.py`
- Статус: обычный; читается **только** при `--speculative-algorithm NGRAM`
- Этап применения: конструктор `NGRAMWorker` → конструктор C++-класса `Trie` (единовременное выделение пула), дальше — только вытеснение

## Что меняет в движке

`Trie::Trie(capacity, param)` (`sglang/python/sglang/kernels/jit/csrc/ngram_corpus/trie.cpp`) делает `nodes_.resize(capacity)` и заполняет `node_pool_` указателями на все элементы. Конструирование по умолчанию каждого элемента означает, что страницы действительно затрагиваются — память резидентна с первой секунды, а не «по мере роста».

Размер одного `TrieNode` на x86-64 с libstdc++ — 176 байт: `std::unordered_map<int32_t, TrieNode*>` (56) + два `std::list::const_iterator` (16) + `token` (4) + `parent` (8) + `std::list<TrieNode*> lru` (24) + `freq` (4) + `version` (8) + `std::multiset sorted_children` (48). Плюс по указателю на узел в `node_pool_` (8 байт). Итого ≈ 184 байта на единицу ёмкости: `10 000 000 × 184 B ≈ 1.71 ГиБ`. Сверх этого по мере наполнения дерева динамически выделяются бакеты хеш-таблиц, узлы списков и красно-чёрных деревьев для реально созданных рёбер — их объём зависит от разнообразия трафика, а не от ёмкости.

Заполнение: на каждом decode-шаге `_update_ngram_corpus` кладёт в очередь вставки хвост длиной до `--speculative-ngram-max-trie-depth` токенов от каждого запроса батча; фоновый поток `insertWorker` вставляет каждый суффикс этого окна в дерево. Один узел соответствует одной уникальной n-грамме длиной до `max_trie_depth`.

Вытеснение: `Trie::squeeze(count)` берёт хвост глобального LRU-списка и освобождает узлы по одному. Она вызывается прямо из `insert`, когда для очередного суффикса не хватает свободных узлов. Освобождать можно только листья: если в хвосте LRU оказался узел с детьми, бросается `std::runtime_error: The node to be released still has child nodes and cannot be released.`. Порядок LRU поддерживается так, что после вставки путь перемещается в начало списка от корня к листу, поэтому в хвосте оказываются именно давно не использованные листья.

`clear_cache_pool` (сброс кеша движка) вызывает `Trie::reset`: пул возвращается целиком, эпоха дерева инкрементируется, все закешированные позиции запросов инвалидируются. Память при этом не освобождается — `nodes_` остаётся выделенным.

## Значения и формат

- Целое число узлов, не токенов и не байтов. «Ёмкость кеша (число записей)» в апстрим-документации — это именно узлы дерева.
- Верхней границы нет; ограничение практическое — доступный RAM хоста.
- Значение не влияет на GPU-память и на размер верификационного батча.
- Ориентир для расчёта: один активный диалог длиной `N` токенов при глубине 18 создаёт не более `N × 18` узлов, а на практике заметно меньше из-за совпадений префиксов. Тысяча запросов по 2000 токенов — это верхняя оценка порядка 36 млн узлов, но реально повторяющийся текст схлопывается, и большинство локальных нагрузок укладывается в сотни тысяч.

## Когда использовать

- Практически всегда стоит уменьшить: на одиночном локальном сервере `--speculative-ngram-capacity 500000` (≈ 88 МиБ) вместо 1.7 ГиБ по умолчанию, и это ощутимая доля host-резерва инстанса.
- Увеличивать имеет смысл только при устойчиво падающем acceptance rate на длинной сессии — признак того, что полезные n-граммы вытесняются раньше, чем пригодятся.
- Не увеличивать «про запас»: память занимается сразу и целиком, независимо от того, сколько узлов реально используется.
- В arriero это host-память инстанса: она должна помещаться в объявленный host-draw (`docs/RESOURCE_MANAGEMENT.md`), иначе фактическое потребление разойдётся с заявкой и ledger admission перестанет защищать хост.

## Влияние на производительность и память

- RAM хоста: ≈ 184 байта на единицу ёмкости, выделяется и затрагивается при старте. Это доминирующий эффект аргумента.
- VRAM: не влияет вообще — структура целиком на хосте.
- Время старта: выделение и конструирование десятка миллионов объектов занимает заметное время (сотни миллисекунд и больше), плюс первый запуск дополнительно платит JIT-компиляцией расширения `ngram_corpus` (`load_jit`, кеш в `TVM_FFI_CACHE_DIR` или `~/.cache/tvm-ffi`).
- CPU под нагрузкой: от ёмкости не зависит; стоимость вставки и поиска определяется `--speculative-ngram-max-trie-depth`, а не размером пула. Вытеснение при заполненном пуле добавляет по одной операции на освобождаемый узел.
- Acceptance rate: растёт с ёмкостью только до момента, когда рабочий набор n-грамм перестаёт вытесняться; дальше — плато.

## Взаимодействие с другими аргументами

- `--speculative-ngram-max-trie-depth`: определяет, сколько узлов расходуется на один вставленный хвост, и потому — скорость исчерпания ёмкости.
- `--speculative-ngram-external-corpus-max-tokens`: внешние корпуса живут **не** в этом пуле, а в отдельных суффиксных автоматах, и учитываются своим лимитом. Их память складывается с этой.
- `--speculative-ngram-match-type`, `--speculative-ngram-max-bfs-breadth`: определяют, как используются накопленные узлы, но не их количество.
- `--max-running-requests`: сколько запросов одновременно подкладывают хвосты в дерево на каждом шаге (при спекуляции значение по умолчанию — `48`).
- `--speculative-algorithm`: вне `NGRAM` аргумент не читается.

## Типовые проблемы и диагностика

- Процесс сразу после старта занимает на 1.7 ГиБ RSS больше ожидаемого — это ёмкость по умолчанию. Уменьшите значение.
- `std::runtime_error: Insufficient node size to release required nodes.` — запрошено освободить больше узлов, чем занято; означает, что ёмкость меньше, чем нужно для одной вставки (то есть меньше `max_trie_depth`). Поднимите ёмкость.
- `std::runtime_error: The node to be released still has child nodes and cannot be released.` — внутренняя инвариантная ошибка вытеснения; воспроизводимый случай стоит зафиксировать с точными значениями ёмкости и глубины.
- Acceptance rate постепенно деградирует на длинной сессии при неизменном характере трафика — рабочий набор не помещается; увеличьте ёмкость шагами в 2 раза и сравните.
- Чем подтвердить: дамп `server_args=` при старте, RSS процесса инстанса (в arriero — карточка процесса и measured-evidence в `docs/MEMORY_ESTIMATION.md`), строки `Decode batch, … accept len: …, accept rate: …`.
