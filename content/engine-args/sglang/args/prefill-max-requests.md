# --prefill-max-requests

## Кратко

Планировщик собирает prefill-батч, добавляя запросы из отсортированной очереди, пока не упрется в один из бюджетов: свободные токены KV, `--max-prefill-tokens`, `--chunked-prefill-size`. `--prefill-max-requests` добавляет к этому набору четвертую, самую простую границу — по числу запросов. Нужен там, где узкое место — не токены, а сама ширина батча (attention-kernel'ы, память под метаданные, длительность одного prefill-прохода).

## Оригинальная справка

```text
The maximum number of requests in a prefill batch. If not specified, there is no limit.
```

## Паспорт аргумента

- Флаги: `--prefill-max-requests`
- Группа: `schedule`
- Тип значения: целое (`Optional[int]`)
- Допустимые значения: не ограничены на уровне argparse; проверок при старте нет
- Значение по умолчанию: `null` — ограничения по числу запросов нет
- Эффективное значение: не переопределяется; `__post_init__` это поле не читает
- Где объявлен: `ServerArgs.prefill_max_requests`, файл — `sglang/python/sglang/srt/server_args.py`
- Статус: обычный
- Этап применения: передается в `PrefillAdder` при каждой сборке prefill-батча

## Что меняет в движке

Значение доходит до `PrefillAdder` (`sglang/python/sglang/srt/managers/schedule_policy.py`) и проверяется в самом начале `add_one_req`:

```python
if (x := self.prefill_max_requests) is not None and len(self.can_run_list) >= x:
    return AddReqResult.OTHER
```

Возврат `OTHER` обрывает обход очереди в `Scheduler._get_new_batch_prefill_raw` — батч закрывается тем составом, что уже набран. Особенности:

- проверка стоит **до** ветвления на путь `add_one_req_ignore_eos` (он используется для запросов с `ignore_eos` при отключенном radix cache), поэтому ограничение работает на обоих путях;
- продолжение уже начатого chunked prefill добавляется в батч раньше цикла (`adder.add_chunked_req`) и этой проверки не проходит: при `--prefill-max-requests 1` в батче может оказаться chunked-запрос плюс ни одного нового;
- ограничение не влияет на decode-батч и на `--max-running-requests`: запросы, не попавшие в этот проход, остаются в очереди и будут разобраны на следующем.

## Значения и формат

- Целое число запросов.
- `null` (не задан) — без ограничения. Отдельного значения «выключено» нет; чтобы снять ограничение, уберите аргумент.
- `0` формально примется и полностью запретит добавление новых запросов в prefill-батч: условие `len(can_run_list) >= 0` истинно всегда. Сервер при этом перестанет обслуживать очередь — значение аварийное.
- `1` — режим «по одному запросу за prefill-проход»; полезен для диагностики и для нагрузок с очень длинными входами.
- Отрицательные значения ведут себя как `0`.

## Когда использовать

- Attention-backend или kernel плохо переносит широкие prefill-батчи (много коротких запросов в одном проходе), и вы видите скачки времени prefill при неизменном `#new-token`.
- Нужна предсказуемая длительность одного prefill-прохода, чтобы decode не простаивал: ограничение по токенам (`--chunked-prefill-size`) регулирует объем, но не число запросов, а накладные расходы частично зависят именно от количества.
- Не используйте для ограничения конкурентности — для этого есть `--max-running-requests`. Этот аргумент ограничивает только один проход сборки, а не число одновременно обслуживаемых запросов.
- Не используйте для экономии памяти: бюджеты KV проверяются независимо и раньше.

## Влияние на производительность и память

- На объем памяти влияет косвенно: меньше запросов в проходе — меньше одновременно зарезервированных страниц (`page_size` резервируется на каждый принятый запрос) и ниже пиковая память активаций prefill.
- Throughput при слишком малом значении падает: очередь разбирается медленнее, prefill-проходов становится больше.
- TTFT при слишком малом значении растет для «хвоста» очереди.
- На время старта и на размер KV-пула не влияет.

## Взаимодействие с другими аргументами

- `--max-prefill-tokens`: параллельный бюджет по токенам (`rem_input_tokens`). Первым срабатывает тот, который исчерпается раньше.
- `--chunked-prefill-size`: бюджет одного chunk'а; при его исчерпании запрос дробится, а не отбрасывается.
- `--max-running-requests`: ограничивает число одновременно обслуживаемых запросов; prefill-батч дополнительно ограничен числом свободных слотов.
- `--schedule-policy`: определяет, какие именно запросы попадут в лимитированный батч.
- `--enable-mixed-chunk`: смешивает decode-токены в prefill-батч; на счетчик запросов это не влияет, счетчик считает только prefill-запросы из `can_run_list`.
- `--enable-dynamic-chunking`: меняет размер chunk'а, но не число запросов.

## Типовые проблемы и диагностика

- Сервер перестал обслуживать очередь, `#queue-req` растет, `#new-seq` всегда 0 — проверьте, не задан ли `--prefill-max-requests 0`.
- `#new-seq` в строках `Prefill batch, #new-seq: …, #new-token: …` уперся в заданное значение — ограничение активно; если при этом `#queue-req` большой, лимит стал узким местом.
- Ограничение не соблюдается ровно на единицу — в батче участвовал chunked-запрос, добавленный вне цикла.
- Принятое значение видно в дампе `server_args=` при старте.

## Примеры

```bash
python -m sglang.launch_server --model-path /models/Qwen3-30B-A3B --prefill-max-requests 8 --chunked-prefill-size 8192
```

```bash
python -m sglang.launch_server --model-path /models/Qwen3-30B-A3B --prefill-max-requests 1 --max-prefill-tokens 32768
```
