# --lora-drain-wait-threshold

## Кратко

Когда активных адаптеров больше, чем слотов, набор «занявших» слоты адаптеров может не меняться сколь угодно долго: пока к ним идут новые запросы, слот не освобождается, а заявки к остальным адаптерам просто пропускаются в очереди. `--lora-drain-wait-threshold` задает время ожидания, после которого планировщик помечает один из работающих адаптеров как «сливаемый»: новых запросов он больше не принимает, дорабатывает текущие и отдает слот голодающему. По умолчанию `0` — механизм выключен.

## Оригинальная справка

```text
When any LoRA adapter request waits longer than this threshold (in seconds), the scheduler will selectively drain one running adapter to make room. This mitigates extreme tail latency under high or skewed workloads by preventing a small set of adapters from monopolizing batch slots. Set to 0 to disable draining (default).
```

## Паспорт аргумента

- Флаги: `--lora-drain-wait-threshold`
- Группа: `lora`
- Тип значения: float, секунды
- Допустимые значения: неотрицательное число; `assert self.lora_drain_wait_threshold >= 0.0, "--lora-drain-wait-threshold must be non-negative."`
- Значение по умолчанию: `0.0` — слив выключен
- Эффективное значение: не переопределяется
- Где объявлен: `ServerArgs.lora_drain_wait_threshold`, файл — `sglang/python/sglang/srt/server_args.py`
- Статус: обычный
- Этап применения: `__post_init__` (валидация) → `Scheduler.init_lora_drainer` (объект создается только при значении > 0) → каждый раунд сборки prefill-батча

## Что меняет в движке

`LoRADrainer` (`sglang/python/sglang/srt/lora/lora_drainer.py`) создается только если значение строго больше нуля; при `0` поле `scheduler.lora_drainer` равно `None`, и все проверки ниже не выполняются.

На каждом раунде планирования, если LoRA включена, вызывается `update_draining_state(waiting_queue, running_reqs)`:

1. **Сбор статистики.** По очереди ожидания — число ждущих заявок на адаптер и максимальное время ожидания (`time.monotonic() - req.time_stats.wait_queue_entry_time`). По работающим — максимум оставшихся токенов (`max_new_tokens - len(output_ids)`).
2. **Выбор голодающих.** Адаптер «голодает», если его максимальное ожидание превысило порог **и** у него есть ждущие заявки.
3. **Ранний выход.** Если число различных адаптеров среди работающих меньше `--max-loras-per-batch`, слив не нужен: место и так есть, метод возвращается сразу.
4. **Назначение жертв.** Голодающие сортируются по убыванию времени ожидания. Для каждого из тех, ради кого слив ещё не идет, выбирается работающий адаптер с **минимальным** `max_remaining_tokens` (то есть тот, кто закончит раньше всех) и помечается `is_draining_for = <голодающий>`. Один адаптер сливается ради одного голодающего.
5. **Снятие метки.** Адаптер, у которого не осталось работающих заявок, считается слитым, и метка снимается.

Фильтр в планировщике — `LoRADrainer.can_schedule(req)`, вызываемый из `Scheduler._can_schedule_lora_req` **до** проверки вместимости пула:

```python
stats = self.adapter_to_stats[req.lora_id]
if not stats.is_draining_for:
    return True
return req.sampling_params.max_new_tokens <= stats.max_remaining_tokens * DRAIN_SCHEDULE_TOLERANCE
```

`DRAIN_SCHEDULE_TOLERANCE = 1.2`. То есть сливаемый адаптер не блокируется наглухо: короткая заявка, которая заведомо закончится не позже уже работающих (с запасом 20 %), всё ещё принимается. Это не даёт слиться в тупик, где адаптер простаивает ради одной длинной генерации.

## Значения и формат

- Дробное число секунд: `--lora-drain-wait-threshold 0.5` и `--lora-drain-wait-threshold 2` одинаково допустимы.
- `0` (по умолчанию) — механизм полностью выключен, объект `LoRADrainer` не создается.
- Отрицательное — ассерт при старте.
- Очень малое положительное значение (например `0.01`) практически означает «сливать при любой задержке»: почти каждая заявка в очереди будет считаться голодающей, и набор работающих адаптеров начнет постоянно ротироваться.
- Отсчет ведется от момента постановки заявки в очередь ожидания (`wait_queue_entry_time`), а не от прихода HTTP-запроса.

## Когда использовать

- Перекошенный трафик: один-два популярных адаптера постоянно держат все слоты, а редкие адаптеры ждут минутами. Симптом — большой разброс TTFT по адаптерам при незагруженном GPU.
- Мультиарендный сервис, где SLA задан по худшему арендатору, а не по среднему.
- Разумная отправная точка — величина порядка типичного времени полной генерации: слишком малый порог превратит сервер в машину по перезагрузке адаптеров, слишком большой не сработает никогда.
- **Не включайте**, если адаптеров не больше, чем слотов: ранний выход по числу работающих адаптеров сделает механизм холостым.
- **Не используйте** как средство от нехватки VRAM: слив не уменьшает пул, он перераспределяет очередь. Настоящее решение — больше слотов или меньше адаптеров.

## Влияние на производительность и память

- Памяти не требует: `LoRADrainer` хранит небольшой словарь статистики на адаптер.
- CPU планировщика: один проход по очереди ожидания и по работающим заявкам на раунд. При очень длинной очереди это заметно в однопоточном цикле scheduler'а, но на порядки дешевле работы с мультимодальными входами.
- **Throughput снижается**: сливаемый адаптер перестает принимать новые заявки, и его слот часть времени простаивает, пока текущие заявки дорабатывают. Это осознанный размен пропускной способности на хвостовую latency.
- Частота промахов слота растет: ротация адаптеров учащается, а значит учащаются и H2D-копии весов.
- На VRAM, размер KV-пула и на decode-фазу не влияет.

## Взаимодействие с другими аргументами

- `--max-loras-per-batch`: слив включается только когда число различных работающих адаптеров достигло этого значения. Увеличение числа слотов — альтернатива сливу, а не дополнение.
- `--lora-eviction-policy`: работает на другом уровне — выбирает, чей слот освободить, когда место уже нужно. Слив же решает, кого перестать пускать в батч.
- `--enable-lora-overlap-loading`: удешевляет промах слота, то есть смягчает побочный эффект слива.
- `--max-loaded-loras`: ярус RAM; на слив не влияет.
- `--schedule-policy`, `--enable-priority-scheduling`: другие механизмы упорядочивания очереди; слив применяется до проверки вместимости пула и поверх выбранной политики.
- `--enable-lora`: без неё драйнер не создается.

## Типовые проблемы и диагностика

- `AssertionError: --lora-drain-wait-threshold must be non-negative.`
- Порог задан, а эффекта нет: чаще всего число различных работающих адаптеров меньше `--max-loras-per-batch`, и срабатывает ранний выход. Проверьте `sglang:lora_pool_slots_used` — если он стабильно ниже `sglang:lora_pool_slots_total`, сливать нечего.
- Пропускная способность просела после включения: порог слишком мал, адаптеры ротируются постоянно. Увеличивайте.
- Отдельный адаптер всё равно ждет долго: у сливаемого адаптера остались длинные генерации — слив ждет их завершения, `DRAIN_SCHEDULE_TOLERANCE` только фильтрует новые заявки, но не прерывает работающие.
- События слива пишутся на уровне `debug`: `LoRA adapter <id> is draining for <id>` и `LoRA adapter <id> finished draining`. Значение аргумента видно в дампе `server_args=`.
