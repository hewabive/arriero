# --offload-prefetch-step

## Кратко

Вторая схема оффлоада не копирует веса в момент, когда они понадобились, — она загружает их заранее, в отдельном CUDA-потоке, пока считаются предыдущие слои. `--offload-prefetch-step` задает глубину этого забегания: сколько выгруженных подмодулей одновременно находятся в процессе загрузки или уже загружены. Значение по умолчанию `1` — то есть пока считается подмодуль `i`, загружается `i + 1`.

Смысл ручки — компромисс. Экономия VRAM от оффлоада уменьшается ровно на объем `prefetch_step` резидентных подмодулей: при глубине, сравнимой с числом выгруженных групп, в памяти одновременно оказывается почти всё, что вы выгрузили, и экономия исчезает.

## Оригинальная справка

```text
Steps to prefetch in offloading.
```

## Паспорт аргумента

- Флаги: `--offload-prefetch-step`
- Группа: `exec.offload`
- Тип значения: int (число подмодулей)
- Допустимые значения: положительное целое; argparse ограничений не накладывает
- Значение по умолчанию: `1`
- Эффективное значение: совпадает с заданным; автоподбора нет
- Где объявлен: `ServerArgs.offload_prefetch_step`, файл — `sglang/python/sglang/srt/server_args.py`
- Статус: обычный
- Этап применения: `post_init` офлоадера (первичная предзагрузка) → каждый forward выгруженного подмодуля

## Что меняет в движке

Значение используется в двух местах `sglang/python/sglang/srt/utils/offloader.py`:

```python
def post_init(self):
    for offloader in self.offloaders:
        offloader.post_init()
    for i in range(self.prefetch_step):
        self.offloaders[i].start_onload()
```

и в хуке завершения forward'а:

```python
def _on_forward_end():
    offloaders[(index + prefetch_step) % len(offloaders)].start_onload()
    offloaders[index].offload()
```

Индексация кольцевая (`% len(offloaders)`), поэтому значение, большее числа выгруженных подмодулей, не выходит за границы — оно просто приводит к тому, что загрузка запускается повторно для уже загруженных, и ни один подмодуль не успевает освободиться до следующего цикла.

Загрузка идет в потоке `get_stream("offload")` — специально отдельном от «альтернативного» потока моделей, чтобы копирование не сериализовалось с чужой работой. Синхронизация через `torch.cuda.Event`: `wait_and_get_device_tensors` ждет событие только если оно записано.

Отдельная ветка — захват CUDA graph: при `torch.cuda.is_current_stream_capturing()` тензоры создаются прямо в текущем потоке без события, то есть внутри графа перекрытия нет.

Обратите внимание: `post_init` запускает предзагрузку без модульной защиты (`self.offloaders[i]`), поэтому при пустом списке офлоадеров и значении больше нуля будет `IndexError`. Пустым список становится, если `--offload-num-in-group` равен `0`.

## Значения и формат

- Целое число подмодулей (не слоев модели: считаются только выгруженные).
- `1` — минимальное осмысленное значение и значение по умолчанию: одна группа загружается, пока считается предыдущая.
- `0` — предзагрузки нет вовсе; тогда `wait_and_get_device_tensors` наткнется на `assert self._device_tensors is not None` и forward упадет. Значение не проверяется на старте.
- Значения, сравнимые с числом выгруженных подмодулей, обнуляют экономию памяти.
- Без `--offload-group-size` больше нуля значение не читается.

## Когда использовать

- Увеличивать до 2–3, когда профилирование показывает, что forward ждет на событии загрузки: полосы PCIe не хватает, чтобы уложиться в время вычисления одного шага.
- Оставлять `1`, когда цель — максимальная экономия VRAM, а падение скорости приемлемо.
- Считать бюджет заранее: резидентный объем равен `prefetch_step × размер одного выгруженного подмодуля`, и он не входит в расчет KV-пула — тот считается по свободной памяти после загрузки весов, когда предзагрузки еще нет.
- Не увеличивать вслепую: сверх точки, где копирование уже полностью перекрыто, дополнительные шаги только занимают VRAM.

## Влияние на производительность и память

- VRAM: `prefetch_step` подмодулей резидентны одновременно. Это прямой вычет из экономии, ради которой включался оффлоад.
- RAM хоста: не меняет — объем выгруженного задают `--offload-group-size` и `--offload-num-in-group`.
- Время старта: `post_init` запускает первые `prefetch_step` загрузок; на общем времени старта это малозаметно.
- Latency: главный эффект. При достаточной глубине копирование полностью прячется за вычислением, и оффлоад почти не стоит времени; при недостаточной каждый выгруженный слой добавляет ожидание.
- Throughput: следует за latency.
- CUDA graph: внутри захвата предвыборка не работает — если графы включены и часть decode-пути захвачена, выигрыш от предвыборки на этой части не проявляется.

## Взаимодействие с другими аргументами

- `--offload-group-size`: включает схему; определяет, сколько всего выгруженных подмодулей существует, а значит и потолок осмысленной глубины.
- `--offload-num-in-group`: вместе с размером группы задает и число подмодулей, и их суммарный объем.
- `--offload-mode`: в режиме `sharded_gpu` «загрузка» — это сбор шардов с других рангов, а не копирование по PCIe, и стоимость шага другая.
- `--cpu-offload-gb`: у первой схемы предвыборки нет вовсе, аргумент к ней не относится.
- `--mem-fraction-static`: резидентные предзагруженные подмодули появляются уже после расчета KV-пула, поэтому запас под них нужно закладывать вручную.
- `--disable-cuda-graph`: без графов вся decode-часть идет по eager-пути, где предвыборка работает.

## Типовые проблемы и диагностика

- `AssertionError` в `wait_and_get_device_tensors` (`assert self._device_tensors is not None`) — предзагрузка не была запущена; проверьте, что значение не `0`.
- `IndexError` в `post_init` — список офлоадеров пуст (например, `--offload-num-in-group 0`), а предзагрузка запрашивается.
- VRAM почти не освободилась, хотя выгружено много слоев — глубина предвыборки сравнима с числом выгруженных подмодулей.
- Оффлоад включен, скорость упала сильнее ожидаемого — перекрытия не хватает; попробуйте увеличить значение на 1 и сравнить время decode-шага.
- Что смотреть: строки `[offloader] offload module_index=… memory_allocated=…` при построении (число выгруженных подмодулей — это потолок для глубины) и фактическое потребление VRAM в `nvidia-smi` под нагрузкой, а не сразу после старта.

## Примеры

```bash
python -m sglang.launch_server --model-path /models/DeepSeek-V2-Lite --offload-group-size 4 --offload-num-in-group 1 --offload-prefetch-step 2
```

```bash
python -m sglang.launch_server --model-path /models/DeepSeek-V2-Lite --offload-group-size 2 --offload-num-in-group 1 --offload-prefetch-step 1 --offload-mode cpu
```
