# --num-reserved-decode-tokens

## Кратко

Аргумент живет в группе `disagg` и читается **только** серверами с `--disaggregation-mode decode`. Decode-сервер принимает запрос, у которого уже есть готовый KV-префикс, и дальше должен его дописывать. Чтобы допущенный запрос не упирался в исчерпанный пул через два шага и не отправлялся на вытеснение, планировщик заранее считает `--num-reserved-decode-tokens` токенов «уже занятыми» на каждый активный запрос. Значение — это компромисс: чем больше резерв, тем реже вытеснения и тем меньше запросов помещается одновременно.

## Оригинальная справка

```text
Number of decode tokens that will have memory reserved when adding new request to the running batch.
```

## Паспорт аргумента

- Флаги: `--num-reserved-decode-tokens`
- Группа: `disagg`
- Тип значения: int
- Допустимые значения: `choices` нет; осмысленны целые ≥ 0
- Значение по умолчанию: `512`
- Эффективное значение: совпадает с заданным — ни один `_handle_*` его не переписывает. Единственное отклонение внутри логики: для SWA-пула резерв обнуляется, когда radix-кеш выключен (на decode это состояние по умолчанию)
- Где объявлен: `ServerArgs.num_reserved_decode_tokens`, файл — `sglang/python/sglang/srt/server_args.py`
- Статус: обычный
- Этап применения: передается в `DecodePreallocQueue` при инициализации scheduler'а decode-сервера → участвует в каждом решении о допуске запроса и в расчете бюджета токенов

## Что меняет в движке

Значение входит в три формулы в `disaggregation/decode.py`:

1. **Требование на один запрос.** `_prealloc_required_tokens` возвращает `full_len + num_reserved_decode_tokens`, где `full_len` — длина принимаемого KV, выровненная по `--page-size`. То есть запрос допускается, только если помимо его собственного KV в пуле есть еще этот резерв.
2. **Суммарный резерв.** `_active_reserved_tokens = num_reserved_decode_tokens * n_active`, где `n_active` считает **все** запросы, за которые сервер уже отвечает: работающий батч, очередь предвыделения, очередь передачи и очередь ожидания. Эта величина вычитается из доступного размера пула при расчете `allocatable_tokens`.
3. **Возобновление вытесненных.** `resume_retracted_reqs` возвращает вытесненный запрос, только если хватает места еще на `num_reserved_decode_tokens` шагов вперед; пока очередь вытесненных не пуста, новые запросы не принимаются вовсе.

Отдельный случай — SWA-пул: `swa_reserved` равен тому же числу, но обнуляется, если `disable_radix_cache` истинно. На decode-сервере radix по умолчанию выключен принудительно, поэтому по SWA-хвосту резерв по умолчанию не берется — берется только по полному пулу.

Есть еще поправка на «только что завершившийся prebuilt-батч»: его запросы уже не в очередях, но их резерв (`num_reserved_decode_tokens × размер батча`) вычитается из бюджета явно, чтобы окно между итерациями не давало ложного профицита.

## Значения и формат

- Целое число токенов. `512` — умолчание.
- `0` формально допустим и означает «не резервировать»: запросы будут допускаться под ровно доехавший KV и вытесняться при первом же дефиците. Планировщик к этому готов (`retracted_queue` и `resume_retracted_reqs` существуют), но поведение станет пилообразным.
- Верхней границы нет. Значение больше типичной длины ответа просто снижает конкурентность без пользы.
- Единица измерения — токены KV, а не страницы: с `--page-size > 1` фактическое выделение округляется вверх аллокатором, но резерв считается в токенах.
- Вне `--disaggregation-mode decode` значение не читается.

## Когда использовать

- Длинные ответы (агентные цепочки, размышляющие модели) и заметная доля вытеснений в логе: поднимайте до величины, близкой к типичной длине генерации.
- Тесный KV-пул и короткие ответы: уменьшайте, чтобы поднять число одновременно работающих запросов. Ориентир — p90 длины ответа вашего трафика.
- Не трогайте, если вытеснений нет, а `max_running_requests` и так упирается в явное ограничение, а не в память: резерв тогда ни на что не влияет.
- Не используйте как способ ограничить длину ответа — для этого есть `--context-length` и параметры запроса.

## Влияние на производительность и память

- **Конкурентность.** Прямая: эффективный бюджет пула уменьшается на `num_reserved_decode_tokens × n_active`. При 512 и 64 активных запросах это 32 768 токенов, «вычеркнутых» из пула.
- **Вытеснения.** Обратная: маленький резерв → чаще срабатывает retract, а каждый retract стоит потери уже посчитанного KV и повторной работы.
- **VRAM.** Аллокации не добавляет: это учетная величина в бюджете, а не отдельный буфер.
- **Latency.** Резерв не влияет на скорость шага; влияет на дисперсию — вытесненный и возобновленный запрос получает большой всплеск ITL.
- **Время старта.** Не влияет.

## Взаимодействие с другими аргументами

- `--disaggregation-mode decode`: единственный режим, где значение читается.
- `--max-running-requests`: верхняя граница `n_active` по работающему батчу; вместе с резервом определяет, сколько токенов вообще останется под данные.
- `--disaggregation-decode-extra-slots`: вторая ось того же дефицита — строки пула `req_to_token` против токенов KV.
- `--mem-fraction-static`: задает размер пула, из которого вычитается резерв.
- `--disaggregation-decode-enable-radix-cache` / `--disable-radix-cache`: при выключенном radix резерв по SWA-хвосту не берется; при включенном — берется, и дополнительно в бюджет попадает вытесняемая часть дерева.
- `--page-size`: длина принимаемого KV выравнивается по странице до прибавления резерва.
- `--disaggregation-decode-polling-interval`: чем реже опрос, тем дольше запросы стоят в очередях и тем дольше держат резерв.

## Типовые проблемы и диагностика

- Частые вытеснения и «пилообразный» ITL на decode: резерв мал относительно длины ответов. Поднимайте до p90 длины генерации.
- Конкурентность заметно ниже `--max-running-requests` при свободной памяти по `nvidia-smi`: память «съедена» резервом, а не данными. Считайте `num_reserved_decode_tokens × n_active` и сравнивайте с `max_total_num_tokens` из строки `KV Cache is allocated. ...` в логе старта.
- Запросы вообще не принимаются, хотя пул почти пуст: скорее всего непустая `retracted_queue` — `process_decode_queue` выходит до допуска новых. Резерв здесь лечит причину, а не симптом.
- Принятое значение — в дампе `server_args=` при старте.
- **В arriero:** это аргумент decode-половины PD-развертывания, которое менеджер не супервизирует (один процесс на инстанс, `process/supervisor.ts`); в конфигурации обычного инстанса он не нужен.

## Примеры

```bash
python -m sglang.launch_server --model-path meta-llama/Llama-3.1-8B-Instruct --disaggregation-mode decode --port 30001 --max-running-requests 128 --num-reserved-decode-tokens 1024
```

```bash
python -m sglang.launch_server --model-path deepseek-ai/DeepSeek-V3 --disaggregation-mode decode --port 30001 --tensor-parallel-size 16 --dp-size 16 --enable-dp-attention --max-running-requests 256 --num-reserved-decode-tokens 256 --mem-fraction-static 0.8
```
