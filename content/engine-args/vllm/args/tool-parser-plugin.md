# --tool-parser-plugin

## Кратко

Аргумент принимает путь к файлу, а не имя пакета. Файл импортируется на старте, и все, что он зарегистрировал через `ToolParserManager.register_module`, становится доступным по имени в `--tool-call-parser`.

Две неочевидные детали: путь короче четырех символов молча игнорируется, а неудачный импорт не роняет сервер — он логируется, и падение приходит позже, на проверке имени парсера.

## Оригинальная справка

```text
Special the tool parser plugin write to parse the model-generated tool
into OpenAI API format, the name register in this plugin can be used in
`--tool-call-parser`.
```

## Паспорт аргумента

- Флаги: `--tool-parser-plugin`
- Группа argparse: `Frontend`
- Тип значения: str — путь к файлу с Python-кодом
- Допустимые значения: не ограничены; проверка одна — `len(value) > 3`
- Значение по умолчанию: `""` (пустая строка), то есть плагин не загружается
- Эффективное значение: не переопределяется
- Где объявлен: `vllm/entrypoints/openai/cli_args.py:BaseFrontendArgs.tool_parser_plugin`
- Этап применения: старт сервера, до валидации имени парсера и до создания движка

## Что меняет в движке

Загрузка происходит в двух местах `vllm/entrypoints/openai/api_server.py` — в `setup_server` и в `run_server_worker`, оба раза одинаково:

```text
if args.tool_parser_plugin and len(args.tool_parser_plugin) > 3:
    ToolParserManager.import_tool_parser(args.tool_parser_plugin)
```

`import_tool_parser` берет имя модуля из basename файла и импортирует его через `import_from_path`. Импорт обернут в `try/except`, который **логирует** `Failed to load module '<name>' from <path>.` и продолжает работу. Никакого исключения наружу не идет.

Регистрация выполняется самим файлом плагина — декоратором `@ToolParserManager.register_module("my_parser")` над классом-наследником `ToolParser`. Декоратор кладет в реестр ленивую запись «имя → (модуль, класс)», а фактический импорт класса происходит при первом обращении.

Сразу после загрузки плагина вызывается `validate_api_server_args`: если `--enable-auto-tool-choice` включен, а имя из `--tool-call-parser` в реестр так и не попало, старт падает с `KeyError` и списком известных имен. Это и есть настоящий сигнал о том, что плагин не загрузился.

## Значения и формат

- Абсолютный или относительный путь к `.py`-файлу: `--tool-parser-plugin /etc/vllm/my_tool_parser.py`.
- Пустая строка (значение по умолчанию) — плагин не загружается.
- **Строка длиной 1-3 символа игнорируется без единого сообщения** из-за проверки `len(...) > 3`. Опечатка вроде `--tool-parser-plugin ./x` пройдет как «плагин не задан».
- Один аргумент — один файл; повторное указание перекрывает предыдущее. Несколько парсеров регистрируйте из одного файла.
- Имя, под которым парсер будет доступен, определяется не путем, а аргументом декоратора внутри файла.

## Когда использовать

- Модель с собственным форматом вызовов, для которого встроенного парсера нет, — штатный способ, рекомендованный `vllm/docs/features/tool_calling.md`.
- Патч поведения встроенного парсера без пересборки движка: наследуетесь от нужного класса и регистрируете под новым именем.
- Не используйте для кода, которому вы не доверяете: файл исполняется в процессе API-сервера с его правами, до всякой авторизации запросов.
- Не используйте, если хватает встроенного имени: любая пользовательская реализация становится вашей зоной ответственности при обновлении vLLM (`ToolParser` — внутренний интерфейс без гарантий совместимости).

## Влияние на производительность и память

Разовый импорт на старте, доли секунды и десятки мегабайт RAM хоста в худшем случае. Влияние на генерацию нулевое — работает только зарегистрированный парсер, и его цена описана в `--tool-call-parser`.

## Взаимодействие с другими аргументами

- `--tool-call-parser`: единственный потребитель зарегистрированного имени.
- `--enable-auto-tool-choice`: без него ни имя, ни плагин не применяются к запросам; и валидация имени тоже не выполняется, поэтому неудачный импорт вообще ничем себя не проявит.
- `--reasoning-parser-plugin`: полный аналог для парсеров рассуждений, загружается рядом теми же двумя строками.

## Типовые проблемы и диагностика

- **Симптом:** старт падает с `KeyError: invalid tool call parser: my_parser (chose from { ... })`, хотя плагин указан. **Причина:** импорт файла не удался или файл не зарегистрировал это имя. **Проверка:** в логе выше должна быть строка `Failed to load module '<name>' from <path>.` с трассировкой. **Лечение:** починить файл или путь.
- **Симптом:** ни ошибки, ни эффекта. **Причина:** длина значения не больше трёх символов — условие загрузки не выполнено. **Лечение:** указать полный путь.
- **Симптом:** плагин работал, после обновления vLLM перестал импортироваться. **Причина:** изменился внутренний интерфейс `ToolParser`. **Проверка:** трассировка в строке `Failed to load module`. **Лечение:** привести класс к текущей сигнатуре `vllm/tool_parsers/abstract_tool_parser.py`.
- **Подтверждение принятого значения:** имя из плагина появляется в списке `vllm serve --help` для `--tool-call-parser`, а при неверном имени — в перечне в тексте `KeyError`.

## Примеры

```bash
vllm serve /models/Qwen3-4B --tool-parser-plugin /etc/vllm/my_tool_parser.py --enable-auto-tool-choice --tool-call-parser my_parser
```

```bash
vllm serve /models/Qwen3-4B --tool-parser-plugin /etc/vllm/my_tool_parser.py --enable-auto-tool-choice --tool-call-parser my_parser --chat-template /etc/vllm/my_tools.jinja
```
