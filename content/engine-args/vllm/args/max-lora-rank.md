# --max-lora-rank

## Кратко

Значение задаёт размер слота, а не ранг конкретного адаптера. Буферы выделяются под максимум сразу, адаптер меньшего ранга занимает часть слота (`copy_` в срез `[:r, :]`), а остаток остаётся нулями — то есть завышенный `--max-lora-rank` расходуется вхолостую.

Список допустимых значений жёстко зафиксирован в `Literal` и проверяется argparse. Адаптер с рангом больше заданного отвергается при загрузке, до копирования весов.

## Оригинальная справка

```text
Max LoRA rank.
```

## Паспорт аргумента

- Флаги: `--max-lora-rank`
- Группа argparse: `LoRAConfig`
- Тип значения: int с фиксированным перечнем (`MaxLoRARanks = Literal[...]`)
- Допустимые значения: `1`, `8`, `16`, `32`, `64`, `128`, `256`, `320`, `512` — argparse отвергает всё остальное на разборе командной строки
- Значение по умолчанию: `16`
- Эффективное значение: не переопределяется; косвенно ограничивает ранг фиктивных адаптеров при профилировании (`min(max_lora_rank, 8)`, при `--fully-sharded-loras` дополнительно округляется вверх до кратного `tensor_parallel_size`)
- Где объявлен: `vllm/config/lora.py:LoRAConfig.max_lora_rank`
- Этап применения: загрузка модели (размер буферов) → профилирование памяти → загрузка каждого адаптера (валидация ранга)

## Что меняет в движке

**Размер слота.** В `create_lora_weights()` каждой обёртки ранг входит в обе стороны разложения:

- `lora_a_stacked`: `(max_loras, 1, max_lora_rank, input_size)`,
- `lora_b_stacked`: `(max_loras, 1, output_size, max_lora_rank)`.

Для MoE-обёртки к этому добавляется размерность экспертов: `w13_lora_a_stacked` — `(max_loras, E, rank, hidden_size)`, `w2_lora_b_stacked` — `(max_loras, E, hidden_size, rank)` и так далее.

**Валидация адаптера.** `PEFTHelper.validate_legal()` сравнивает `r` из `adapter_config.json` с `max_lora_rank` и при превышении добавляет в сообщение `LoRA rank {r} is greater than max_lora_rank {N}.` Проверка выполняется до `from_local_checkpoint`, то есть до чтения весов.

**Прогрев.** `maybe_setup_dummy_loras()` умышленно берёт ранг `max_lora_rank if max_lora_rank < 8 else 8`, чтобы фиктивные адаптеры не раздували пик активаций. Сами буферы при этом уже выделены под полный ранг, поэтому профилирование измеряет память корректно.

**Шардирование.** При `--fully-sharded-loras` и `tensor_parallel_size > 1` для column-parallel слоёв берётся `divide(max_lora_rank, tp_size)`, а `divide` требует точной делимости: комбинация вроде ранга `1` с TP `2` завершится ошибкой делимости на старте.

## Значения и формат

- Только одно из девяти перечисленных чисел. Ранги вроде `4`, `24`, `48` не принимаются — argparse ответит `invalid choice`.
- Значение `1` формально допустимо, но осмысленно только при TP 1 (см. выше про делимость при `--fully-sharded-loras`).
- Значение `320` в списке присутствует специально: это не степень двойки, а ранг, встречающийся у части опубликованных адаптеров.
- Ранг конкретного адаптера читается из `r` в его `adapter_config.json`; вычислять его по формам тензоров не требуется.

## Когда использовать

- Задавайте максимум по фактическому набору адаптеров и округляйте вверх до ближайшего допустимого значения. Для набора рангов `[16, 32, 64]` правильное значение — `64`, а не `256`.
- Оставляйте дефолт `16`, только если все адаптеры действительно ранга ≤ 16.
- Не задавайте «с запасом на будущее»: память под слот выделяется целиком и не возвращается.
- Если в набор попал один адаптер с непропорционально большим рангом, дешевле обслуживать его отдельным инстансом, чем поднимать `--max-lora-rank` для всех.

## Влияние на производительность и память

- **VRAM.** Линейный множитель во всех буферах адаптеров вместе с `--max-loras`. Переход с 16 на 64 при прочих равных учетверяет постоянно занятую под LoRA память и ровно на столько же сокращает KV-cache.
- **RAM хоста.** Прямо не влияет: на CPU хранятся веса реальных адаптеров их собственного ранга, а не слоты.
- **Время старта.** Слабо: аллокация нулевых тензоров дешёвая, профилирование выполняется на урезанном ранге.
- **Throughput.** Ядра shrink/expand работают на реальном ранге адаптера, а не на `max_lora_rank`, поэтому завышенное значение бьёт по памяти, а не по времени forward. Upstream-документация тем не менее предупреждает и о деградации производительности при сильно завышенном значении.

## Взаимодействие с другими аргументами

- `--max-loras`: второй множитель тех же буферов; итоговая память пропорциональна произведению.
- `--lora-dtype`: определяет размер элемента буфера (2 байта для `float16`/`bfloat16`).
- `--fully-sharded-loras` + `--tensor-parallel-size`: делят ранг между рангами TP для column-parallel слоёв; требуется точная делимость.
- `--lora-target-modules`: уменьшает число слоёв, к которым применяется этот множитель.
- `--gpu-memory-utilization`: общий бюджет; всё, что ушло в LoRA-буферы, не достанется KV-cache.

## Типовые проблемы и диагностика

- **Симптом:** argparse отвечает `argument --max-lora-rank: invalid choice: 48`. **Причина:** значение вне фиксированного списка. **Лечение:** взять ближайшее допустимое сверху (`64`).
- **Симптом:** загрузка адаптера падает с `LoRA rank 64 is greater than max_lora_rank 16.` **Причина:** ранг адаптера больше слота. **Проверка:** поле `r` в `adapter_config.json` адаптера. **Лечение:** поднять `--max-lora-rank` до нужного значения из списка.
- **Симптом:** при статическом `--lora-modules` сервер не поднимается вовсе. **Причина:** та же ошибка ранга, но `init_static_loras` превращает её в `ValueError` и прекращает старт.
- **Симптом:** после подъёма ранга упал `Maximum concurrency` и участились вытеснения. **Причина:** буферы отняли память у KV-cache. **Лечение:** вернуть минимально достаточный ранг, ограничить `--lora-target-modules` или поднять `--gpu-memory-utilization`.
- **Симптом:** ошибка делимости при старте с TP > 1. **Причина:** `--fully-sharded-loras` с рангом, не кратным `tensor_parallel_size`. **Лечение:** выбрать ранг, кратный числу рангов TP, или снять `--fully-sharded-loras`.

## Примеры

```bash
vllm serve /models/Qwen3-4B --enable-lora --max-lora-rank 64 --max-loras 2
```

```bash
vllm serve /models/Qwen3-4B --enable-lora --max-lora-rank 32 --lora-target-modules q_proj k_proj v_proj o_proj
```
