# --lora-target-modules

## Кратко

Аргумент задаёт **пересечение** с тем, что поддерживает модель: обёртка ставится на модуль, если он и в списке поддерживаемых LoRA-модулей модели, и проходит этот фильтр. Всё, что не обёрнуто, не получает LoRA-буферов — отсюда экономия VRAM.

Опасная часть: фильтр применяется к модели, а не к адаптеру. Веса адаптера для отфильтрованных модулей всё равно читаются с диска, но никогда не применяются, и никакого предупреждения об этом не печатается. Выход модели тихо отличается от того, что даёт тот же адаптер без фильтра.

## Оригинальная справка

```text
Restrict LoRA to specific module suffixes (e.g., ["o_proj", "qkv_proj"]).
If None, all supported LoRA modules are used. This allows deployment-time
control over which modules have LoRA applied, useful for performance tuning.
```

## Паспорт аргумента

- Флаги: `--lora-target-modules`
- Группа argparse: `LoRAConfig`
- Тип значения: список строк (`list[str] | None` ⇒ `type=optional_type(str)`, `nargs="+"`)
- Допустимые значения: не ограничены; ожидаются суффиксы имён модулей (`o_proj`, `qkv_proj`, `gate_up_proj`, `down_proj`, …). Реальный набор зависит от архитектуры и виден как множество, собранное `get_supported_lora_modules()` по всем `LinearBase`/`MoERunner` модели
- Значение по умолчанию: `null` (`None`) — ограничений нет, оборачиваются все поддерживаемые модули
- Эффективное значение: не переопределяется; входит в `LoRAConfig.compute_hash()`, поэтому смена списка инвалидирует кэш компиляции
- Где объявлен: `vllm/config/lora.py:LoRAConfig.target_modules`
- Этап применения: загрузка модели (`_create_lora_modules`, подмена слоёв) — позже фильтр нигде не перепроверяется

## Что меняет в движке

`LoRAModelManager._match_target_modules(name)` возвращает `True`, только если выполнены оба условия: `is_supported_lora_module(name, supported_lora_modules)` и `is_in_target_modules(name, target_modules, packed_modules_mapping)`. Модуль, не прошедший проверку, пропускается в цикле `_create_lora_modules()` — без обёртки, без буферов и без записи в `self.modules`.

`is_in_target_modules()` умеет три вида совпадения:

1. суффикс имени модуля (последний сегмент после точки) есть в списке, либо полное имя модуля есть в списке;
2. модуль — «упакованный» родитель (`qkv_proj`, `gate_up_proj`), и в списке есть хотя бы один из его дочерних адаптерных имён (`q_proj`, `gate_proj`, …);
3. модуль — дочернее адаптерное имя, а в списке указан упакованный родитель.

Так что для модели с fused-QKV записи `q_proj` и `qkv_proj` дадут одинаковый результат — обёртка ставится на упакованный слой целиком, отдельно q, k и v не разделяются.

Проверка **не** влияет на `expected_lora_modules`, по которому `LoRAModel.from_local_checkpoint()` решает, не содержит ли адаптер лишних модулей: этот список строится из полного `supported_lora_modules` модели. Поэтому адаптер с весами на отфильтрованные модули грузится успешно, кладётся в CPU-кэш и частично не используется: `activate_adapter()` копирует веса только в те модули, что есть в `self.modules`.

## Значения и формат

- Несколько значений через пробел: `--lora-target-modules o_proj qkv_proj down_proj`.
- Регистр и точное имя важны: сравнение строгое, по множеству строк.
- Значения, которых нет в модели, не вызывают ошибку — они просто ни с чем не совпадут. Полностью «промахнувшийся» список даёт модель без единой LoRA-обёртки; поймать это можно только по неизменившимся ответам.
- Пустой список задать нельзя (`nargs="+"` требует хотя бы одно значение); «без ограничений» — это отсутствие аргумента.
- Литерал `None` принимается парсером (`optional_type`) и равнозначен отсутствию аргумента.

## Когда использовать

- Нужно урезать VRAM под LoRA на большой модели, и заранее известно, что адаптеры содержат веса только на подмножество модулей — тогда список ровно совпадает с содержимым адаптеров и потерь по качеству нет.
- Профилирование показывает, что LoRA-ядра на MLP-слоях дороже, чем выигрыш от них, и вы сознательно отключаете их (эксперимент, а не штатная настройка).
- Не используйте, чтобы «на всякий случай сузить»: неполное применение адаптера — не отказ, а тихая деградация качества.
- Не используйте как способ обслуживать адаптеры разной структуры одним инстансом: список общий для всех адаптеров процесса.

## Влияние на производительность и память

- **VRAM.** Единственный аргумент группы, который уменьшает число буферов, а не их размер. Экономия пропорциональна доле исключённых слоёв: убрать MLP-проекции у типовой decoder-модели — это убрать большую часть суммарного `input_size + output_size`, на которые множатся `max_loras × max_lora_rank`.
- **RAM хоста.** Не уменьшает: CPU-копия адаптера читается целиком, включая отфильтрованные модули.
- **Время старта.** Слегка сокращает: меньше подмен модулей и меньше аллокаций.
- **Throughput.** Меньше обёрнутых слоёв — меньше вызовов shrink/expand на каждый forward. Это и есть заявленный в справке «performance tuning».

## Взаимодействие с другими аргументами

- `--max-loras`, `--max-lora-rank`, `--lora-dtype`: задают размер одного буфера; этот аргумент задаёт их количество.
- `--fully-sharded-loras`: применяется к тем модулям, которые прошли фильтр.
- `--gpu-memory-utilization`: освобождённая память уходит в KV-cache.
- `--enable-lora`: без него аргумент игнорируется целиком.

## Типовые проблемы и диагностика

- **Симптом:** адаптер загружен, но ответы почти не отличаются от базовой модели. **Причина:** список не совпал ни с одним модулем либо совпал лишь с малой их частью. **Проверка:** `target_modules` в `adapter_config.json` адаптера против заданного списка; при уровне логирования debug в логе видны строки `Successfully loaded LoRA weights for module ...` только для обёрнутых модулей. **Лечение:** привести список в соответствие с содержимым адаптера или убрать аргумент.
- **Симптом:** качество с адаптером хуже, чем при запуске без этого аргумента. **Причина:** часть весов адаптера не применяется. **Лечение:** убрать фильтр либо расширить список.
- **Симптом:** при загрузке адаптера `While loading <dir>, expected target modules in {...} but received [...]. Please verify that the loaded LoRA module is correct`. **Причина:** это **не** про `--lora-target-modules`: адаптер содержит модуль, которого нет в модели вообще. **Лечение:** проверить, что адаптер обучен на этой базовой архитектуре.
- **Подтверждение принятого значения:** прямой строки в логе старта нет. Косвенно — падение потребления VRAM в строке `Available KV cache memory: X GiB` относительно запуска без аргумента при прочих равных.

## Примеры

```bash
vllm serve /models/Qwen3-4B --enable-lora --lora-target-modules o_proj --max-lora-rank 16
```

```bash
vllm serve /models/Qwen3-4B --enable-lora --lora-target-modules qkv_proj o_proj gate_up_proj down_proj --max-loras 2
```
