# --fail-on-environ-validation

## Кратко

vLLM конфигурируется двумя независимыми слоями: аргументами CLI и переменными окружения `VLLM_*`. Опечатка в аргументе ловится argparse немедленно, опечатка в имени переменной — нет: неизвестное имя просто игнорируется, и движок работает с дефолтом.

`--fail-on-environ-validation` закрывает эту дыру. При включенном флаге любая переменная с префиксом `VLLM_`, отсутствующая в реестре `vllm/envs.py`, приводит к `ValueError` на старте; при выключенном (дефолт) — только к предупреждению в логе.

## Оригинальная справка

```text
If set, the engine will raise an error if environment validation fails.
```

## Паспорт аргумента

- Флаги: `--fail-on-environ-validation`, `--no-fail-on-environ-validation`
- Группа argparse: без группы (объявлен напрямую в `EngineArgs.add_cli_args`)
- Тип значения: bool, `action=argparse.BooleanOptionalAction` — есть парная отключающая форма
- Допустимые значения: флаг присутствует, присутствует `--no-` форма, либо не задан
- Значение по умолчанию: `False` — только предупреждение
- Эффективное значение: не переопределяется
- Где объявлен: `vllm/engine/arg_utils.py:add_cli_args`
- Этап применения: самое начало `create_engine_config()` — до создания `ModelConfig`, до чтения конфигурации модели и до любой загрузки весов

## Что меняет в движке

`create_engine_config()` вызывает `envs.validate_environ(self.fail_on_environ_validation)` сразу после платформенного хука `pre_register_and_update()` и создания `DeviceConfig`. Сама проверка тривиальна:

```python
for env in os.environ:
    if env.startswith("VLLM_") and env not in environment_variables:
        if hard_fail:
            raise ValueError(f"Unknown vLLM environment variable detected: {env}")
        else:
            logger.warning("Unknown vLLM environment variable detected: %s", env)
```

Отсюда следуют границы применимости, которые важнее самого флага.

- Проверяется **только** префикс `VLLM_`. Опечатки в `HF_TOKEN`, `CUDA_VISIBLE_DEVICES`, `NCCL_*`, `TORCH_*` не ловятся ничем.
- Проверяется только **имя**, не значение. `VLLM_USE_FLASHINFER_SAMPLER=maybe` пройдет проверку и упадет позже, уже при чтении переменной.
- Реестр известных имен — словарь `environment_variables` в `vllm/envs.py`. Он меняется от релиза к релизу, поэтому переменная, корректная в одной версии, в другой может стать «неизвестной». Актуальный список конкретной сборки смотрится так: `python -c "import vllm.envs as e; print(dir(e))"` в том же окружении. Описание назначений — в `vllm/docs/configuration/env_vars.md`.
- Проверка выполняется в том процессе, который собирает `VllmConfig`, — то есть один раз на старте, а не в каждом worker'е.

## Значения и формат

- Голый флаг включает, `--no-fail-on-environ-validation` явно выключает.
- «Не задан» здесь означает именно `False`, а не «решит движок».
- Из YAML через `--config` работают оба варианта: `fail-on-environ-validation: true` и `false` (парная `--no-` форма зарегистрирована, поэтому `false` не теряется).

## Когда использовать

- **Включайте на управляемом сервере.** Переменные окружения инстанса задаются руками и входят в снимок запуска, по которому arriero определяет дрейф конфигурации; опечатка в имени превращается в тихое «настройка не применилась». Профиль vLLM в arriero прямо требует `VLLM_USE_FLASHINFER_SAMPLER=0` для квалифицированной сборки — молча не сработавшая переменная здесь стоит падения при старте на этапе JIT-компиляции сэмплера (`docs/VLLM_OPERATIONS.md`, arriero).
- Включайте при переносе конфигурации между версиями vLLM: флаг сразу покажет переменные, которые в новой версии переименовали или удалили.
- Не включайте, если в окружении процесса сознательно живут собственные переменные с префиксом `VLLM_` (например, для внешних скриптов или плагинов) — движок посчитает их неизвестными и откажет в старте. В этом случае префикс лучше сменить.

## Влияние на производительность и память

Один проход по `os.environ` при старте. На VRAM, throughput, latency и время загрузки модели не влияет.

## Взаимодействие с другими аргументами

Прямых связей с другими аргументами нет: слой переменных окружения отделен от слоя CLI, и ни один аргумент не задает и не отменяет переменную. Косвенно флаг защищает любую настройку, которая в vLLM управляется только окружением, — от выбора сэмплера и бэкендов до отключения UVA при выгрузке весов.

## Типовые проблемы и диагностика

- **Симптом:** `ValueError: Unknown vLLM environment variable detected: VLLM_USE_FLASHINFER_SAMLER`. **Причина:** опечатка в имени. **Лечение:** исправить имя; список допустимых — `python -c "import vllm.envs as e; print(dir(e))"`.
- **Симптом:** сервер стартует, но настройка из переменной окружения не действует, флаг не задан. **Проверка:** предупреждение `Unknown vLLM environment variable detected: <NAME>` в начале лога — его легко пропустить среди строк загрузки. **Лечение:** включить флаг, чтобы такие случаи становились ошибкой.
- **Симптом:** после обновления vLLM сервер перестал стартовать с этой ошибкой, хотя окружение не менялось. **Причина:** переменную удалили или переименовали в новой версии. **Лечение:** сверить имя с `vllm/docs/configuration/env_vars.md` установленной версии.
- **Симптом:** переменная задана верно по имени, но с бессмысленным значением, и флаг не помог. **Причина:** валидируются только имена. **Лечение:** проверять значения отдельно.
- **Подтверждение принятого значения:** отсутствие ошибки при заведомо неверном имени означает, что флаг не применился; для быстрой проверки достаточно запустить сервер с временной переменной `VLLM_DEFINITELY_NOT_A_REAL_VAR=1`.

## Примеры

```bash
vllm serve /models/Qwen3-4B --fail-on-environ-validation --gpu-memory-utilization 0.85
```

```bash
vllm serve /models/Qwen3-4B --no-fail-on-environ-validation --gpu-memory-utilization 0.85
```
