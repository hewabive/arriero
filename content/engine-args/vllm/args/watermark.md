# --watermark

## Кратко

Планировщик впускает запрос, если для него хватает свободных блоков. Ровно «хватает» — плохая политика: запрос заходит, через шаг блоков не хватает уже работающим, кто-то вытесняется, освободившиеся блоки тут же занимает следующий из очереди, и система входит в цикл вытеснений с пересчетом prefill.

`--watermark` вводит запас: при впуске **ожидающего или вытесненного** запроса требуется не просто «поместиться», а «поместиться, оставив свободными `watermark × общее число блоков`». Уже работающие запросы этот запас не видят и продолжают выделять блоки под decode.

## Оригинальная справка

```text
Fraction of total KV cache blocks to keep free (the watermark) when
admitting waiting or preempted requests into the running queue. This headroom
helps avoid frequent KV cache eviction and the resulting repeated preemption
of requests when GPU memory is scarce. Must be in the range [0.0, 1.0); 0.0
(the default) disables the watermark.
```

## Паспорт аргумента

- Флаги: `--watermark`
- Группа argparse: `SchedulerConfig`
- Тип значения: float (доля, не проценты)
- Допустимые значения: `[0.0, 1.0)` — валидация `ge=0.0, lt=1.0`; ровно `1.0` запрещено
- Значение по умолчанию: `Field(default=0.0, ge=0.0, lt=1.0)` — то есть `0.0` при указанных границах; `0.0` отключает механизм
- Эффективное значение: не переопределяется. В блоки пересчитывается один раз при создании `KVCacheManager`: `watermark_blocks = int(watermark × kv_cache_config.num_blocks)`
- Где объявлен: `vllm/config/scheduler.py:SchedulerConfig.watermark`
- Этап применения: конструктор `KVCacheManager` (пересчет в блоки) → каждое выделение блоков для waiting/preempted запроса

## Что меняет в движке

`KVCacheManager.allocate_slots()` (`vllm/v1/core/kv_cache_manager.py`) применяет запас условно:

```
watermark_blocks = 0
if has_scheduled_reqs and request.status in (WAITING, PREEMPTED):
    watermark_blocks = self.watermark_blocks
...
required_blocks = num_blocks_to_allocate + watermark_blocks
if required_blocks > available_blocks:
    return None
```

Три условия сразу:

1. запас применяется только к запросам в состоянии `WAITING` или `PREEMPTED` — то есть при **впуске**, а не при продолжении работы;
2. запас применяется только если в этом шаге уже есть запланированные запросы (`has_scheduled_reqs`). На пустом движке первый запрос впускается без запаса, иначе при большом watermark сервер не смог бы обслужить вообще ничего;
3. при включенном `--scheduler-reserve-full-isl` тот же `watermark_blocks` добавляется и к предварительной проверке «вся последовательность помещается».

Абсолютная величина считается от **общего** числа блоков KV-cache, известного после профилирования памяти, а не от свободного.

## Значения и формат

- Дробное число в `[0.0, 1.0)`. `0.05` — 5 % блоков остаются свободными при впуске.
- `0.0` — механизм выключен (значение по умолчанию); поведение полностью совпадает с версиями движка до появления флага.
- `1.0` и выше отвергаются валидацией; `0.9` формально допустимо, но означает, что впуск возможен лишь при 90 % свободного KV — сервер будет обрабатывать запросы фактически по одному.
- Реальная гранулярность — блоки: `int(watermark × num_blocks)`. При маленьком KV-cache значение вроде `0.001` может дать `0` блоков и не иметь эффекта.
- Осмысленный диапазон для практики — `0.01`–`0.1`.

## Когда использовать

- В логе стабильно растут `Preemptions: N`, `GPU KV cache usage` держится у 100 %, throughput ниже ожидаемого — классический thrashing. Запас в 2–5 % часто убирает большую часть вытеснений.
- Нагрузка с длинными ответами: decode постоянно докупает блоки, и без запаса каждый новый впуск отбирает память у работающих.
- Не используйте как замену `--gpu-memory-utilization`: watermark не добавляет памяти, а только резервирует часть уже имеющейся под сглаживание.
- Не завышайте: каждый процент запаса — это процент KV-cache, который никогда не используется под новые запросы.

## Влияние на производительность и память

- **VRAM.** Ничего не выделяет дополнительно; фиксированная доля уже выделенных блоков просто становится недоступной при впуске.
- **Эффективная конкурентность.** Снижается: часть блоков зарезервирована, поэтому одновременно работающих запросов будет чуть меньше.
- **Throughput.** При дефиците памяти растет за счет исчезновения пересчетов вытесненных prefill; при достатке памяти слегка падает.
- **TTFT.** Может вырасти: новый запрос ждет, пока свободных блоков станет достаточно с учетом запаса.
- **Время старта.** Не влияет.

## Взаимодействие с другими аргументами

- `--scheduler-reserve-full-isl`: работает в связке — запас добавляется и к проверке «вся входная последовательность помещается». Вместе они дают строгую политику впуска.
- `--gpu-memory-utilization`: определяет `num_blocks`, от которого доля и считается. Поднять utilization обычно полезнее, чем ставить большой watermark.
- `--max-num-seqs`: если очередь упирается в этот лимит, а не в память, watermark не даст ничего.
- `--max-model-len`, `--block-size`: определяют, сколько блоков нужно одному запросу, то есть цену запаса в запросах.
- `--enable-prefix-caching`: попадания в кэш уменьшают потребность в новых блоках и делают запас менее заметным.
- `--num-gpu-blocks-override`: перебивает результат профилирования; `watermark_blocks` считается уже от итогового числа блоков.
- `--scheduling-policy`: определяет, кто именно из ожидающих проверяется на запас первым.

## Типовые проблемы и диагностика

- **Симптом:** значение задано, ничего не изменилось. **Причина:** `int(watermark × num_blocks)` дал 0, либо запросы ограничены `--max-num-seqs`, а не памятью. **Проверка:** число блоков видно из строки `GPU KV cache size: N tokens` и `--block-size`. **Лечение:** увеличить долю или искать настоящее узкое место.
- **Симптом:** после включения watermark выросло `Waiting: N reqs`, а `GPU KV cache usage` перестал доходить до 100 %. **Причина:** ровно спроектированное поведение. **Лечение:** ничего, если `Preemptions` при этом упали; иначе снизить долю.
- **Симптом:** сервер обрабатывает по одному запросу. **Причина:** завышенная доля (0.5 и выше). **Лечение:** вернуть в диапазон 0.01–0.1.
- **Симптом:** вытеснения остались, несмотря на watermark. **Причина:** запас не применяется к уже работающим запросам, и дефицит возникает на этапе decode. **Лечение:** снижать `--max-num-seqs` или поднимать `--gpu-memory-utilization`.
- **Подтверждение принятого значения:** отдельной строки лога нет. Наблюдаемые следствия — поле `Preemptions: N` (появляется только при ненулевом счетчике), `GPU KV cache usage` в периодическом логе и счетчик `vllm:num_preemptions` в `/metrics`.

## Примеры

```bash
vllm serve /models/Qwen3-4B --watermark 0.05 --max-num-seqs 16 --gpu-memory-utilization 0.9
```

```bash
vllm serve /models/Qwen3-4B --watermark 0.02 --scheduler-reserve-full-isl --max-model-len 32768
```
