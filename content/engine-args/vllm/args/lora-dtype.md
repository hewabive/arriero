# --lora-dtype

## Кратко

Один тип на всю LoRA-подсистему: и на постоянные GPU-буферы слотов, и на CPU-копии загруженных адаптеров. Веса адаптера с диска приводятся к нему при загрузке (`tensor.to(device=..., dtype=...)`), независимо от того, в каком типе они лежали в safetensors.

Дефолт `auto` означает «взять `ModelConfig.dtype`», то есть тип базовой модели после всех её собственных доопределений.

## Оригинальная справка

```text
Data type for LoRA. If auto, will default to base model dtype.
```

## Паспорт аргумента

- Флаги: `--lora-dtype`
- Группа argparse: `LoRAConfig`
- Тип значения: строка из фиксированного перечня (объявлено как `torch.dtype | LoRADType`)
- Допустимые значения: `auto`, `float16`, `bfloat16`
- Значение по умолчанию: `auto`
- Эффективное значение: переопределяется в `LoRAConfig.verify_with_model_config()`, вызываемой из `VllmConfig.__post_init__`: при `auto` (и при `None`) поле становится равным `model_config.dtype`, иначе строка превращается в объект `torch.dtype` через `getattr(torch, ...)`. То есть после сборки конфига в поле всегда лежит настоящий `torch.dtype`, а не строка
- Где объявлен: `vllm/config/lora.py:LoRAConfig.lora_dtype`
- Этап применения: сборка `VllmConfig` (разрешение `auto`) → загрузка модели (выделение буферов) → загрузка каждого адаптера (приведение весов)

## Что меняет в движке

Значение читается в двух местах.

**Выделение буферов.** Все `torch.zeros(...)` в `create_lora_weights()` LoRA-обёрток создаются с `dtype=lora_config.lora_dtype`. Размер элемента определяет объём постоянно занятой VRAM: и `float16`, и `bfloat16` — по 2 байта, поэтому выбор между ними на объём не влияет.

**Загрузка адаптера.** `WorkerLoRAManager._load_adapter()` передаёт `dtype=self.lora_config.lora_dtype` в `LoRAModel.from_local_checkpoint()`, где каждый тензор `lora_a`/`lora_b` приводится к этому типу при переносе на CPU. Приведение выполняется до упаковки и до закрепления памяти.

Отдельного пути «квантованный адаптер» нет: если база квантована (например, в 4 бита), буферы LoRA всё равно живут в 16-битном типе.

## Значения и формат

- `auto` — наследовать `--dtype` базовой модели (сам он тоже может быть `auto` и разрешаться по конфигу модели).
- `float16` и `bfloat16` — принудительный тип. `float32` в перечне нет.
- Значение `None` на командной строке не принимается (поле не помечено `optional` в extract), но внутри конфига `None` обрабатывается наравне с `auto`.
- Несоответствие типа адаптера типу в этом флаге не является ошибкой: веса приводятся молча. Ошибкой это станет только по качеству — приведение `bfloat16` → `float16` теряет динамический диапазон.

## Когда использовать

- Оставляйте `auto` в подавляющем большинстве случаев: совпадение типов LoRA и базы — то, что нужно для корректного сложения выходов.
- Задавайте явно, если база загружена в тип, отличный от того, в котором обучался адаптер, и вы сознательно выбираете, какой из двух сохранить.
- Не используйте `float16` под базой в `bfloat16`, если веса адаптера содержат большие по модулю значения: диапазон `float16` уже, и получите переполнение в inf с последующим NaN в выходах.

## Влияние на производительность и память

- **VRAM.** Определяет размер элемента буферов слотов. Оба допустимых типа занимают 2 байта, поэтому смена значения объём не меняет — меняет только численное поведение.
- **RAM хоста.** Аналогично для CPU-копий адаптеров.
- **Время старта.** Приведение типа выполняется при загрузке каждого адаптера; на времени старта заметно только при большом `--lora-modules`.
- **Throughput.** Прямого влияния нет: ядра shrink/expand работают в том же 16-битном типе в обоих вариантах.

## Взаимодействие с другими аргументами

- `--dtype`: источник значения при `auto`. Если базовая модель разрешилась в `bfloat16`, а адаптеры обучены в `float16`, расхождение проявится именно здесь.
- `--max-loras`, `--max-lora-rank`: вместе с типом задают размер буферов (`max_loras × rank × размерность × 2 байта`).
- `--fully-sharded-loras`: меняет формы буферов, но не их тип.

## Типовые проблемы и диагностика

- **Симптом:** `argument --lora-dtype: invalid choice: 'float32'`. **Причина:** тип вне перечня. **Лечение:** `auto`, `float16` или `bfloat16`.
- **Симптом:** ответы с адаптером содержат `NaN`/пустые токены, без него модель работает. **Причина:** веса адаптера приведены к `float16` из `bfloat16` и переполнились. **Проверка:** `torch_dtype` в `adapter_config.json`/метаданных safetensors адаптера против `--dtype` базы. **Лечение:** привести оба к `bfloat16`.
- **Симптом:** качество с адаптером заметно хуже ожидаемого при отсутствии ошибок. **Причина:** молчаливое приведение типа. **Проверка:** та же. **Лечение:** согласовать `--dtype` и `--lora-dtype`.
- **Подтверждение принятого значения:** отдельной строки в логе нет; тип базовой модели печатается в стартовой сводке конфигурации (`dtype=...`), и при `auto` LoRA использует его.

## Примеры

```bash
vllm serve /models/Qwen3-4B --enable-lora --lora-dtype bfloat16 --max-lora-rank 32
```

```bash
vllm serve /models/Qwen3-4B --enable-lora --dtype bfloat16 --lora-dtype auto --lora-modules sql=/models/lora/sql
```
