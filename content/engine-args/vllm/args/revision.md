# --revision

## Кратко

`--revision` фиксирует, какую именно версию репозитория модели читает движок: конфиг, веса, generation config, pooling config, image-processor config. Без него берется версия по умолчанию (обычно `main`), то есть содержимое может измениться между двумя перезапусками одного и того же инстанса.

Для локального пути аргумент бесполезен — версионирование там ваше собственное.

## Оригинальная справка

```text
The specific model version to use. It can be a branch name, a tag name,
or a commit id. If unspecified, will use the default version.
```

## Паспорт аргумента

- Флаги: `--revision`
- Группа argparse: `ModelConfig`
- Тип значения: str или `None`
- Допустимые значения: имя ветки, имя тега или commit-хеш; парсером не ограничены
- Значение по умолчанию: `None`
- Эффективное значение: `ModelConfig.__post_init__` вызывает `resolve_revision(model, revision, hf_token)`, который через `HfApi.resolve_revision` превращает ветку/тег в commit-хеш — но только когда конфиг и веса берутся из того же репозитория, что и модель (`hf_config_path` и `model_weights` не указывают в сторону). Для локального пути и при `VLLM_USE_MODELSCOPE` шаг пропускается; при любой ошибке Hub возвращается исходное значение, и это пишется только в debug-лог
- Где объявлен: `vllm/config/model.py:ModelConfig.revision`
- Этап применения: сборка `ModelConfig` (разрешение ревизии, чтение конфигов) → загрузка весов

## Что меняет в движке

Разрешенное значение расходится по всем чтениям репозитория модели:

- `get_config(...)` — `config.json`/mistral-конфиг;
- `try_get_generation_config(...)` — `generation_config.json` (дефолты сэмплинга);
- `get_pooling_config(model, revision)` и `get_sentence_transformer_tokenizer_config(model, revision)` — конфигурация pooling-моделей;
- `get_hf_image_processor_config(model, revision=…)` — для мультимодальных моделей;
- `try_get_dense_modules(model, revision=…)` — размерность эмбеддингов;
- загрузчик весов — скачивание файлов нужного снапшота.

Смысл однократного разрешения проговорен в докстринге `resolve_revision`: это снимает повторные HTTP-запросы и защищает от гонки, когда ветка сдвигается прямо во время загрузки модели. Возвращаемое значение остается читаемым (`ResolvedRevision` ведет себя как исходная строка), поэтому сообщения об ошибках не превращаются в хеши.

Отдельно: `--revision` **не** управляет ревизией удаленного кода. За нее отвечает `--code-revision`, который передается в `AutoConfig.from_pretrained(code_revision=…)`.

## Значения и формат

- Ветка: `main`, `refs/pr/3`.
- Тег: `v1.0`.
- Коммит: полный SHA — единственная форма, которая действительно фиксирует содержимое.
- `None` — версия по умолчанию репозитория.
- Локальный путь в `--model` делает значение неэффективным: `resolve_revision` возвращает его как есть, а `from_pretrained` по каталогу ревизию не использует.

## Когда использовать

- Всегда при работе по идентификатору HF на управляемом сервере: без пина конфигурация инстанса не воспроизводима. В arriero пиннинг ревизии входит в квалификационный профиль (`docs/VLLM_OPERATIONS.md`).
- Обязательно вместе с `--trust-remote-code`: иначе исполняемый код репозитория может поменяться без вашего участия.
- Не задавайте, если модель уже лежит локально — это создаст ложное впечатление контроля версии.

## Влияние на производительность и память

На память не влияет. На время старта — один сетевой запрос к Hub при разрешении ревизии (пропускается офлайн и для локальных путей). Смена ревизии инвалидирует кеш скачанных файлов и вызывает повторную загрузку весов.

Косвенно значение может изменить всё остальное: другая ревизия — другой `config.json`, а значит другая производная длина контекста, другой `generation_config.json` и другие дефолты сэмплинга.

## Взаимодействие с другими аргументами

- `--model`: репозиторий, к которому относится ревизия.
- `--tokenizer-revision`: наследует это значение, если не задан явно.
- `--code-revision`: отдельная ось для удаленного кода; при `--trust-remote-code` пинить нужно обе.
- `--hf-config-path`: если конфиг берется из другого репозитория, ревизия модели не разрешается заранее.
- `--hf-token`: нужен для приватных репозиториев; передается и в разрешение ревизии.
- `--trust-remote-code`: делает пин ревизии вопросом безопасности, а не только воспроизводимости.

## Типовые проблемы и диагностика

- **Симптом:** ошибка Hub «Revision Not Found». **Причина:** ветки/тега/коммита нет в репозитории. **Лечение:** исправить значение.
- **Симптом:** поведение инстанса изменилось после перезапуска без правок конфигурации. **Причина:** ревизия не зафиксирована, ветка сдвинулась. **Лечение:** зафиксировать commit-хеш.
- **Симптом:** задан `--revision`, но в логах видно, что используется другая версия. **Причина:** конфиг или веса берутся из другого репозитория (`--hf-config-path`, объектное хранилище), поэтому предварительное разрешение ревизии не выполняется. **Проверка:** ветка `can_resolve_model_revision` в `ModelConfig.__post_init__`.
- **Симптом:** в офлайн-режиме модель не находится. **Причина:** в локальном кеше нет снапшота этой ревизии. **Лечение:** прогреть кеш онлайн либо перейти на локальный путь.
- **Симптом:** ревизия задана веткой, но разрешение молча не сработало. **Причина:** `resolve_revision` глотает любую ошибку Hub и пишет о ней только в debug. **Проверка:** запустить движок с `VLLM_LOGGING_LEVEL=DEBUG` и найти `Failed to resolve revision for …`.

```bash

```

```bash
vllm serve org/custom-model --revision 3f1c9d2ab4e5f6789012345678abcdef01234567 --code-revision 3f1c9d2ab4e5f6789012345678abcdef01234567 --trust-remote-code
```
