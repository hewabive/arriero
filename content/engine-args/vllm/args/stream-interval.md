# --stream-interval

## Кратко

Аргумент относится к группе `SchedulerConfig`, но планировщик его не читает: значение доходит до `OutputProcessor` (`vllm/v1/engine/output_processor.py`) и работает как буфер на стороне выдачи. Пока не накопилось `stream_interval` новых токенов, ответ клиенту не формируется.

Каждый отправленный кусок — это отдельное SSE-событие, детокенизация, сборка JSON и запись в сокет. На быстрой модели с большим числом одновременных потоков этот путь становится заметной долей CPU-времени процесса, и укрупнение кусков дает реальный выигрыш.

## Оригинальная справка

```text
The interval (or buffer size) for streaming in terms of token length.
A smaller value (1) makes streaming smoother by sending each token immediately,
while a larger value (e.g., 10) reduces host overhead and may increase throughput
by batching multiple tokens before sending.
```

## Паспорт аргумента

- Флаги: `--stream-interval`
- Группа argparse: `SchedulerConfig`
- Тип значения: int (токены)
- Допустимые значения: `>= 1` (валидация `Field(default=1, ge=1)`)
- Значение по умолчанию: `Field(default=1, ge=1)` — то есть `1` при минимуме `1`
- Эффективное значение: не переопределяется движком, но **может быть увеличено на уровне запроса**: `stream_interval` в теле запроса комбинируется как `max(запрос, движок)`, поэтому запрос вправе только загрубить стрим, но не сделать его мельче серверного значения
- Где объявлен: `vllm/config/scheduler.py:SchedulerConfig.stream_interval`
- Этап применения: HTTP-слой / обработка выхода, на каждом сформированном ответе

## Что меняет в движке

`AsyncLLM` передает значение в `OutputProcessor`, оттуда оно попадает в `RequestState.stream_interval`. В `RequestState.make_request_output()` при `stream_interval > 1` кусок отправляется, только если выполнено одно из трех условий:

1. запрос завершен (`finished`);
2. это самый первый отправляемый кусок (`sent_tokens_offset == 0`);
3. с прошлой отправки накопилось не меньше `stream_interval` выходных токенов.

В режиме `DELTA` (обычный стриминг OpenAI) при отправке берется срез `output_token_ids[sent_tokens_offset:]`, и `sent_tokens_offset` двигается вперед.

Нестримовые ответы (`RequestOutputKind.FINAL_ONLY`) аргументом не затрагиваются: они и так формируются один раз по завершении.

## Значения и формат

- Целое число, минимум 1. `0` и отрицательные отвергаются валидацией поля.
- `1` — поведение по умолчанию: каждый токен уходит отдельным событием; условие `stream_interval > 1` не выполняется, и весь буферизующий код не работает.
- `10` — типичное «крупное» значение из справки; на глаз это заметная, но еще приемлемая ступенчатость.
- Первый токен уходит всегда сразу, поэтому TTFT (время до первого токена) от значения не зависит — «рваным» становится только последующий поток.
- Значение в теле запроса (`stream_interval`, `>= 1`) не может опустить серверный порог: применяется `max(значение запроса, значение сервера)`.

## Когда использовать

- Высокая конкурентность быстрых потоков, где профиль показывает, что процесс упирается в CPU на детокенизации и сборке ответов: `4`–`10` заметно снижают эту нагрузку.
- Клиенты, которые все равно не рисуют текст потокенно (агенты, пайплайны, накопление в буфер): для них мелкий стрим — чистые накладные расходы.
- Не трогайте для интерактивного чата: ступенчатая выдача воспринимается как «подвисание», хотя суммарное время ответа не меняется.
- Не используйте как способ снизить сетевой трафик поверх прокси: экономия идет на числе событий, а не на объеме текста.

## Влияние на производительность и память

- **CPU хоста.** Основной эффект: меньше вызовов детокенизации, меньше сборок JSON, меньше записей в сокет. Пропорционально `1/stream_interval` для стримящих запросов.
- **Throughput.** Может слегка вырасти на нагрузке из многих быстрых потоков — освобожденное CPU-время достается циклу движка.
- **TTFT.** Не меняется: первый токен отправляется вне зависимости от порога.
- **Воспринимаемая плавность.** Ухудшается прямо пропорционально значению.
- **VRAM.** Не влияет: буферизуются уже готовые токены на стороне хоста.
- **Время старта.** Не влияет.

## Взаимодействие с другими аргументами

- `--max-num-seqs`: чем больше одновременных стримов, тем ощутимее выигрыш от укрупнения кусков.
- `--max-num-batched-tokens`: определяет темп генерации токенов, то есть как быстро набирается очередной кусок.
- `--async-scheduling`: снимает простой GPU между шагами; после этого узким местом чаще становится именно CPU-путь выдачи, где и помогает `--stream-interval`.
- `--enable-log-outputs`, `--return-tokens-as-token-ids`: другие настройки выдачи; на группировку кусков не влияют.
- В arriero стрим проходит через прокси (`docs/API_PROXY_FOUNDATION.md`): крупные куски означают меньше SSE-событий на всем тракте, включая запись трасс запросов.

## Типовые проблемы и диагностика

- **Симптом:** текст в UI появляется рывками по несколько слов. **Причина:** `--stream-interval` больше 1 (или клиент запросил большее значение). **Лечение:** вернуть `1`.
- **Симптом:** клиент прислал `"stream_interval": 1`, а стрим все равно крупный. **Причина:** серверное значение больше и побеждает: применяется `max(запрос, сервер)`. **Лечение:** менять серверное значение.
- **Симптом:** значение задано, но эффекта нет. **Причина:** запросы нестримовые — для `FINAL_ONLY` буферизация не применяется. **Проверка:** `"stream": true` в запросе.
- **Симптом:** ошибка валидации `stream_interval must be at least 1, got 0.` **Причина:** нулевое значение в теле запроса. **Лечение:** передавать `>= 1`.
- **Подтверждение принятого значения:** отдельной строки лога нет; наблюдаемое следствие — размер `delta` в SSE-событиях ответа.

## Примеры

```bash
vllm serve /models/Qwen3-4B --stream-interval 8 --max-num-seqs 64
```

```bash
vllm serve /models/Qwen3-4B --stream-interval 1 --max-num-seqs 8
```
