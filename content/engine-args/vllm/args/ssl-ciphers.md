# --ssl-ciphers

## Кратко

Значение уходит в `uvicorn.Config(ssl_ciphers=...)` и превращается в вызов `set_ciphers` у `SSLContext`. Это строка в синтаксисе OpenSSL, а не список.

Оригинальная справка прямо ограничивает область действия: TLS 1.2 и ниже. Наборы TLS 1.3 в OpenSSL настраиваются отдельным интерфейсом, и `set_ciphers` их не затрагивает — то есть на современном клиенте, договорившемся на TLS 1.3, аргумент ничего не изменит.

## Оригинальная справка

```text
SSL cipher suites for HTTPS (TLS 1.2 and below only).
Example: 'ECDHE-RSA-AES256-GCM-SHA384:ECDHE-RSA-CHACHA20-POLY1305'
```

## Паспорт аргумента

- Флаги: `--ssl-ciphers`
- Группа argparse: `Frontend`
- Тип значения: str, допускается `None`
- Допустимые значения: строка наборов OpenSSL, элементы через двоеточие
- Значение по умолчанию: `None` — используется значение по умолчанию uvicorn/OpenSSL
- Эффективное значение: не переопределяется vLLM; фактический набор определяется сборкой OpenSSL и системной политикой шифров
- Где объявлен: `vllm/entrypoints/openai/cli_args.py:FrontendArgs.ssl_ciphers`
- Этап применения: HTTP-слой, `serve_http()` → `uvicorn.Config(...).load()`

## Что меняет в движке

vLLM пробрасывает строку без разбора: `serve_http(..., ssl_ciphers=args.ssl_ciphers, ...)`. Валидация происходит внутри OpenSSL при построении контекста, то есть уже после инициализации движка.

Если строка не выбирает ни одного доступного набора, старт падает с `ssl.SSLError: No cipher can be selected`. Если строка выбирает наборы, которых нет у клиента, старт пройдет успешно, а клиенты будут получать ошибку рукопожатия — это заметно только под нагрузкой.

## Значения и формат

- Синтаксис OpenSSL: `ECDHE-RSA-AES256-GCM-SHA384:ECDHE-RSA-CHACHA20-POLY1305`, поддерживаются и групповые имена вроде `HIGH:!aNULL:!MD5`.
- Не задан — набор по умолчанию; для большинства развертываний это правильный выбор.
- Проверить, что фактически принимает сервер, можно внешними средствами (`openssl s_client -connect host:port -tls1_2 -cipher ...`), а не по логу vLLM: движок принятый список не печатает.

## Когда использовать

- Когда есть внешнее требование по набору шифров (комплаенс, корпоративная политика) и клиенты заведомо его поддерживают.
- Не используйте как «усиление безопасности наугад»: ошибочный список либо не меняет ничего (TLS 1.3), либо отсекает часть клиентов.
- Для управляемых инстансов arriero не применяется: TLS на самом инстансе не поддерживается, менеджер работает по `http://<host>:<port>` (`docs/API_PROXY_FOUNDATION.md`, arriero).

## Влияние на производительность и память

На память не влияет. Выбор шифра меняет стоимость рукопожатия и потоковой шифрации; на современных CPU с AES-NI разница между AES-GCM и ChaCha20 практически незаметна на фоне генерации токенов.

## Взаимодействие с другими аргументами

- `--ssl-certfile`, `--ssl-keyfile`: без включенного TLS значение не используется.
- `--ssl-cert-reqs`, `--ssl-ca-certs`: независимые настройки; шифры не влияют на проверку клиентских сертификатов.

## Типовые проблемы и диагностика

- **Симптом:** `ssl.SSLError: ('No cipher can be selected.',)` при старте. **Причина:** строка не выбрала ни одного доступного набора. **Лечение:** убрать аргумент или взять строку из примера в справке.
- **Симптом:** часть клиентов не может подключиться, остальные работают. **Причина:** список слишком узкий для старых клиентов. **Лечение:** расширить набор.
- **Симптом:** аргумент задан, а перечень договариваемых шифров не изменился. **Причина:** соединение идет по TLS 1.3, где `set_ciphers` не действует. **Проверка:** `openssl s_client -connect host:port` и строка `Protocol` в выводе.

## Примеры

```bash
vllm serve /models/Qwen3-4B --host 0.0.0.0 --ssl-certfile /etc/ssl/vllm/fullchain.pem --ssl-keyfile /etc/ssl/vllm/privkey.pem --ssl-ciphers 'ECDHE-RSA-AES256-GCM-SHA384:ECDHE-RSA-CHACHA20-POLY1305'
```

```bash
openssl s_client -connect 127.0.0.1:8000 -tls1_2 -cipher ECDHE-RSA-AES256-GCM-SHA384
```
