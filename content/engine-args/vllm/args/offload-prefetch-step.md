# --offload-prefetch-step

## Кратко

`--offload-prefetch-step` — единственный параметр prefetch-выгрузки, который стоит VRAM. Он задает две вещи сразу, и это одно и то же число: глубину опережения (`next_index = (index + step) % число_выгруженных_слоев`) и вместимость статического буферного пула (`slot_capacity = prefetch_step`).

Поэтому размен прямой: `step=1` — минимум памяти и минимум перекрытия; `step=3` — втрое больший пул и подкачка, стартующая на три выгруженных слоя раньше.

Значение имеет смысл только в prefetch-режиме: при `--offload-group-size 0` и при `--offload-backend uva` оно не читается.

## Оригинальная справка

```text
Number of layers to prefetch ahead.
Higher values hide more latency but use more GPU memory. Default is 1.
```

## Паспорт аргумента

- Флаги: `--offload-prefetch-step`
- Группа argparse: `OffloadConfig`
- Тип значения: int (число выгруженных слоев)
- Допустимые значения: `>= 0` по валидации поля (`ge=0`), но при активном prefetch дополнительно требуется `>= 1`
- Значение по умолчанию: `Field(default=1, ge=0)`, то есть `1`
- Эффективное значение: не переопределяется; не читается вне prefetch-режима
- Где объявлен: `vllm/config/offload.py:PrefetchOffloadConfig.offload_prefetch_step`
- Этап применения: `create_engine_config` (валидация) → `post_init()` в конце `load_model` (аллокация пула) → каждый forward

## Что меняет в движке

1. **Буферный пул.** В `PrefetchOffloader.post_init()` создается `StaticBufferPool(param_infos, slot_capacity=self.prefetch_step, device)`. Пул аллоцирует `slot_capacity` копий каждого уникального сочетания `(имя, форма, strides, dtype)` параметра. Так как выгруженные слои обычно однотипны, размер пула равен `prefetch_step × объем выгруженных параметров одного слоя`.
2. **Раздача слотов.** Каждый выгруженный слой получает `slot_idx = index % prefetch_step`, где `index` — порядковый номер среди выгруженных слоев. При `step=1` все выгруженные слои делят один слот.
3. **Опережение.** После forward выгруженного слоя вызывается `torch.ops.vllm.start_prefetch(output, next_index)` с `next_index = (index + prefetch_step) % len(module_offloaders)` — то есть подкачка запускается не для следующего выгруженного слоя, а для того, что через `step` позиций.
4. **Стартовый прогрев.** В конце `post_init()` запускается подкачка первых `min(prefetch_step, число_выгруженных_слоев)` слоев.
5. **Синхронизация.** `start_onload_to_static()` перед копированием форкает `copy_stream` от вычислительного потока — буфер нельзя перезаписывать, пока предыдущий владелец слота его читает. Отсюда и следует, что перекрытие возникает **только** когда между слоем-источником события и слоем-получателем буфера есть чужая работа.

Именно пункты 2 и 5 объясняют главное практическое правило: при подряд идущих выгруженных слоях (`--offload-num-in-group > 1`) шаг меньше `num_in_group` не дает перекрытия — второй слой пары ждет освобождения того же слота, который только что использовал первый.

## Значения и формат

- Целое число. Осмысленный минимум — `1`.
- `0` принимается валидацией поля, но при `--offload-group-size > 0` (или `--offload-backend prefetch`) отвергается конфигурационным валидатором: `offload_prefetch_step (0) must be >= 1 when prefetch offloading is enabled (offload_group_size > 0)`. Вне prefetch-режима ноль просто игнорируется.
- Верхней границы нет. Значение больше числа выгруженных слоев работает, но полезного эффекта не дает: подкачка идет по кругу по тому же списку, а пул продолжает расти линейно.
- Специальных значений (`auto`, `-1`) нет.

## Когда использовать

- Оставляйте `1` при `--offload-num-in-group 1`: одиночные выгруженные слои разнесены на `group_size − 1` обычных слоев, и одного слота хватает, чтобы копия шла параллельно их вычислению.
- Поднимайте до значения `--offload-num-in-group`, если выгружаете по нескольку подряд идущих слоев. Это минимальный шаг, при котором каждый слой пары/тройки получает собственный слот.
- Поднимайте выше, только если замер показывает, что подкачка все еще на критическом пути, и в VRAM есть свободное место — каждый шаг стоит еще одну копию слоя.
- Не увеличивайте «про запас»: пул аллоцируется до профилирования памяти и напрямую уменьшает KV-cache в рамках `--gpu-memory-utilization`.

## Влияние на производительность и память

- **VRAM.** Единственная составляющая prefetch-режима, которая занимает память на устройстве. Пул аллоцируется в `post_init()`, вызываемом в конце `load_model`, то есть попадает в измеренную профилированием «consumed memory» и вычитается из бюджета `--gpu-memory-utilization` до KV-cache. Фактическое число печатается как `Static buffer pool: Y GB`.
- **RAM хоста.** Не зависит от этого аргумента — в хосте лежит по одной копии каждого выгруженного параметра независимо от шага.
- **Latency.** Растущий шаг увеличивает окно, за которое можно спрятать копирование. Потолок эффекта — когда время передачи слоя становится меньше суммарного времени вычисления слоев, попадающих в окно; дальше повышение бесполезно.
- **Время старта.** Растет незначительно (аллокация пула и стартовые копии), плюс любое изменение поля меняет `OffloadConfig.compute_hash()` и вызывает перекомпиляцию модели.
- **CUDA graphs.** Совместимо: копии форкаются через события, `sync_prev_onload()` и `join_after_forward()` вызываются из обвязки захвата графов. Отдельный `--enforce-eager` для prefetch-режима не требуется.

## Взаимодействие с другими аргументами

- `--offload-num-in-group`: практическое требование `prefetch_step >= num_in_group`; иначе подряд идущие выгруженные слои конкурируют за один слот.
- `--offload-group-size`: включает режим; при нуле аргумент не читается.
- `--offload-backend`: значение действует только при `prefetch` (или `auto` с ненулевой группой).
- `--offload-params`: сужает набор параметров в слое и тем самым уменьшает размер одного слота — при узком фильтре можно позволить себе больший шаг.
- `--gpu-memory-utilization`: общий бюджет, из которого пул вычитается до KV-cache.
- `--enforce-eager`: не требуется; актуален для не-UVA запасного пути `--cpu-offload-gb`, а не здесь.

## Типовые проблемы и диагностика

- **Симптом:** `offload_prefetch_step (0) must be >= 1 when prefetch offloading is enabled (offload_group_size > 0)`. **Лечение:** задать 1 или больше.
- **Симптом:** после повышения шага упала емкость KV-cache и `Maximum concurrency`. **Причина:** буферный пул вырос линейно по шагу. **Проверка:** `Static buffer pool: Y GB` в строке `[PrefetchOffloader] Initialized ...` и `Available KV cache memory:` в логе профилирования. **Лечение:** вернуть шаг или понизить долю выгруженных слоев.
- **Симптом:** OOM на этапе аллокации буферов сразу после загрузки весов. **Причина:** пул не помещается. **Лечение:** снизить шаг, уменьшить `--offload-num-in-group`, сузить `--offload-params`.
- **Симптом:** шаг увеличен, а скорость не изменилась. **Причина:** передача уже перекрыта, узкое место в другом месте (например, в самой полосе PCIe при слишком большой доле выгруженных весов). **Лечение:** снизить долю выгрузки, а не наращивать шаг.
- **Подтверждение принятого значения:** `[PrefetchOffloader] Initialized N modules. Total GPU memory saved: X GB, Static buffer pool: Y GB (group_size=..., num_in_group=..., prefetch_step=K, mode=cpu)`.

## Примеры

```bash
vllm serve /models/Qwen3-4B --offload-group-size 8 --offload-num-in-group 1 --offload-prefetch-step 1
```

```bash
vllm serve /models/Qwen3-4B --offload-group-size 6 --offload-num-in-group 3 --offload-prefetch-step 3 --gpu-memory-utilization 0.9
```
