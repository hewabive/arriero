# --long-prefill-token-threshold

## Кратко

Chunked prefill режет промпт по остатку бюджета шага. Если бюджет 16384, а в очереди один запрос с промптом на 100 000 токенов, он честно возьмет все 16384 и на этом шаге ни один другой запрос prefill не начнет. `--long-prefill-token-threshold N` ограничивает вклад **одного** запроса в шаг числом `N`, оставляя остаток бюджета остальным.

Несмотря на формулировку справки («запрос считается длинным, если промпт длиннее этого числа»), в коде нет отдельной категории «длинных» запросов: значение работает как безусловный потолок `num_new_tokens` на запрос на шаг.

## Оригинальная справка

```text
For chunked prefill, a request is considered long if the prompt is
longer than this number of tokens. 0 disables the cap (default).
```

## Паспорт аргумента

- Флаги: `--long-prefill-token-threshold`
- Группа argparse: `SchedulerConfig`
- Тип значения: int (токены)
- Допустимые значения: `>= 0` (валидация `Field(default=0, ge=0)`) и дополнительно `<= max_model_len` (проверка `verify_max_model_len`)
- Значение по умолчанию: `Field(default=0, ge=0)` — то есть `0` при минимуме `0`; `0` означает «ограничения нет»
- Эффективное значение: не подбирается автоматически, но принудительно сбрасывается в `0` для encoder-decoder моделей в `SchedulerConfig.__post_init__` (там же выключается chunked prefill)
- Где объявлен: `vllm/config/scheduler.py:SchedulerConfig.long_prefill_token_threshold`
- Этап применения: валидация `SchedulerConfig` → планировщик, на каждом шаге

## Что меняет в движке

В `Scheduler.schedule()` порог применяется в двух местах — к запросам из running-очереди (незавершенные prefill-куски) и к новым запросам из waiting-очереди — одинаковым образом:

```
if 0 < long_prefill_token_threshold < num_new_tokens:
    num_new_tokens = long_prefill_token_threshold
```

Обрезание происходит **до** зажима остатком бюджета (`min(num_new_tokens, request_token_budget)`), поэтому порог действует как дополнительная, более узкая граница. Для decode-запросов он не наблюдаем: там `num_new_tokens` равен 1 (плюс спекулятивные токены).

Третье место — `_mamba_block_aligned_split`: при block-aligned разрезе для Mamba/SSM-моделей верхняя граница куска считается как `min(max_num_scheduled_tokens, long_prefill_token_threshold)`, если порог задан.

## Значения и формат

- Целое число токенов, минимум 0.
- `0` — ограничение выключено (условие `0 < threshold` не выполняется). Это значение по умолчанию.
- Значение больше `--max-model-len` отвергается на старте: `long_prefill_token_threshold (N) cannot be greater than the max_model_len (M).`
- Значение больше `--max-num-batched-tokens` формально допустимо, но бессмысленно — реальным ограничителем останется бюджет шага.
- Осмысленный диапазон — доля бюджета шага: например, `2048` при `--max-num-batched-tokens 8192` гарантирует, что один запрос не займет больше четверти итерации.

## Когда использовать

- Смешанная нагрузка, где рядом живут длинные разовые запросы (документы, RAG-контексты) и интерактивные диалоги: без порога первый же длинный промпт заметно портит ITL остальным.
- Когда нужно, чтобы несколько prefill стартовали параллельно, а не строго по очереди: порог позволяет впустить два-три запроса в один шаг.
- Не используйте на однородной нагрузке: порог всегда стоит времени — общий TTFT длинного промпта растет пропорционально числу дополнительных шагов.
- Не используйте как защиту от переполнения памяти: за это отвечают `--max-model-len`, `--max-num-seqs` и `--scheduler-reserve-full-isl`.

## Влияние на производительность и память

- **TTFT длинного запроса.** Растет: промпт длиной `L` требует не менее `ceil(L / N)` шагов независимо от свободного бюджета.
- **ITL остальных запросов.** Улучшается и стабилизируется — ради этого порог и вводят.
- **Throughput.** Обычно слегка падает: шаги дробятся мельче, накладные расходы на итерацию растут.
- **VRAM.** Прямого влияния нет. Косвенное — запрос дольше остается в состоянии prefill и дольше удерживает уже выделенные KV-блоки.
- **Время старта.** Не влияет.

## Взаимодействие с другими аргументами

- `--enable-chunked-prefill`: без chunked prefill порог не наблюдаем — планировщик и так не режет промпт, а просто ждет, пока тот поместится целиком.
- `--max-num-batched-tokens`: общий бюджет шага; порог имеет смысл только как его доля.
- `--max-num-scheduled-tokens`: второй потолок планировщика, с которым порог комбинируется в Mamba-разрезе.
- `--max-model-len`: жесткая верхняя граница значения.
- `--max-num-seqs`: определяет, сколько запросов вообще могут одновременно претендовать на бюджет, освобожденный порогом.
- `--prefill-schedule-interval`: решает, **когда** впускать prefill; порог решает, **насколько крупным** будет кусок. Это ортогональные механизмы.

## Типовые проблемы и диагностика

- **Симптом:** `long_prefill_token_threshold (65536) cannot be greater than the max_model_len (32768).` **Лечение:** снизить порог или поднять `--max-model-len`.
- **Симптом:** значение задано, но поведение не изменилось. **Причина:** chunked prefill выключен, либо порог больше фактического остатка бюджета шага, либо нагрузка состоит из коротких промптов. **Проверка:** строка `Chunked prefill is enabled with max_num_batched_tokens=N.` при старте.
- **Симптом:** резко вырос TTFT на длинных документах. **Причина:** слишком маленький порог. **Лечение:** поднять до 1/2–1/4 бюджета шага.
- **Симптом:** `Waiting: N reqs` не уменьшается при свободном GPU. **Причина:** порог занижен настолько, что шаг не успевает продвигать очередь. **Лечение:** увеличить порог или бюджет шага.
- **Подтверждение принятого значения:** отдельной строки лога нет; наблюдаемое следствие — размер вклада запроса в шаг, видимый при `--enable-logging-iteration-details`.

## Примеры

```bash
vllm serve /models/Qwen3-4B --enable-chunked-prefill --max-num-batched-tokens 8192 --long-prefill-token-threshold 2048
```

```bash
vllm serve /models/Qwen3-4B --max-model-len 32768 --max-num-batched-tokens 16384 --long-prefill-token-threshold 4096 --max-num-seqs 16
```
