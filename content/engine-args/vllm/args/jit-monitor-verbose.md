# --jit-monitor-verbose

## Кратко

Без этого флага монитор JIT-компиляций пишет одно предупреждение на уникальное имя ядра: `logger.warning_once` кэширует пару «сообщение + аргументы», и повторные компиляции того же ядра с другой формой входа молча теряются. Из-за этого по умолчанию невозможно понять, компилируется ядро один раз или сотню.

Флаг меняет две вещи сразу: предупреждение печатается на каждое событие и содержит расшифровку параметров компиляции Triton — значения constexpr, сигнатуру типов и ключ кэша.

## Оригинальная справка

```text
Log every monitored JIT compile with runtime details. This can emit many
logs and add overhead, so it is intended for debugging.
```

## Паспорт аргумента

- Флаги: `--jit-monitor-verbose`, `--no-jit-monitor-verbose`
- Группа argparse: `ObservabilityConfig`
- Тип значения: bool (`argparse.BooleanOptionalAction`)
- Допустимые значения: флаг без значения; выключается парной формой из списка выше
- Значение по умолчанию: `false`
- Эффективное значение: не переопределяется; при `--jit-monitor-mode error` практического эффекта почти нет — там первое же событие поднимает `RuntimeError` и до второго дело не доходит
- Где объявлен: `vllm/config/observability.py:ObservabilityConfig.jit_monitor_verbose`
- Этап применения: конец прогрева воркера (передаётся в `jit_monitor.activate`) → каждое событие компиляции во время обслуживания

## Что меняет в движке

**Ветвление обработчика.** В `_handle_jit_event()` при `mode == "warn"` выбор такой: с флагом — `logger.warning(message, *args)` на каждое событие, без флага — `logger.warning_once(message, *args)` с кэшированием по аргументам.

**Детали Triton.** `_log_triton_jit_compile()` при включённом флаге вызывает `_format_verbose_triton_compile_details(kwargs)` и приписывает к сообщению строку вида

```text
constexprs={...}; signature={...}; extra_compile_info={...}; key=...
```

- `constexprs` — значения constexpr-параметров, где числовые индексы заменены на имена параметров ядра (`_constant_name` сопоставляет их с `jit_function.params`);
- `signature` — карта типов аргументов;
- `extra_compile_info` — остальные поля блока `compile`, кроме `constants`, `signature`, `key`, `fn`, `name`;
- `key` — ключ кэша компиляции.

Каждое значение прогоняется через `_safe_repr` с обрезкой до 120 символов, поэтому длинные repr'ы усекаются.

Для CuTeDSL и TileLang формируются свои строки деталей; общий формат сообщения тот же.

**Побочная защита.** При установке хука монитор оборачивает `triton.runtime.jit.serialize_specialization_data` так, чтобы `TypeError`/`ValueError` при сериализации несериализуемых constexpr'ов не роняли компиляцию, а возвращали `None`. Это происходит независимо от verbose.

## Значения и формат

- Значение по умолчанию `false`; «не задан» и `--no-jit-monitor-verbose` эквивалентны.
- Градаций детализации нет: либо полная расшифровка на каждое событие, либо одно предупреждение на имя ядра.
- Уровень сообщений в обоих случаях `WARNING`, то есть флаг не требует поднимать уровень логирования.

## Когда использовать

- Монитор уже сообщил о поздней компиляции, и нужно понять, какая форма входа её вызывает: `constexprs` и `signature` показывают конкретные размеры блоков и типы.
- Нужно оценить масштаб: одно предупреждение в дедуплицированном режиме может скрывать десятки реальных компиляций.
- Не включайте в эксплуатации: справка прямо называет флаг отладочным, а поток предупреждений на нагрузке с разнородными формами будет непрерывным.
- Не включайте вместе с `--jit-monitor-mode error`: движок умрёт на первом событии, и подробности вы получите ровно один раз — их и так печатает текст исключения.

## Влияние на производительность и память

- **CPU.** Форматирование деталей выполняется только в момент реальной компиляции ядра, то есть в редких событиях. Но сама компиляция уже является скачком latency, и форматирование добавляется к нему.
- **Диск.** Основной риск: без дедупликации каждое событие даёт длинную строку. На нагрузке, где ядра компилируются постоянно (много разных форм), лог растёт быстро.
- **VRAM, RAM хоста.** Не влияет.
- **Latency.** Косвенно: запись длинных предупреждений идёт из процесса воркера синхронно.

## Взаимодействие с другими аргументами

- `--jit-monitor-mode`: определяет саму реакцию; verbose влияет только на ветку `warn`.
- `--compilation-config`, `--cudagraph-capture-sizes`, `--max-cudagraph-capture-size`: то, что обычно и правят по полученным деталям, чтобы прогрев покрыл нужные формы.
- `--enforce-eager`: убирает torch.compile и CUDA graph, но Triton-ядра остаются, поэтому детали по-прежнему полезны.
- Переменная окружения `TRITON_PRINT_AUTOTUNING=0` подавляет отдельный поток сообщений автотюнинга, который монитор включает при активации.

## Типовые проблемы и диагностика

- **Симптом:** нужно понять причину скачков latency, а в логе одно старое предупреждение о компиляции. **Причина:** дедупликация `warning_once`. **Лечение:** включить этот флаг на время наблюдения.
- **Симптом:** после включения лог заполняется предупреждениями с одинаковым именем ядра, но разными `constexprs`. **Причина:** ядро компилируется под каждую новую форму входа. **Лечение:** расширить набор захватываемых размеров, чтобы формы попадали в прогретые.
- **Симптом:** в `constexprs` вместо имён параметров печатаются кортежи-пути. **Причина:** `_constant_name` не смог сопоставить путь с параметрами ядра. **Лечение:** ориентироваться на `signature` и `key`.
- **Симптом:** значения в деталях обрываются многоточием. **Причина:** `_safe_repr` усекает до 120 символов. **Лечение:** ожидаемое поведение.
- **Подтверждение принятого значения:** отдельной строки нет; в логе старта режим монитора печатается как `Kernel JIT monitor activated; monitored JIT compilations during inference will use mode=warn.`, а действие флага видно по появлению суффикса с `constexprs=...` в предупреждениях.

## Примеры

```bash
vllm serve /models/Qwen3-4B --jit-monitor-verbose --jit-monitor-mode warn
```

```bash
vllm serve /models/Qwen3-4B --jit-monitor-verbose --enforce-eager --max-num-seqs 1
```
