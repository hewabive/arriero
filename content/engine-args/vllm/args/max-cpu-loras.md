# --max-cpu-loras

## Кратко

Разделение двухуровневое: `--max-loras` — сколько адаптеров одновременно лежит в GPU-буферах, `--max-cpu-loras` — сколько адаптеров вообще зарегистрировано в менеджере и хранится в RAM хоста. Всё, что не поместилось в CPU-кэш, вытесняется по LRU и при следующем обращении читается с диска заново.

Память под этот кэш не преаллоцируется: она растёт по мере фактической загрузки адаптеров, размером в реальные веса каждого адаптера, а не в слот `max_lora_rank`.

## Оригинальная справка

```text
Maximum number of LoRAs to store in CPU memory. Must be >= than
`max_loras`.
```

## Паспорт аргумента

- Флаги: `--max-cpu-loras`
- Группа argparse: `LoRAConfig`
- Тип значения: int, допускающий `None` (`optional_type(int)`, литерал `None` принимается на командной строке)
- Допустимые значения: не ограничены сверху; ограничение снизу — «не меньше `max_loras`» — проверяется валидатором конфига, а не парсером
- Значение по умолчанию: `null` (`None`)
- Эффективное значение: переопределяется дважды. В `create_engine_config()` значение подставляется только если оно истинно и `> 0` — иначе передаётся `None`; затем `LoRAConfig._validate_lora_config` при `None` присваивает `max_cpu_loras = max_loras`. То есть `0` и отрицательные значения молча означают «равно `--max-loras`»
- Где объявлен: `vllm/config/lora.py:LoRAConfig.max_cpu_loras`
- Этап применения: сборка `VllmConfig` (валидация и подстановка) → регистрация адаптеров в менеджере

## Что меняет в движке

`LoRAModelManager.capacity` возвращает `max_cpu_loras` и задаёт ёмкость LRU-кэша `_registered_adapters`. В этот кэш попадает объект `LoRAModel`, чьи тензоры загружены с `device="cpu"` и, если доступна закреплённая память (`PIN_MEMORY`), переведены в pinned-память после упаковки весов — это ускоряет последующее асинхронное копирование в GPU-слот.

`LRUCacheWorkerLoRAManager.add_adapter()` работает в строгом порядке: сначала новый адаптер читается с диска и валидируется, затем удаляется одноимённая старая запись, затем, если `len(manager) + 1 > capacity`, вытесняется самый старый адаптер, и только потом новый добавляется в кэш и активируется. Из-за этого порядка число загруженных адаптеров кратковременно может превысить `--max-cpu-loras` на единицу — это отмечено комментарием в самом коде.

Вытеснение из CPU-кэша (`_on_remove`) деактивирует адаптер и в GPU-слотах. Обратной подкачки «из CPU в GPU без переоткрытия файла» отдельного механизма нет: активация берёт веса из зарегистрированной CPU-копии, а если её вытеснили — адаптер читается с диска целиком.

## Значения и формат

- Целое. `None` (не задан) ⇒ равен `--max-loras`.
- `0` и отрицательные значения не отвергаются: условие `if self.max_cpu_loras and self.max_cpu_loras > 0` в `create_engine_config()` превращает их в `None`, то есть в то же «равен `--max-loras`». Это единственный аргумент группы, где неверное значение не приводит к ошибке.
- Значение меньше `--max-loras` (но больше 0) — ошибка старта: `max_cpu_loras (N) must be >= max_loras (M).`
- Верхняя граница определяется свободной RAM хоста, движком не проверяется.

## Когда использовать

- Адаптеров больше, чем GPU-слотов, и переключение между ними частое: держите в CPU-кэше весь рабочий набор, чтобы смена активного адаптера не превращалась в чтение с диска.
- Статический набор через `--lora-modules`: задайте `--max-cpu-loras` не меньше числа записей в списке, иначе часть адаптеров, загруженных на старте, будет вытеснена ещё до первого запроса.
- Не трогайте, если адаптер один: дефолтная подстановка (`= --max-loras`) уже верна.
- Не завышайте на десятки при крупных адаптерах: это чистая RAM хоста, и в arriero она входит в ручной host-резерв инстанса.

## Влияние на производительность и память

- **RAM хоста.** Основной эффект. Верхняя граница — `max_cpu_loras × размер весов одного адаптера`; фактический размер — сумма по реально загруженным. Веса при возможности закрепляются (pinned), то есть эта память не свопится и учитывается ядром как заблокированная.
- **VRAM.** Не влияет: GPU-слоты задаёт `--max-loras`.
- **Время старта.** Не влияет напрямую; влияет длина `--lora-modules` — каждый статический адаптер грузится синхронно.
- **Latency.** Промах CPU-кэша означает повторное чтение и разбор safetensors адаптера в горячем пути запроса — на десятки-сотни миллисекунд дороже, чем активация из уже зарегистрированной копии.

## Взаимодействие с другими аргументами

- `--max-loras`: нижняя граница и одновременно значение по умолчанию.
- `--lora-modules`: число статических адаптеров имеет смысл держать `<= --max-cpu-loras`.
- `--lora-dtype`: определяет, в каком типе хранятся CPU-копии, и тем самым их размер.
- `--max-lora-rank`: на размер CPU-копий не влияет (там лежат реальные веса адаптера), влияет только на GPU-слот.

## Типовые проблемы и диагностика

- **Симптом:** `ValueError: max_cpu_loras (2) must be >= max_loras (4).` **Причина:** CPU-кэш меньше числа GPU-слотов. **Лечение:** поднять значение или снизить `--max-loras`.
- **Симптом:** `--max-cpu-loras 0` не даёт ожидаемого «отключить кэш». **Причина:** `0` трактуется как «не задано» и превращается в `--max-loras`. **Лечение:** отключить кэш нельзя, это не предусмотренный режим.
- **Симптом:** первый запрос к «редкому» адаптеру стабильно медленнее остальных. **Причина:** адаптер вытеснен из CPU-кэша и читается с диска. **Проверка:** строка `Loaded new LoRA adapter: name '...', path '...'` появляется в логе повторно для уже виденного адаптера. **Лечение:** поднять `--max-cpu-loras` до размера рабочего набора.
- **Симптом:** рост RSS процесса движка при переборе адаптеров. **Причина:** заполняется CPU-кэш вплоть до ёмкости. **Лечение:** снизить значение либо увеличить host-резерв инстанса.
- **Подтверждение принятого значения:** прямой строки в логе нет; косвенно — отсутствие повторных `Loaded new LoRA adapter` для адаптеров рабочего набора.

## Примеры

```bash
vllm serve /models/Qwen3-4B --enable-lora --max-loras 2 --max-cpu-loras 8
```

```bash
vllm serve /models/Qwen3-4B --enable-lora --max-loras 2 --max-cpu-loras 4 --lora-modules sql=/models/lora/sql chat=/models/lora/chat
```
