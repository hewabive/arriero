# --enable-server-load-tracking

## Кратко

Флаг заводит в состоянии приложения целочисленный счетчик, который увеличивается на входе в обработчик инференс-запроса и уменьшается после того, как ответ полностью отдан. Значение читается через `GET /load`.

Ловушка в том, что маршрут `/load` регистрируется всегда. Без флага он отвечает `{"server_load": 0}` — балансировщик, настроенный на этот эндпоинт, будет считать сервер вечно свободным.

## Оригинальная справка

```text
If set to True, enable tracking server_load_metrics in the app state.
```

## Паспорт аргумента

- Флаги: `--enable-server-load-tracking`, `--no-enable-server-load-tracking`
- Группа argparse: `Frontend`
- Тип значения: bool (`argparse.BooleanOptionalAction`)
- Допустимые значения: флаг присутствует (`true`), парный `--no-...` или отсутствие обоих (`false`)
- Значение по умолчанию: `false`
- Эффективное значение: для CPU-only render-сервера значение принудительно `False` (`init_render_app_state`)
- Где объявлен: `vllm/entrypoints/openai/cli_args.py:BaseFrontendArgs.enable_server_load_tracking`
- Этап применения: инициализация состояния API-сервера → HTTP-слой, декоратор на инференс-обработчиках

## Что меняет в движке

`init_app_state` записывает `state.enable_server_load_tracking` и `state.server_load_metrics = 0`. Декоратор `load_aware_call` (`vllm/entrypoints/serve/utils/api_utils.py`) навешен на инференс-обработчики независимо от флага и первым делом проверяет его: при выключенном — просто вызывает обработчик.

При включенном флаге счетчик увеличивается до вызова и уменьшается:

- сразу, если обработчик бросил исключение;
- сразу, если результат не `JSONResponse`/`StreamingResponse`;
- иначе — фоновой задачей `decrement_server_load`, которая выполняется после того, как ответ (в том числе весь SSE-поток) доставлен.

Именно поэтому счетчик отражает «запросы, по которым ответ еще не дописан», а не «последовательности в батче движка».

Список учитываемых маршрутов перечислен в самом обработчике `/load` (`vllm/entrypoints/serve/instrumentator/basic.py`): Responses (включая отмену), Anthropic `/v1/messages`, чат и completions, транскрипция/перевод, embeddings, pooling, classify, score и все варианты rerank.

## Значения и формат

- Включение: `--enable-server-load-tracking`. Выключение: `--no-enable-server-load-tracking`.
- «Не задан» = `false`.
- Ответ эндпоинта: `{"server_load": <целое>}`. Никакой другой размерности (очередь, слоты, токены) там нет.
- Счетчик не персистентный: перезапуск обнуляет его.

## Когда использовать

- Внешний балансировщик распределяет запросы по нескольким инстансам по числу активных запросов, а не round-robin.
- Нужна дешевая проверка «есть ли сейчас работа» из скрипта — например, перед плановой остановкой инстанса.
- Не используйте как метрику насыщения: `/load` не различает запрос в очереди и запрос, генерирующий токены; для этого есть `/metrics` (`vllm:num_requests_running`, `vllm:num_requests_waiting`).
- Не оставляйте `/load` в схеме балансировки, если флаг выключен: постоянный ноль хуже отсутствия метрики.

## Влияние на производительность и память

Стоимость — инкремент/декремент целого числа и одна фоновая задача на запрос. На VRAM, KV-cache, время старта и throughput не влияет. Счетчик хранится в состоянии одного процесса API-сервера: при `--api-server-count > 1` каждый процесс считает только свои запросы, и агрегировать их придется снаружи.

## Взаимодействие с другими аргументами

- `--max-num-seqs`: определяет, сколько запросов реально исполняется одновременно; превышение `server_load` над этим числом означает очередь.
- `--enable-per-request-metrics`: дает `queue_time_ms` по каждому запросу — точный ответ на тот же вопрос, но постфактум.
- `--disable-access-log-for-endpoints`: частый сосед, если балансировщик опрашивает `/load` часто и засоряет access-лог.

## Типовые проблемы и диагностика

- **Симптом:** `/load` всегда возвращает 0 под нагрузкой. **Причина:** флаг выключен. **Проверка:** строка `non-default args: {...}` в логе старта. **Лечение:** включить флаг.
- **Симптом:** счетчик не возвращается к нулю после отмены стрима клиентом. **Причина:** фоновая задача уменьшения выполняется по завершении доставки ответа; при разорванном соединении это происходит после того, как сервер закончит поток. **Проверка:** `vllm:num_requests_running` в `/metrics`. **Лечение:** ориентироваться на `/metrics` как на источник истины о работе движка.
- **Симптом:** сумма по инстансам не сходится с числом запросов. **Причина:** несколько процессов API-сервера, у каждого свой счетчик. **Лечение:** суммировать по процессам либо использовать `/metrics`.
- **Подтверждение принятого значения:** `curl http://127.0.0.1:8000/load` во время активной генерации возвращает ненулевое значение.

## Примеры

```bash
vllm serve /models/Qwen3-4B --enable-server-load-tracking --max-num-seqs 8
```

```bash
vllm serve /models/Qwen3-4B --enable-server-load-tracking --disable-access-log-for-endpoints /load,/health
```
