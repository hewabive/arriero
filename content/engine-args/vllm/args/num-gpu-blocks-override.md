# --num-gpu-blocks-override

## Кратко

Аргумент подменяет `num_blocks`, вычисленное из профилированной памяти, заданным числом. Собственная docstring поля не скрывает назначения: «Used for testing preemption».

Это последняя ступень в цепочке «бюджет памяти → байты под KV-cache → число блоков»: она перебивает и `--gpu-memory-utilization`, и `--kv-cache-memory-bytes`, потому что действует уже после них.

## Оригинальная справка

```text
Number of GPU blocks to use. This overrides the profiled `num_gpu_blocks`
if specified. Does nothing if `None`. Used for testing preemption.
```

## Паспорт аргумента

- Флаги: `--num-gpu-blocks-override`
- Группа argparse: `CacheConfig`
- Тип значения: int (число блоков, не токенов и не байт)
- Допустимые значения: не ограничены списком; дополнительно принимается литерал `None` (и пустая строка)
- Значение по умолчанию: `None` — переопределения нет
- Эффективное значение: применяется как есть; при этом `get_kv_cache_configs` пересчитывает и «доступную память» под это число блоков, чтобы auto-fit и проверки исходили из той же емкости
- Где объявлен: `vllm/config/cache.py:CacheConfig.num_gpu_blocks_override`
- Этап применения: сборка KV-cache-конфигурации после профилирования (`get_kv_cache_configs` / `get_num_blocks`)

## Что меняет в движке

`may_override_num_blocks(vllm_config, num_blocks)` возвращает заданное число вместо вычисленного везде, где число блоков выводится из доступной памяти. Чтобы остальная логика не работала с рассогласованными величинами, `get_kv_cache_configs` дополнительно **пересчитывает** `available_memory`:

```
bytes_per_block = _pool_bytes_per_block(vllm_config, groups)
available_memory = override × bytes_per_block
```

и пишет в лог `Overriding num_gpu_blocks=%d with num_gpu_blocks_override=%d`, где первое число — то, что получилось бы из профилирования. После этого на пересчитанной емкости работают и auto-fit `max_model_len` (при `--max-model-len -1`), и проверка «хватает ли памяти на один запрос максимальной длины», и построение конфигурации каждого worker'а.

Итоговое число попадает в `cache_config.num_gpu_blocks`, в block pool (`BlockPool(num_gpu_blocks=...)`) и в планировщик, который на старте требует `num_gpu_blocks > 0`.

Обратите внимание: переопределение **не уменьшает** фактически зарезервированную под инстанс VRAM, которая определяется `--gpu-memory-utilization`. Оно уменьшает (или увеличивает) только размер аллоцируемых тензоров KV-cache.

## Значения и формат

- Целое число блоков. Токенов в блоке — `--block-size`, поэтому емкость в токенах равна `num_gpu_blocks × block_size` для однородной модели; для гибридных моделей это соотношение неверно, и правильный ответ печатает строка `GPU KV cache size: N tokens`.
- `None` или пустая строка — отключить переопределение.
- Слишком маленькое значение приводит к отказу старта на проверке «влезает ли один запрос длиной `max_model_len`».
- Значение больше того, что помещается в реальную память, приведет к OOM при аллокации KV-cache: проверки на верхнюю границу здесь нет.

## Когда использовать

- Для воспроизведения вытеснений (preemption) и отладки поведения планировщика под давлением: искусственно маленький пул — самый прямой способ.
- Для сравнения конфигураций при строго одинаковой емкости KV-cache, когда профилирование дает разные числа от прогона к прогону.
- **Не используйте в продакшене** как способ ограничить память: для этого есть `--gpu-memory-utilization` (доля) и `--kv-cache-memory-bytes` (байты), и оба они согласованы с профилированием.
- Не используйте вместе с arriero-оценкой памяти: оценщик считает draw по `--gpu-memory-utilization`, и переопределение числа блоков сделает фактическое потребление меньше декларированного (память все равно зарезервирована), а планирование — бессмысленно точным.

## Влияние на производительность и память

- **VRAM.** Меняет размер тензоров KV-cache. Зарезервированный движком бюджет при этом остается прежним, так что «сэкономленная» память просто не используется.
- **Throughput.** Прямо задает `Maximum concurrency`: меньше блоков — раньше начинается вытеснение и пересчет prefill.
- **max_model_len.** При `--max-model-len -1` auto-fit подбирает длину под переопределенную емкость, а не под реальную память.
- **Время старта.** Не меняется: профилирование выполняется.

## Взаимодействие с другими аргументами

- `--gpu-memory-utilization`: определяет реально зарезервированную память; переопределение действует поверх и обесценивает связь между бюджетом и емкостью.
- `--kv-cache-memory-bytes`: задает байты под KV-cache; переопределение числа блоков применяется после и выигрывает.
- `--block-size`: вместе с числом блоков определяет емкость в токенах.
- `--max-model-len`: проверка «хотя бы один запрос» выполняется по переопределенной емкости; при `-1` длина подбирается под нее.
- `--max-num-seqs`: при малом числе блоков заявленное число последовательностей физически недостижимо, и планировщик начнет вытеснять.

## Типовые проблемы и диагностика

- **Симптом:** `To serve at least one request with the model's max seq len (N), (X GiB KV cache is needed, which is larger than the available KV cache memory (Y GiB).` при большом свободном объеме на карте. **Причина:** переопределение задало слишком мало блоков; проверка идет по пересчитанной емкости. **Лечение:** увеличить значение или убрать флаг.
- **Симптом:** постоянные вытеснения и низкий throughput. **Причина:** это и есть назначение аргумента. **Проверка:** строка `Overriding num_gpu_blocks=<профилированное> with num_gpu_blocks_override=<ваше>` в логе старта и `Preemptions: N` в периодическом логе.
- **Симптом:** OOM при аллокации KV-cache. **Причина:** значение больше того, что помещается в память; верхняя граница не проверяется. **Лечение:** уменьшить значение.
- **Подтверждение итоговой емкости:** `GPU KV cache size: N tokens, Maximum concurrency for M tokens per request: X.XXx`.

## Примеры

```bash
vllm serve /models/Qwen3-4B --num-gpu-blocks-override 256 --max-model-len 2048
```

```bash
vllm serve /models/Qwen3-4B --num-gpu-blocks-override 512 --block-size 16 --max-num-seqs 16
```
