# --ssl-cert-reqs

## Кратко

Аргумент повторяет константы `ssl.CERT_*` из стандартной библиотеки Python и задает, требует ли сервер сертификат от клиента. Значение — целое число, а не имя константы.

По умолчанию `0` (`CERT_NONE`): клиентский сертификат не запрашивается вообще, даже если задан `--ssl-ca-certs`.

## Оригинальная справка

```text
Whether client certificate is required (see stdlib ssl module's).
```

## Паспорт аргумента

- Флаги: `--ssl-cert-reqs`
- Группа argparse: `Frontend`
- Тип значения: int
- Допустимые значения: `0` — `ssl.CERT_NONE`, `1` — `ssl.CERT_OPTIONAL`, `2` — `ssl.CERT_REQUIRED`; список `choices` в argparse не задан, поэтому парсер примет любое целое, а отвергнет его уже модуль `ssl`
- Значение по умолчанию: `int(ssl.CERT_NONE)`, то есть `0`
- Эффективное значение: не переопределяется; уходит в `uvicorn.Config(ssl_cert_reqs=...)` и далее в `SSLContext.verify_mode`
- Где объявлен: `vllm/entrypoints/openai/cli_args.py:FrontendArgs.ssl_cert_reqs`
- Этап применения: HTTP-слой, `serve_http()` → `uvicorn.Config(...).load()`

## Что меняет в движке

vLLM только пробрасывает число в uvicorn: `serve_http(..., ssl_cert_reqs=args.ssl_cert_reqs, ...)`. Смысл значений полностью определяется модулем `ssl`:

- `0` — сертификат клиента не запрашивается;
- `1` — запрашивается, но соединение не разрывается, если его нет; предъявленный сертификат при этом проверяется по CA;
- `2` — обязателен и должен проверяться по CA из `--ssl-ca-certs`.

Проверенный сертификат клиента дальше в приложение не пробрасывается: маршрутов, которые различали бы клиентов по subject, у vLLM нет. То есть mTLS здесь — транспортный фильтр, а не механизм авторизации по идентичности.

## Значения и формат

- Пишется цифрой: `--ssl-cert-reqs 2`. Имя `CERT_REQUIRED` парсер не примет как строку — тип аргумента `int`.
- `1` и `2` без `--ssl-ca-certs` бессмысленны: проверять цепочку не по чему, обязательный режим приведет к отказам на рукопожатии.
- Значение действует только при включенном TLS (`--ssl-certfile` + `--ssl-keyfile`).

## Когда использовать

- `2` — когда доступ к серверу должен быть ограничен клиентами с выданными вами сертификатами и это единственный контур аутентификации транспорта.
- `1` — промежуточный режим на время миграции: клиенты уже могут предъявлять сертификат, но еще не обязаны.
- Для управляемых инстансов arriero не используйте: менеджер ходит на инстанс по `http://<host>:<port>` (`docs/API_PROXY_FOUNDATION.md`, arriero) и сертификат не предъявляет.

## Влияние на производительность и память

Не влияет на память; проверка цепочки клиента добавляет работу на каждое рукопожатие.

## Взаимодействие с другими аргументами

- `--ssl-ca-certs`: обязательный спутник для `1` и `2`.
- `--ssl-certfile`, `--ssl-keyfile`: без них TLS не включен и режим проверки не применяется.
- `--api-key`: независимые уровни. mTLS отсекает клиентов на транспорте, ключ — на HTTP, и только на защищенных префиксах.

## Типовые проблемы и диагностика

- **Симптом:** все клиенты получают ошибку рукопожатия после включения `2`. **Причина:** не задан `--ssl-ca-certs` или сертификаты выпущены другим CA. **Лечение:** указать правильный файл CA.
- **Симптом:** значение задано, но клиентов без сертификата по-прежнему пускает. **Причина:** оставлен режим `0` или TLS вообще не включен. **Проверка:** адрес в логе должен начинаться с `https://`.
- **Симптом:** `ValueError` при построении контекста. **Причина:** передано число вне диапазона `0..2`. **Лечение:** использовать только `0`, `1` или `2`.

## Примеры

```bash
vllm serve /models/Qwen3-4B --host 0.0.0.0 --ssl-certfile /etc/ssl/vllm/fullchain.pem --ssl-keyfile /etc/ssl/vllm/privkey.pem --ssl-ca-certs /etc/ssl/vllm/clients-ca.pem --ssl-cert-reqs 2
```

```bash
vllm serve /models/Qwen3-4B --host 0.0.0.0 --ssl-certfile /etc/ssl/vllm/fullchain.pem --ssl-keyfile /etc/ssl/vllm/privkey.pem --ssl-ca-certs /etc/ssl/vllm/clients-ca.pem --ssl-cert-reqs 1
```
