# --h11-max-incomplete-event-size

## Кратко

vLLM выставляет два лимита парсера h11: этот и `--h11-max-header-count`. Оба нужны против запросов с раздутыми заголовками — типичного дешевого способа занять память фронтенда.

Ключевая оговорка: uvicorn выбирает реализацию HTTP автоматически, и при установленном `httptools` она будет не h11. В таком окружении оба лимита не применяются, хотя аргументы принимаются без возражений.

## Оригинальная справка

```text
Maximum size (bytes) of an incomplete HTTP event (header or body) for
h11 parser. Helps mitigate header abuse. Default: 4194304 (4 MB).
```

## Паспорт аргумента

- Флаги: `--h11-max-incomplete-event-size`
- Группа argparse: `Frontend`
- Тип значения: int (байты)
- Допустимые значения: не ограничены; проверок в vLLM нет
- Значение по умолчанию: `default` в extract записан выражением `H11_MAX_INCOMPLETE_EVENT_SIZE_DEFAULT` — это константа `4194304` (4 MiB) из `vllm/entrypoints/serve/utils/constants.py`
- Эффективное значение: `serve_http` подставляет ту же константу, если значение почему-то `None`; фактическое применение зависит от того, какую реализацию HTTP выбрал uvicorn
- Где объявлен: `vllm/entrypoints/openai/cli_args.py:FrontendArgs.h11_max_incomplete_event_size`
- Этап применения: конфигурация uvicorn при запуске HTTP-сервера

## Что меняет в движке

`run_server` передает значение в `serve_http` (`vllm/entrypoints/launcher.py`), где оно вынимается из `uvicorn_kwargs` и присваивается напрямую полю конфигурации:

```text
config = uvicorn.Config(app, **uvicorn_kwargs)
config.h11_max_incomplete_event_size = h11_max_incomplete_event_size
config.h11_max_header_count = h11_max_header_count
```

Поле читает протокол h11: он копит байты незавершенного события (стартовая строка и заголовки до пустой строки) и при превышении лимита обрывает соединение ответом 431. Тело запроса передается потоково и под этот лимит не подпадает, несмотря на формулировку справки.

vLLM не передает `uvicorn.Config` параметр `http`, поэтому действует значение uvicorn по умолчанию — `auto`. Реализация выбирается по наличию `httptools` в окружении: при нем берется httptools-протокол, у которого свои встроенные лимиты и который эти два поля не читает. Проверить свое окружение можно так:

```bash
python -c "import httptools; print(httptools.__version__)"
```

Ошибка импорта означает, что используется h11 и лимиты работают.

Тот же набор аргументов применяется и в render-режиме (`build_and_serve_renderer`).

## Значения и формат

- Целое число байт: `--h11-max-incomplete-event-size 65536`.
- Значение по умолчанию — 4 MiB, то есть очень щедрый лимит для заголовков.
- Ноль и отрицательные значения не отвергаются vLLM; поведение при них определяется uvicorn/h11 и по существу означает «любой заголовок слишком велик».
- Единиц измерения кроме байт нет; суффиксы вроде `4M` в этом аргументе не поддерживаются.

## Когда использовать

- Инстанс доступен не только с localhost: 4 MiB заголовков на соединение — слишком много, чтобы это оставлять по умолчанию. Разумный потолок для OpenAI-совместимого API — десятки килобайт.
- Наоборот, поднимайте лимит, если легитимный клиент шлет крупные заголовки (длинные токены авторизации, трассировочные заголовки прокси) и получает 431.
- Не используйте как ограничение размера промпта: тело запроса под лимит не попадает. Размер входа ограничивают `--max-model-len` и параметры планировщика.
- Не задавайте вслепую, не проверив, какая реализация HTTP используется: в окружении с `httptools` аргумент молча ничего не сделает.

## Влияние на производительность и память

Ограничивает верхнюю границу памяти, которую одно неполное соединение может занять в процессе API-сервера. На VRAM, KV-cache, throughput и latency инференса не влияет. Экономия ощутима только под атакой или при ошибочном клиенте, шлющем бесконечные заголовки.

## Взаимодействие с другими аргументами

- `--h11-max-header-count`: второй лимит того же парсера (по умолчанию 256 заголовков), выставляется тем же кодом. Их имеет смысл настраивать вместе.
- `--api-key`: авторизация проверяется уже после разбора заголовков, поэтому лимит защищает и от неаутентифицированных запросов.
- `--middleware`: пользовательское ASGI-middleware работает после парсера; ограничить размер заголовков им не получится.
- `--max-model-len`: то, чем действительно ограничивается размер полезной нагрузки.

## Типовые проблемы и диагностика

- **Симптом:** клиент получает 431 (Request Header Fields Too Large). **Причина:** суммарный размер заголовков превысил лимит. **Проверка:** размер заголовков запроса, включая накопленные прокси. **Лечение:** повысить лимит или уменьшить заголовки на стороне клиента/прокси.
- **Симптом:** лимит понижен, но большие заголовки проходят. **Причина:** используется httptools-реализация, и поле не читается. **Проверка:** `python -c "import httptools"` в окружении инстанса. **Лечение:** ограничивать заголовки на обратном прокси перед vLLM.
- **Симптом:** большое тело запроса отвергается, и это списывают на этот аргумент. **Причина:** тело под лимит не подпадает; отказ пришел из валидации запроса или из ограничений длины контекста. **Лечение:** смотреть текст ошибки и `--max-model-len`.
- **Подтверждение принятого значения:** непустое значение видно в строке `non-default args: {...}` при старте; фактический эффект проверяется запросом с заголовком заведомо большего размера.

## Примеры

```bash
vllm serve /models/Qwen3-4B --h11-max-incomplete-event-size 65536 --h11-max-header-count 64
```

```bash
vllm serve /models/Qwen3-4B --h11-max-incomplete-event-size 1048576 --host 127.0.0.1
```
