# --trust-remote-code

## Кратко

`--trust-remote-code` снимает запрет `transformers` на исполнение `*.py` из репозитория модели. Без него кастомная архитектура, которой еще нет в `transformers`, не загрузится; с ним репозиторий получает произвольное выполнение кода в процессе движка.

Это не «ручка совместимости», а решение о доверии конкретному репозиторию **и конкретной ревизии**. Флаг никак не ограничивает, что именно исполняемый код делает.

## Оригинальная справка

```text
Trust remote code (e.g., from HuggingFace) when downloading the model
and tokenizer.
```

## Паспорт аргумента

- Флаги: `--trust-remote-code`, `--no-trust-remote-code`
- Группа argparse: `ModelConfig`
- Тип значения: bool
- Допустимые значения: флаг без значения (`--trust-remote-code`) либо парная отрицательная форма (`--no-trust-remote-code`)
- Значение по умолчанию: `false`
- Эффективное значение: не переопределяется глобально, но локально гасится: если `model_type` чекпойнта есть в собственном реестре конфигов vLLM (`_CONFIG_REGISTRY`), vLLM регистрирует свой класс конфига и вызывает `AutoConfig.from_pretrained` уже с `trust_remote_code=False` — «теперь это не удаленный код»
- Где объявлен: `vllm/config/model.py:ModelConfig.trust_remote_code`
- Этап применения: сборка `ModelConfig` (чтение `config.json`) → загрузка токенизатора → резолв класса модели (в том числе Transformers-fallback) → во **всех** процессах-воркерах

## Что меняет в движке

Значение прокидывается в три независимые точки, каждая из которых — исполнение чужого кода:

1. **Конфиг.** `get_config(...)` вызывает `AutoConfig.from_pretrained(model, trust_remote_code=..., revision=..., code_revision=...)`. При включенном флаге `transformers` скачивает и импортирует `configuration_*.py` из репозитория. Импортированные классы оседают в кеше модулей HF (`transformers_modules`).
2. **Токенизатор.** `cached_tokenizer_from_config` и `resolve_tokenizer_args` передают тот же флаг в `from_pretrained`, то есть репозиторий может принести собственный класс токенизатора.
3. **Класс модели.** В Transformers-fallback (`_try_resolve_transformers`) `try_get_class_from_dynamic_module(...)` загружает класс модели по `auto_map` — снова импорт стороннего модуля.

Дополнительно, при включенном флаге вызывается `maybe_register_config_serialize_by_value()`: `transformers_modules` регистрируется в cloudpickle «по значению», чтобы кастомный класс конфига пережил передачу в воркеры и на другие узлы. Если это не удалось, в логе появляется предупреждение `Unable to register remote classes used by trust_remote_code with by-value serialization. This may lead to a later error. If remote code is not needed remove '--trust-remote-code'`. Практический смысл: код едет в каждый рабочий процесс, а не только во фронтенд.

Флаг входит в ключ кеша резолва архитектуры (`get_model_architecture`) вместе с `model`, `runner_type`, `convert_type` и `model_impl`.

## Значения и формат

- Не задан — `false`: удаленный код не исполняется. Репозиторий с кастомной архитектурой упадет на чтении конфига.
- `--trust-remote-code` — включить.
- `--no-trust-remote-code` — явно выключить; полезно, чтобы перебить значение, пришедшее из `--config` YAML (значения из файла подставляются **до** явных флагов, поэтому явный флаг выигрывает).
- Промежуточных режимов вроде «доверять только токенизатору» нет.

## Когда использовать

- Когда модель объективно требует своего кода: конфиг ссылается на `auto_map`, а архитектуры еще нет в установленной версии `transformers` и нет нативной реализации в vLLM.
- Когда вы контролируете репозиторий — например, веса лежат локально и `*.py` в них прочитаны глазами.
- Не включайте «на всякий случай» и не оставляйте включенным в шаблоне инстанса: флаг ничего не ускоряет и не расширяет функциональность для моделей, которым он не нужен.
- Не включайте для репозитория, который вы указываете веткой (`--revision main`): содержимое ветки может измениться между перезапусками, а вместе с ним и исполняемый код.

## Влияние на производительность и память

На производительность и память сам флаг не влияет: он лишь разрешает импорт дополнительных модулей. Единственный измеримый эффект — небольшое увеличение времени старта на скачивание и импорт `*.py` и заполнение кеша модулей HF.

## Взаимодействие с другими аргументами

- `--model`, `--tokenizer`: именно их репозитории получают право исполнять код; если токенизатор взят из другого репозитория, доверие распространяется и на него.
- `--revision`, `--code-revision`: единственный способ зафиксировать, **какой** код будет исполнен. `--code-revision` пинит именно ревизию удаленного кода, отдельно от весов.
- `--model-impl transformers`: Transformers-fallback опирается на `auto_map`, то есть для кастомных моделей требует этот флаг.
- `--config-format`: определяет, какой парсер конфига будет использован до того, как встанет вопрос об удаленном коде.
- `--allowed-local-media-path`: другой аргумент, ослабляющий изоляцию сервера; вместе с этим флагом дает исполняемому коду и доступ к путям, объявленным для медиа.

## Типовые проблемы и диагностика

- **Симптом:** `Failed to load the model config. If the model is a custom model not yet available in the HuggingFace transformers library, consider setting 'trust_remote_code=True' in LLM or using the '--trust-remote-code' flag in the CLI.` **Причина:** репозиторий требует исполнить свой файл конфигурации. **Лечение:** либо включить флаг осознанно, либо взять чекпойнт с архитектурой, поддержанной нативно.
- **Симптом:** `Unable to register remote classes used by trust_remote_code with by-value serialization…` в логе старта. **Причина:** cloudpickle не смог зарегистрировать `transformers_modules`. **Следствие:** возможна более поздняя ошибка при передаче конфига в воркер. **Лечение:** проверить, действительно ли удаленный код нужен.
- **Симптом:** модель загружается по-разному на двух перезапусках без изменения аргументов. **Причина:** `--revision` указывает на подвижную ветку, содержимое репозитория (включая исполняемый код) изменилось. **Лечение:** зафиксировать коммит в `--revision` и `--code-revision`.
- **Симптом:** флаг включен, а поведение не изменилось. **Причина:** для `model_type` из `_CONFIG_REGISTRY` vLLM подставляет собственный класс конфига и отключает удаленный код для этого вызова. **Проверка:** `vllm/transformers_utils/config.py`, ветка регистрации класса конфига.

## Безопасность на общем хосте

Что именно получает автор репозитория при включенном флаге:

- выполнение произвольного Python в процессе фронтенда и в каждом воркере, с правами того пользователя, под которым запущен движок;
- доступ ко всей файловой системе, видимой этому пользователю. В arriero это, в частности, каталог конфигурации `data/config/` вместе с `config/.secrets.json`, где лежат ключи API-эндпоинтов и ключи источников прокси;
- сетевой доступ: код исполняется до старта HTTP-слоя и никак не изолирован;
- персистентность: импортированные модули оседают в кеше HF (`transformers_modules`) и переиспользуются на следующих стартах.

Практические следствия для управляемого сервера:

- включайте флаг **на конкретном инстансе**, а не в шаблоне аргументов по умолчанию;
- всегда вместе с ним фиксируйте `--revision` (и `--code-revision`, если код живет отдельно) коммит-хешем, а не веткой;
- предпочтительный вариант — скачать репозиторий локально, прочитать все `*.py` и запускать по локальному пути: тогда содержимое не меняется без вашего участия;
- относитесь к включению флага как к установке пакета из этого репозитория, а не как к опции загрузчика.

## Примеры

```bash
vllm serve /models/custom-arch-model --trust-remote-code --max-model-len 8192
```

```bash
vllm serve org/custom-arch-model --trust-remote-code --revision 3f1c9d2ab4e5f6789012345678abcdef01234567 --code-revision 3f1c9d2ab4e5f6789012345678abcdef01234567
```
